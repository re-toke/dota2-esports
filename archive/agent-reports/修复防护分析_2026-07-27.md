# 历史显示/状态问题修复 — 系统性防护分析

> 分析对象：三轮历史修复（P1 状态判定一致性 / P2 状态判定逻辑优化 / P3 赛事信息展示准确性）。
> 目标：复现风险评估 → 现有防护盘点 → 防护缺口与改进建议。
> 日期：2026-07-27 ｜ 范围：dota2-esports 微信小程序 + 云函数。

---

## 历史问题编号定义

- **P1 · 状态判定一致性 Bug**：赛事在列表页「全部」标签显示「已结束」、但「进行中」标签缺失；结束当日（7/27）边界处理错误；列表页标签分类与详情页状态判定不一致（EPL/EWC）。
- **P2 · 状态判定逻辑优化**：重新梳理「进行中/已结束」判定规则 — 明确边界条件、排查竞态（SQL 窗口缓存 TTL 2h vs 进行中 duration=0 未计入 lastEnd）、优化状态流转、覆盖异常场景。
- **P3 · 赛事信息展示准确性**：多模块直接用 OpenDota 原始名 `l.name`/`league_name`（未走 curation 规范名），导致「EPL Masters 2026」误显、CS2/DOTA2 跨游戏混淆、赛期用「已进行比赛窗口」而非 curation 完整赛期。

## 一、同类问题复现风险评估

### P1（状态判定一致性）
- **其他模块复现风险：中。**
  - 依据①：判定逻辑虽已收敛到 `util.isOngoing` + `leagues.js normalize()` 的 `util.statusOf` + curation 状态硬覆盖，但**任何未来新增的「按状态分类/筛选」展示位**（如新的「我的赛程」「赛事日历」组件）若自行实现判定而非复用 `statusOf`/`isOngoing`，会再次与详情页错位。
  - 依据②：列表页用 `getLeagueWindows` 的 **2h 缓存 SQL 聚合 lastEnd**，详情页用新鲜 `/leagues/{id}/matches`；二者新鲜度差天然存在。修复靠 curation 日期/状态硬覆盖消除差异，**仅当 curation 有该赛事条目时生效**——若某赛事 curation 无覆盖，列表仍可能因缓存陈旧与详情短暂不一致。
  - 依据③：`ongoingBufferSec=2h` 是**单点配置**，历史上正是其旧值（7 天）导致状态卡死；若未来被调回大值，P1 立即复现（配置回归型）。
- **未来迭代风险：中。** P1 当初就是在「新增列表页标签分类」时因复用旧 `l.name`+旧窗口判定而引入，属典型扩散失败。

### P2（状态判定逻辑优化）
- **其他模块复现风险：低–中。**
  - 依据：判定已收敛到 `util.js` 单一函数，下游（`normalize`、`statusOf`）均调用它，扩散面小。
  - 残留①：第三路径兜底（duration=0 且 latest 在缓冲内）对「回填且 duration=0、start 较新」的赛事**无法与真正进行中区分**（working memory 已记为已知局限），仅能靠 curation `status` 硬覆盖纠偏。
  - 残留②：SQL `lastEnd` 缓存 TTL 2h 仍可能在 live 窗口内造成列表/详情**瞬时**不一致（结构性，未根除）。
- **未来迭代风险：中。** 若未来新增第 4 条判定路径或调整优先级而不保留「路径①（OpenDota 真实结束）最精确」原则，会重新引入边界误判；`ongoingBufferSec` 单点配置回归风险高。

### P3（展示名覆盖缺失）
- **其他模块复现风险：高。**
  - 依据①：本轮就是「详情页修了、其余 9 处漏了」的典型扩散失败；修复靠人工全量 Grep 排查，**无机制保证**。任何**新增展示位**（新页面/组件/云函数）几乎必然再次直接用 `l.name`/`league_name`——开发者拿到联赛对象的第一反应是 `item.name`，而「安全路径」不是默认路径。
  - 依据②：`cloudfunctions/aggregation` 是**独立部署**，含一份平行 `canonicalLeagueName` 副本（`index.js:36`），与 `curation.js` 双源；任一侧更新别名都会漂移。
  - 依据③：`getLeagueName`（consensus 投票器，`sources.js:98`，仍导出）其「取更长名」规则在缺乏 canonical 覆盖时仍可能选回旧名——属潜在误用点（detail 页 `league-detail.js:224` 仍把它当 fallback）。
- **未来迭代风险：高。** 展示位是**开放集合**（随功能增长），约束却是「每个新展示位都记得调函数」——这是最难靠人工维持的不变量。

**风险评估结论**：P3 残留与复发风险最高（开放集合 + 非默认安全路径）；P1/P2 因逻辑已集中，风险中等且偏「配置回归型」。

## 二、防护机制盘点（当前已实施）

### A. 代码层（已落地）
1. **`utils/sources.js → canonicalLeagueName(rawName)`**（`sources.js:464`，已导出 `:682`）：单一覆盖入口，curation canonical 优先，否则原样返回。✅ 核心防护。
2. **详情页 `league-detail.js finalize()`**：优先级 ①curation canonical > ②consensus，与集中函数口径一致，避免 detail 回归。
3. **`pages/leagues/leagues.js normalize()`**（`leagues.js:349` 等）：状态走 `util.statusOf` + curation `status` 硬覆盖；`name` 走 `canonicalLeagueName`；`dateRange` 优先 curation 完整赛期（cur.start/cur.end）回退比赛窗口；返回补 startDate/endDate。
4. **`utils/util.js isOngoing`**：三路径优先级（OpenDota 真实结束 > curation/外部源日期 > 未结算兜底）+ `ongoingBufferSec=2h` 统一边界；`statusOf(mixed)` 出口。
5. **`utils/curation.js`**：EPL 条目补 `epl2026` 别名；canonical 权威展示名、别名跨游戏隔离、start/end 完整、status 字段规范（working memory 记载）。
6. **`cloudfunctions/aggregation/index.js`**：内联 `canonicalLeagueName`（`index.js:36`），推送 `thing1` 走规范名（`index.js:716`）。
7. **验证脚本**（上一轮临时 `_verify_canonical.js`）：运行时校验映射+赛期，已跑通但**未持久化**。

### B. 工程设施（已存在，但有限）
8. **ESLint**（`package.json` `lint` 脚本 + `.eslintrc.json`）：仅通用风格/正确性规则（`no-undef`、`no-redeclare`、`semi`、`prefer-const` 等），**无领域专用规则**——对 P3 类「直接用原始联赛名」零拦截。
9. **既有测试脚本**（`scripts/test-sources.js`、`test-consensus.js`、`test-incremental.js`、`test-series.js`，见 `CODE_WIKI.md:617-620`）：覆盖多源回退链、consensus 名称/时间/分级投票。**未覆盖**本次新增的 `canonicalLeagueName`、curation 赛期优先级、列表/详情状态一致性。
10. **文档 `CODE_WIKI.md`**：记载测试运行方式、架构与 curation 约定——作为人工 code-review 参考。
11. **手动 `node --check` 全量语法校验**：每次修改后人工执行，非自动化。

### C. 流程层
12. **数据变更评审约定**（working memory 记载的 curation 规范）：新增/修改赛事条目需 canonical 正确、别名跨游戏隔离、start/end 完整——但为「记忆约定」，非强制检查点。

## 三、防护缺口与改进建议

> 优先级：高 / 中 / 低。预期拦截效果指「该措施能挡住哪类复发」。

### 【高】G1 — 让安全路径成为默认路径：在数据层注入 `displayName`
- **方案**：在 `sources`/归一化层返回的 league 对象上直接附带 `displayName`（= `canonicalLeagueName(name)`），下游展示位直接用 `item.displayName`，无需记忆调用。把「必须调函数」的不变量从 N 个展示位收敛为 **1 个数据出口**。
- **预期拦截**：彻底消除 P3 类「新增展示位漏调」复发（开放集合 → 单点保证）。WXML 中 `{{item.name}}` 无法被 ESLint 管，G1 从根上解决。
- **落地**：改 `sources` 归一化函数与 `normalize()` 使返回含 `displayName`；逐步将现有 `canonicalLeagueName(x.name)` 调用替换为读 `x.displayName`。成本低。

### 【高】G2 — 为 `canonicalLeagueName` / 赛期 / 状态一致性补自动化测试，接入 `npm test`
- **方案**：在 `scripts/` 新增 `test-canonical.js`（沿用现有 `check`/`assert` 运行器），断言：
  ① `canonicalLeagueName('EPL Masters 2026')` → `'EPL Masters I'`；② `canonicalLeagueName('EPL 2026')` → `'EPL Masters I'`；③ 无匹配名原样返回；④ curation 赛期 `formatDateRange(cur.start,cur.end)` = `7/20–8/12`（非窗口 `7/20–7/27`）；⑤ 对一组已知赛事断言 `normalize` 状态 == `finalize`/`isOngoing` 状态（列表 vs 详情一致）。
  在 `package.json` 加 `"test": "node scripts/test-sources.js && node scripts/test-consensus.js && node scripts/test-canonical.js ..."`。
- **预期拦截**：P3（映射/别名/赛期回归）、P1（列表/详情状态不一致回归）**首次复现即红**。复用现有 runner，落地成本低。

### 【高】G3 — 自定义 ESLint 规则 / 约定，拦截「展示路径直接用原始联赛名」
- **方案（轻量）**：在 `.eslintrc.json` 加 `no-restricted-syntax` 或自定义 rule，禁止在赋值给 `name`/`leagueName`/`league`/`title` 等展示字段时直接引用 `*.league_name` / `l.name` / `m.league.name`（未经 `canonicalLeagueName`/`displayName` 包裹）。配合 `CODE_WIKI`/AGENTS 约定 + review 清单明确「展示联赛名必须来自 `displayName`/`canonicalLeagueName`」。
- **预期拦截**：P3 类直接在 JS 里写 `name: l.name` 的新增代码（静态拦截，合入前）。WXML 部分需 G1 兜底。

### 【中】G4 — 云函数与小程序共用同一份 curation 映射，消除双源漂移
- **方案**：把别名/规范名映射抽成 `utils/curation-shared.json`（或云函数运行时从同一数据源拉取），小程序 `sources.canonicalLeagueName` 与云函数 `canonicalLeagueName` 都引用同一份；或云函数部署时由脚本从 `curation.js` 导出注入。加测试断言两侧映射等价。
- **预期拦截**：P3 跨端（小程序 vs 云推送）展示名不一致复发。

### 【中】G5 — 收敛 / 标记 `getLeagueName` 仅用于匹配，禁止展示用途
- **方案**：`getLeagueName` 重命名为 `voteLeagueNameForMatch`（或加 `@deprecated` + lint 禁用），明确其 consensus 结果仅用于索引/匹配；展示一律走 `canonicalLeagueName`/`displayName`；从 detail 页移除对它的展示依赖（detail 已有 `finalize` canonical 优先，可去掉该 fallback 或明确其只用于「无 curation 且无 canonical」兜底）。
- **预期拦截**：P3 因误用 consensus「取更长名」选回旧名。

### 【中】G6 — curation 数据变更评审清单 + 快照校验
- **方案**：在 `CODE_WIKI`/AGENTS 加「赛事条目变更 checklist」（canonical 正确性、别名跨游戏隔离、start/end 完整、status 与 OpenDota 一致）；`test-canonical.js` 加 curation 条目断言快照（如 EPL `canonical==='EPL Masters I'`、`status==='进行中'`）。
- **预期拦截**：P3 数据层（跨游戏混淆、别名遗漏、赛期错）回归。

### 【中】G7 — CI 拦截（若仓库托管于 git 平台）
- **方案**：加 `.github/workflows/ci.yml`：PR 时跑 `npm run lint` + `npm test` + 全量 `node --check`（utils/pages/subpackages/cloudfunctions）。
- **预期拦截**：把 G2/G3 从「本地可跑」升级为「合入强制」，杜绝「忘记跑测试就合入」。依赖 G2 先有 `npm test`。

### 【低】G8 — 监控 / 告警（运行时发现残余）
- **方案**：线上对「展示名与 curation 不匹配」「列表/详情状态不一致」打点上报（利用现有 analytics）。
- **预期拦截**：兜底发现未被测试覆盖的残余实例（如新数据源引入的例外）。

### 【低】G9 — pre-commit hook（husky + lint-staged）
- **方案**：提交时自动跑受影响文件的 `eslint` + 相关 `test-sources`，阻断带语法/规则错误的提交。
- **预期拦截**：把 G3/G2 前移到个人提交阶段，减少 CI 噪音。

## 风险总评与建议落地顺序

| 问题 | 复发风险 | 主要缺口 |
|------|----------|----------|
| P1 状态一致性 | 中 | 无状态一致性测试、缓存 TTL 结构性差异、`ongoingBufferSec` 单点配置 |
| P2 判定逻辑 | 低–中 | 第三路径兜底局限、配置回归风险 |
| P3 展示名 | **高** | 非默认安全路径、云函数双源、无 `canonicalLeagueName` 测试、ESLint 无领域规则 |

**推荐落地顺序（杠杆从高到低、成本从低到高）：**
1. **G1 + G2**（最高杠杆、最低成本、直接闭环 P3 + P1）—— 先做。
2. **G3**（静态拦截新增 `name: l.name`）。
3. **G4 / G5 / G6**（消除双源漂移、误用、数据层回归）。
4. **G7 / G9**（流程固化：CI + pre-commit）。
5. **G8**（运行时兜底监控）。

> 说明：当前所有防护中，**只有 G1（数据层 displayName）能从结构上消除 P3 的开放集合风险**；其余（测试/ESLint/CI）是「复发即红」的检测层。建议优先把「安全路径变为默认路径」，再叠加检测层。
