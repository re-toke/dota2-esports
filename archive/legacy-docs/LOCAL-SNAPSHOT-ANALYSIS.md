> 结论先行：**本地快照本质是用「发版频率」换「零服务端」**。它的有效刷新天花板是小程序重新上传 + 审核发布的周期，不是任何 cron 频率。

## 1. 当前更新频率机制（实况）

- **手动 build-time，运行时不刷新**。脚本在开发/构建阶段由人（或 CI）运行一次，把结果写死进包。
- `tryLocalUpcoming()` 在运行时执行 `require('../../utils/upcoming-local.json')` —— 同步、只读、随主包分发，**没有任何定时器、没有运行时网络拉取、没有增量 diff**。
- 脚本对 JSON 是**全量覆盖**：重新跑一遍 `main()`，`fs.writeFileSync` 整文件重写，并写入 `generatedAt` 时间戳。
- 数据规模约 2KB（当前 8 条），全量覆盖在成本上完全合理。

## 2. 定时刷新周期的几种实现与「用户可见下限」

| 方案 | 怎么做 | 用户看到新数据的真实下限 |
|------|--------|--------------------------|
| 现状 | 开发者发布前手动跑一次 | = 你的发版节奏 |
| Git pre-commit hook | 提交前自动跑脚本，保证入库即最新 | 仍须重新发布才到用户 |
| CI cron（GitHub Actions 每日） | 定时重抓并自动提 PR | 仍须人合并 + 重新发布 |
| 运行时从自建服务器拉 | 已超出“本地快照”范畴 → 等价于方案 B 代理，需 request 合法域名 | 实时，但不再是本地 |

**关键约束**：小程序包内静态资源更新，用户侧生效必须走「重新上传 + 审核发布」。所以无论你把脚本排得多密，**本地快照的有效刷新频率天花板 = 发版节奏**。这是分析所有下游影响的前提。

## 3. 增量更新策略

- **物理增量：不需要**。2KB 全量覆盖优于任何 diff/merge 逻辑，避免漂移与合并 bug。
- **逻辑稳定身份（已具备，需保持）**：事件 id 由 `hashId(name)` 用**归一名**哈希得出稳定负数。只要 Liquipedia 侧赛事名拼写不变，regeneration 后 id 一致 → `follow.isFollowed('leagues', id)` 等客户端状态跨刷新存活。这是“增量”真正该关心的点：保留客户端注解/关注，而非文件级 diff。
- 若将来要在快照上叠加客户端本地注解，应按**归一名（norm）做 key 合并**，而不是整体替换文件。

## 4. 对依赖模块的具体影响

### 4.1 数据一致性

- **读时一致性**：运行时 `require` 是静态副本，无并发写，不会与运行时状态互相打架；但它会随真实 Liquipedia **静默漂移**。
- **与 curation 的一致性**：`mergeCurationUpcoming()` 按**归一名**去重（不看 id），快照结果先入 `results`，curation 只补不重名项 → **快照优先、curation 补位**；`source` 字段（`liquipedia` / `community`）区分来源，两份静态源之间不会重复。潜在不一致：若 curation 日期比快照更新，因“先到先得”不会覆盖快照日期。
- **schema 一致性**：JSON 字段形状与 `buildUpcomingCard()` 强耦合，且**无版本号/无校验**。脚本改字段名即渲染异常，属于高暴露面。
- **时间一致性**：`parseLiquipediaDate` 用 `Date.UTC` 取 UTC 零点；倒计时在本地时区计算，可能有数小时偏差（对“几天后开赛”无影响）。`generatedAt` 可用来显示“数据截至 YYYY-MM-DD”并标过期。

### 4.2 延迟容忍度（by module）

| 模块 | 延迟容忍度 | 说明 |
|------|-----------|------|
| leagues 即将到来 tab | **高** | 非交易/非实时；但赛事改期、临时增删要等到下次发布才反映，倒计时可能基于旧日期 |
| follow 关注 | **中** | 关注状态按 id 绑定；上游改名 → id 变 → 关注“伪丢失” |
| mergeCurationUpcoming | **高** | 归一名去重稳定，快照/ curation 互补 |
| buildUpcomingCard | **高** | schema 契约，与延迟无关，但与快照字段正确性强相关 |
| 开赛提醒（若将来做） | **低** | 发布期延迟会直接污染提醒准确性 → **不应依赖快照**，必须走云端实时源 |

### 4.3 模块间耦合关系

- **直接消费者唯一**：`leagues.js` 的 `tryLocalUpcoming()`，且位于 `loadUpcoming` 回退链**末端**（云端 → 本地快照 → 串行 OpenDota+curation）。blast radius 被限制在这一个入口。
- **契约耦合（三处）**：
  1. `buildUpcomingCard` 字段形状契约（高暴露，无校验）；
  2. `follow` 存储的 id 键契约（依赖归一名稳定）；
  3. `mergeCurationUpcoming` 的 norm 去重契约（快照与 curation 靠同一条归一名对齐）。
- **物理耦合**：打进主包，`require` 同步加载，2KB 占包体可忽略；但更新需重新发布。
- **依赖方向单向**：快照 → `tryLocalUpcoming` → `mergeCurationUpcoming` → `setData` 渲染，无反向依赖，解耦良好。
- **风险点**：它是回退链最后一环——云端与串行都失败时，其正确性 = tab 是否为空。

## 5. 改进建议（落到可维护/可扩展）

1. **用 `generatedAt`**：tab 上显示“数据截至 YYYY-MM-DD”，超过 N 天自动标“可能过期”，把隐性陈旧变显性。
2. **CI 定时 + 自动 PR**：在不引入运行时效应的前提下，保证仓库内快照始终较新（仍需发布才到用户）。
3. **实时诉求走云函数**：项目已具备 `aggregation` 云函数（服务端可热更、免发版、免域名白名单）。本地快照明确定位为**离线兜底**，别指望它实时。
4. **加 `version` 字段 + 消费者轻量校验**：防止 schema 漂移导致渲染异常；版本不符时降级到 curation。
5. **保持归一名哈希 id**：这是关注状态等客户端数据跨刷新存活的锚点，不要改成随机 id 或按行号。
