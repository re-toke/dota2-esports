## 二、社区分级规则 Liquipedia 对齐（核心变更）

### 2.1 现有问题分析

当前 `COMMUNITY_TIERS` 是手工维护的正则规则集，存在以下问题：

1. **Elite League 严重低估**：社区规则标为 A（rank 2），但 Liquipedia 明确标为 Tier 1（S → rank 3）。$960K 奖金的 24 队国际赛事，与 DreamLeague 同级。
2. **1win Essence 系列粒度不足**：社区规则统一标为 A（rank 2），但 1win Essence II（$200K）已从 Liquipedia 获得 Tier 1 评级，而 1win Essence I（$100K）为 Tier 2。
3. **Games of the Future 低估**：社区规则标为 B（rank 1），但 2024 年赛事 Liquipedia 标为 Tier 2（A → rank 2），且奖金池 $1M。
4. **The Summit 过期**：社区规则中 The Summit 标为 A，但该系列自 2020 年以来未举办新赛事，在 2024+ 生态中已无实际影响。
5. **Clavision 无法验证**：社区规则中 Clavision 标为 A，但 Liquipedia 上 Clavision 页面无法通过 API 找到，需进一步确认。
6. **TI 分级一致**：社区规则中 TI 标为 S（rank 3），与 Liquipedia Tier 1 完全一致，无需修改。`DISPLAY_TIERS` 中的 SSS 条目保留不动（仅用于未来其他来源可能产生 rank>=4 的兜底展示），社区规则不再产出 SSS。

### 2.2 核心原则：三级兜底 + 加权投票

Liquipedia 的分级权威性通过以下机制保证：

1. **Liquipedia 源权重最高（4）**：`consensus.js` 中 `liquipedia: 4`，在冲突时 Liquipedia 胜出
2. **社区规则是零网络兜底**：仅当 Liquipedia 数据不可用时，社区正则规则才生效
3. **curation 是次优权威**：`curation: 3`，覆盖 Liquipedia 未收录的赛事

因此，社区规则的目标是：**在 Liquipedia 数据不可用时，产出与 Liquipedia 一致的分级**。

### 优化项 4：Liquipedia 赛程 phase 判定统一（来自 v1 优化项 4）

**保留但需要补充完善**。当前 `liquipedia-parse.js` 的 `parseMatchFields` 函数中 phase 判定缺少 24h 上界守卫：

```js
// 当前代码（liquipedia-parse.js L519-528）
if (finished) {
  phase = 'recent';
} else if (startTime > nowSec) {
  phase = 'upcoming';
} else {
  phase = 'live';  // 已开赛但未结束 → 缺少 24h 上界检查
}
```

**漏洞分析**：`sources.js` groupSeries 中 OpenDota 的 LIVE 判定已包含 24h 上界（`(nowSec - gStartSec) < 24 * 3600`），但 `liquipedia-parse.js` 的 Liquipedia 侧没有。导致：
- Liquipedia 标记的「已开赛未结束」比赛，如果开赛超过 24h，会被误判为 LIVE
- 而对应的 OpenDota 数据可能已判定为 RECENT（24h 超时），造成跨源 phase 不一致

**修复方案**：
```js
// 修复后
if (finished) {
  phase = 'recent';
} else if (startTime > nowSec) {
  phase = 'upcoming';
} else if ((nowSec - startTime) < 24 * 3600) {
  phase = 'live';  // 24h 上界，与 groupSeries 一致
} else {
  phase = 'recent';  // 超 24h 未结束 → 数据异常，降级为 recent
}
```

**变更**：
| 文件 | 行号 | 修改内容 |
|------|------|---------|
| `utils/liquipedia-parse.js` | L519-528 | `parseMatchFields` phase 判定增加 24h 上界守卫 |

## 四、新增优化项

### 优化项 10：Liquipedia 分级覆盖率监控（新增）

#### 问题描述

社区规则是否与 Liquipedia 一致，需要持续监控。当前 `cron-discover-tournaments` 云函数已发现新赛事，但未验证这些赛事在 Liquipedia 上的实际分级。

#### 方案

在 `npm run coverage` 脚本中新增 Liquipedia 分级覆盖率检查：

1. 从 `curation_events` 数据库读取所有评级为 S/A/B 的赛事
2. 对每个赛事名，调用 Liquipedia API 获取 `liquipediatier` 字段
3. 对比社区规则与 Liquipedia 分级，输出差异报告
4. 差异报告自动生成告警，提示需要更新社区规则或 curation 数据

#### 变更

| 文件 | 修改内容 |
|------|---------|
| `scripts/coverage.js` | 新增 Liquipedia 分级覆盖率检查函数 |
| `package.json` | `npm run coverage` 命令包含 Liquipedia 分级检查 |

#### 影响范围

- **正面**：持续监控社区规则与 Liquipedia 的一致性
- **风险**：低。不影响小程序运行，纯运维工具

### 优化项 11：Liquipedia Tier 数据本地缓存增强（新增）

#### 问题描述

当前 `getLeagueTier` 每次调用都独立抓取 Liquipedia wikitext，与 `getLeagueMetadata` 共享缓存但缓存 key 独立。这导致同一赛事可能发起两次 Liquipedia 请求（一次元数据，一次分级）。

#### 方案

在 `liquipedia.js` 中，`getLeagueTier` 优先复用 `getLeagueMetadata` 的缓存结果：

1. 先查 `liquipedia_league_` 缓存（`getLeagueMetadata` 写入）
2. 如果命中且 meta 中已有 `liquipediaTier` 字段，直接映射返回
3. 如果未命中或 meta 中无 `liquipediaTier`，才独立抓取

#### 变更

| 文件 | 修改内容 |
|------|---------|
| `utils/liquipedia.js` | `getLeagueTier` 增加缓存复用逻辑 |

#### 影响范围

- **正面**：减少约 50% 的 Liquipedia 请求量
- **风险**：低。缓存命中时直接返回，不增加网络延迟

### 优化项 12：curation 数据源 Liquipedia 分级同步（新增）

#### 问题描述

当 curation 中某赛事的分级与 Liquipedia 不一致时（如当前 Elite League 标为 A 但 Liquipedia 标为 Tier 1），`consensusTier` 投票中 curation（权重 3）会与 Liquipedia（权重 4）冲突。虽然 Liquipedia 最终胜出，但会增加不确定性。

#### 方案

在 `cron-discover-tournaments` 云函数中，新增定期同步 curation 赛事分级的任务：

1. 遍历 `curation_events` 数据库中有 `liquipediaSlug` 的条目
2. 对每个条目，调用 Liquipedia API 获取 `liquipediatier`

### 优化项 17：精确僵死检测 — 基于 BO 胜场条件（新增）

#### 问题描述

优化项 13 已提出 6 小时无更新自动降级，但不够精确。更精确的检测方式是：
- 如果已结算场数已达到 BO 类型所需胜场数（如 BO3 中一方已赢 2 局），则即使最后一局 `radiant_win` 为 null，也应判定该系列为 RECENT

**场景示例**：
- BO3 系列，前两局 A 队 2-0 领先（`radiant_win` 已结算），第三局已开赛但 `radiant_win` 仍为 null
- 当前判定：`isLive = true`（因为最后一局未结算且开赛时间在 24h 内）
- 实际状态：比赛实际上已经结束（A 队 2-0 横扫），但第三局数据延迟
- 正确判定：应为 RECENT（因为已无需再打第三局）

#### 方案

在 `sources.js` `groupSeries` 中，LIVE 判定增加 BO 胜场条件检测：

```js
// 在 isLive 判定后，增加精确僵死检测
// 如果已结算场数已达 BO 胜场条件，直接判定为 recent
const BO_WIN_THRESHOLD = { 'BO3': 2, 'BO5': 3, 'BO2': 2, 'BO1': 1 };
const winThreshold = BO_WIN_THRESHOLD[boType] || 0;
if (isLive && winThreshold > 0 && (scoreA >= winThreshold || scoreB >= winThreshold)) {
  isLive = false;
  // 标记为「精确僵死」，供 UI 显示提示
  // 注意：此场景仅发生在 OpenDota 数据延迟时，不影响比分显示
}
```

#### 变更

| 文件 | 行号 | 修改内容 |
|------|------|---------|
| `sources.js` groupSeries | L847-855 | 在 isLive 判定后，增加 BO 胜场条件精确僵死检测 |

#### 影响范围

- **正面**：更精确的僵死检测，减少 OpenDota 数据延迟导致的 LIVE 误判
- **风险**：低。仅在已满足胜场条件时才触发，不影响正常进行中的比赛
- **预期收益**：减少 LIVE 段中「实际上已结束」的比赛，提升数据准确性

### 优化项 18：Liquipedia 补充赛程 `isRecent` 字段语义修复（新增）

#### 问题描述

在 `league-detail.js` 的 Liquipedia 补充赛程转换中（L455-488），`isRecent` 字段直接从 `m.phase` 映射：

isRecent: m.phase === 'recent'

```js
// 修复后
const lastEnd = m.startTime || 0;
const isRecent = lastEnd && m.phase === 'recent' && (fmtNowSec - lastEnd) < 2 * 3600;
```

#### 变更

| 文件 | 行号 | 修改内容 |
|------|------|---------|
| `league-detail.js` | L464-465 | Liquipedia 补充赛程的 `isRecent` 按 2h 语义计算 |

#### 影响范围

- **正面**：字段语义统一，减少后续维护风险
- **风险**：极低。WXML 已不依赖 `s.isRecent` 字段

## 九、FAQ

### Q1：这些优化会影响现有数据吗？

不会。所有优化项仅限于展示层和排序逻辑，不涉及数据存储格式变更。

### Q2：优化后是否需要重新部署云函数？

P0/P1 全部不需要。仅 P2 的 ⑫ curation 分级同步需要云函数更新。

### Q3：社区规则调整后，Liquipedia 数据是否仍优先？

是的。`consensus.js` 中 `liquipedia: 4` 权重最高，社区规则 `community: 1` 权重最低。Liquipedia 数据可用时，始终以 Liquipedia 为准。

### Q4：TI 为什么是 S 而不是 SSS？

Liquipedia 将 TI 标为 Tier 1，与 DreamLeague、EWC、Elite League 同级。社区规则与之完全对齐，TI 不再使用 SSS 特殊等级，统一为 S 级（rank 3）。`DISPLAY_TIERS` 中的 SSS 条目保留不动（仅用于未来其他来源可能产生 rank>=4 的兜底展示），但社区规则不再产出 SSS。

### Q5：如何验证 Elite League 确实是 Liquipedia Tier 1？

已通过 Liquipedia API 直接验证：`liquipediatier=1, prizepoolusd=960000, type=Online, team_number=24`。FISSURE/ESB 联合主办，2024 年 Elite League Season 1 是 24 队国际赛事，奖金池 $960K，与 DreamLeague 处于同一量级。

### Q6：LIVE/UPCOMING/RECENT 三态判定的核心漏洞是什么？

共发现 6 个核心漏洞：

| # | 漏洞 | 影响 | 对应优化项 |
|---|------|------|-----------|
| 1 | Liquipedia `parseMatchFields` 缺少 24h 上界守卫 | 跨源 phase 不一致 | ④ |
| 2 | Liquipedia 补充 LIVE 在 league-detail.js 中无时间窗口过滤 | 异常 LIVE 数据污染 | ⑯ |
| 3 | OpenDota UPCOMING 无时间窗口限制 | 与 Liquipedia 窗口不一致 | ⑭ |
| 4 | 僵死检测缺失（仅 6h 阈值，无 BO 胜场条件） | 已结束比赛误判为 LIVE | ⑰ |
| 5 | Liquipedia RECENT 比赛比分缺失 | 用户看不到比赛结果 | ⑮ |
| 6 | Liquipedia 补充赛程的 `isRecent` 字段语义与 `groupSeries` 不一致 | 维护风险 | ⑱ |

### Q7：如何确保跨源 phase 一致？

通过三层守卫机制：
1. **liquipedia-parse.js 层**：24h 上界守卫（优化项 ④）
2. **league-detail.js 过滤层**：LIVE 24h 二次校验（优化项 ⑯）
3. **sources.js 层**：精确僵死检测（优化项 ⑰）

三层守卫独立工作，任一层都能阻止异常 LIVE 数据。
