# `normalize` 成本构成实测（2026-09-27 · "先测再改"）

> 目的：在决定"是否优化阶段 2"之前，**先量清 `normalize` 的成本构成**（复核 R8 / 三项意见 §4 留的口子）
> 结论：**① 找到了最大的一块（语义等价可省 45%）② 但它对"阶段 2 总时长"的贡献可能只有 ~16%**
> ⇒ **建议做一个 2 行的算法性修复（低风险、已证等价），但必须标注：用户可感知收益很小**
> ⚠️ 本报告**只测不改**，未改动任何业务代码。

---

## 1. 方法（以及为什么不能用模拟器）

| 手段 | 问题 |
|---|---|
| 模拟器 + `Date.now()` | **1ms 分辨率**，而单条 `normalize` 仅 1~2ms ⇒ 逐段增量大量为 0，**不可用** |
| ✅ 采用：Node 侧基准 | 桩化 `wx`/`Page`（同 `scripts/diag/repro-leagues-ongoing.js` 的手法），
用 **`process.hrtime.bigint()`（纳秒级）** 跑 591 条真实联赛；用**源码字符串变异**做**消融（ablation）** |

### ★ 方法论自纠：破坏式 vs 语义等价
第一轮我用了"破坏式"挖掉某段（V1~V3），**结果不可用** ——
例如挖掉快照匹配会让 `_snapHit` 恒为 null ⇒ **下游 `mergeEventPeriod` 走不同分支** ⇒
差值里**混入了副作用**，不能当作"该段的成本"。
⇒ 第二轮加做**语义等价变体**，并**逐条比对输出**（`JSON.stringify` 全等）才认账。

★ 每条变异都带**元断言**（锚点必须**恰好命中 1 次**），防"没替换成功 ⇒ 假验证"。

### 输入
OpenDota `/api/leagues` 全量 + 粗筛 ⇒ **591 条**（沙箱内可取到；非 EF 的 751，但**相对占比有效**）。
Windows 用 leagueid 派生的合成值（让 `validateLeagueWindow` 做真实工作，且可复现）。

## 2. 结果（取 3 次中位数）

```
V0  基线（完整 normalize）                     173.1ms   0.293ms/条
V0b 基线·第 2 遍（curation 缓存已热）             146.4ms   0.248ms/条   快 15.4%
── 语义等价候选（★ 可信）──
V6  leagueKey(e.name) 记忆化                   95.1ms   0.161ms/条   快 78.0ms / 45.1%   ✅ 输出逐条一致
── 破坏式（⚠️ 混入下游行为变化，仅作线索）──
V1  挖掉「快照匹配扫描」                        68.1ms   0.115ms/条   快 60.6%
V2  挖掉 curation 查表                        153.7ms   0.260ms/条   快 11.2%
V3  挖掉 validateLeagueWindow               136.3ms   0.231ms/条   快 21.3%
```

### 定位：贵的到底是什么？
`normalize` 里 L831-848 的快照匹配块，**每个联赛**都做了：
```js
_snap.events.find((e) => {
  const _en = leagueKey(e.name || '');     // ← 内层对**每个事件**重算 leagueKey
  return _en && (_en === _dn || _dn.indexOf(_en) >= 0 || _en.indexOf(_dn) >= 0);
});
```
⇒ **每个联赛扫全部 17 个事件**（`upcoming-local` 快照实测 M=17）⇒ **591 × 17 ≈ 10,047 次 `leagueKey`**，
而**事件名在 591 轮里是同一批** ⇒ 99.7% 是**重复计算** ⇒ 典型 **O(N×M)，且内层键每轮重算**。

单价实测（★ 这里我**先测错了一次**，见 §4）：
| 函数 | 单次 | ×10,047 |
|---|---|---|
| `names.normAsciiKey`（我**误用**的） | 0.44 µs | 4.4ms |
| **`sources.leagueKey`（页面真正用的）** | **3.88 µs** | **≈39ms** |

⇒ 与 V6 实测收益（78ms）**同量级**（差值部分来自测量方差与函数被调用时的内部缓存状态）⇒ **因果成立**。

## 3. ★★ 但必须泼一盆冷水：它对"阶段 2 总时长"的贡献可能只有 ~16%

- 真实阶段 2：**751 条 ≈ 1.3~1.4s**（模拟器实测，16 批 × 50 条，52~100ms/批）
- Node 里 `normalize` 单价 **0.293ms/条** ⇒ 751 条 ≈ **220ms**
- ⇒ `normalize` 自身**只占真实阶段 2 的约 16%**；**~84% 不在 `normalize` 里**
  （候选：模拟器引擎比 Node 慢数倍、**16 批之间的 `setTimeout` 事件循环切换**、批间 `setData`/渲染）
- 且 Node 绝对耗时比设备快近一个数量级 ⇒ **Node 的 45% 不能直接外推为"用户少等 45%"**

⇒ **本项优化的用户可感知收益上限**：
**≈ 50~100ms，且每会话仅一次**（阶段 2 只在首访执行）── **属于"低收益"**。

## 4. 我在这轮犯的两个测量错误（记录以防再犯）

1. **测错了函数**：micro 基准里我量的是 `names.normAsciiKey`，而页面用的是 `sources.leagueKey`
   （前者 0.44µs、后者 3.88µs，**差 8.8 倍**）⇒ 导致"V1 省 58% 但基元只要 7ms"的**假矛盾**，
   一度让我怀疑 V1 的变异有问题。
   ⇒ **教训：micro 基准必须用"调用点真正调用的那个函数"**（先 grep 调用点，再量）。
2. **破坏式消融的差值不可信**（见 §1）。⇒ 已加"语义等价 + 输出逐条比对"这一关。

## 5. 建议（等你拍板）

| 选项 | 评价 |
|---|---|
| **A（推荐）做那个记忆化** | 改动极小（模块级 memo + 一处调用点），**已被证明输出逐条一致**，风险低；<br>★ 它同时把 **O(N×M) 且内层键重算** 的写法修成 O(N+M)（**算法卫生**，快照变大时不会劣化）；<br>⚠️ 但收益上限 50~100ms/会话，**必须诚实标注"低收益"** |

| **C 若真想提速阶段 2** | 杠杆**不在 `normalize` 的数学**（只占 ~16%），而在**批间调度/事件循环/批间渲染**<br>⇒ 那需要另做一轮测量（先测再改） |

## 6. 诚实边界

- 输入是 **591 条（OpenDota 粗筛）**，非 EF 的 751 ⇒ **只保证相对占比**，绝对值不外推。
- Node 与小程序引擎差异**未量化**（§3 的"~16%"是**推算**，非实测）⇒ 标为**待设备复核**。
- 快照匹配块内 `require()` × 591 在 Node 里仅 **3.3ms**（可忽略）；**设备侧 `require` 成本未测**
  ⇒ 因此**不建议**顺带改 `require`（不做未测量的改动）。
- 未测 `unifiedTier` / 对象构造 / `tagThemeOf` 等剩余分段（本轮锚点未覆盖）；
  由 V4（挖掉 `statusOf`，仅快 3.3%）可见"状态判定"不是热点。
