## 2. 性能优化方向

> 每项按「**为什么优化** → **做什么** → **优化后会怎么样** → **风险**」四段写。

### P0-1 · 架构收口：明确云开发退役边界（本次复核新增，优先级最高）

- **为什么优化**：现在**同一份数据存在两条链路**（EF 缓存 + 云开发缓存），且 7 个 action 仍在云开发、触发器已停。这意味着一部分功能失去了原定的定时刷新能力，且两条链路的数据新鲜度、TTL、失效策略互不知情 → **不一致是必然的，只是还没被发现**。另外云开发触发器已停 6 天以上，如果那 7 个 action 原本依赖触发器预热，它们现在正在**冷启动**。
- **做什么**：① 逐条审计 7 个未迁 action 是否曾依赖已停的触发器（`schedulePreheat` 停用是 `阶段6` 明确标注的"**唯一无替代品**"）；② 确认 `liquipediaScheduledMatches`（详情页/首页赛程主源、文档标注"收益最大"）在无预热下的真实耗时；③ 给出云开发退役时间表或明确的"永久保留"清单。
- **优化后会怎么样**：把"沉默降级"变成"已知状态"。这一步不提升性能数字，但它决定后面所有性能优化**有没有意义** —— 因为在双链路下测出来的耗时是不可信的。
- **风险**：无（纯审计）。

### P0-2 · 文档对齐：补上 36 个版本号 / 148 个提交

- **为什么优化**：`阶段6` 手册里"已修 v8.87"这类信息**只存在于零散交付物中**，整合版技术文档的版本日志停在 v8.51。而项目的全部工程纪律（G14 双源一致、三处字节一致、铁律清单）都依赖"文档 = 事实"。现在这个前提已经破了 —— **上一轮我自己就被过时文档误导了一次**（把 Supabase 当灰度）。
- **做什么**：以 `git log` 为唯一事实源，把 v8.52 → v8.87 区间的落地项按既有三层结构（倒序版本日志 + 专题章节 + 索引）补进整合版；同时更新 §1.3 版本快照 / §1.4 提交链；并修正 README 的三处过时口径（"进行中 = 7 天"实际 2h、STRATZ 写"已停用"实际 `enabled: true`、目录结构仍写 `pages/league-detail`）。
- **优化后会怎么样**：后续任何优化方案有可信坐标系；新人（或下一次的我）不会重复踩"被文档误导"。
- **风险**：低。唯一注意：主编档在工作区外，Edit 被权限拦截，需经脚本写入（须先征得同意 + 先备份）。

### P0-3 · LOGO 链路仍整体 no-op

- **为什么优化**：`config.images = {}`（[config.js](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/config.js#L260-L261)）→ `optimizeImageUrl` 的代理缩放能力**从未生效**。后果是双重的：① 原图直出，流量与解码开销高；② 详情页 logo 逐队查询还额外消耗 OpenDota 配额（而 OpenDota 是最紧的配额，`maxPerMin = 50`）。
- **做什么**：填 `proxyBase` 指向一个支持 query 尺寸缩放的图床/代理；对已 build-time 快照的本地 logo 走本地优先；把 logo 获取改成批量（见 P1-3）。
- **优化后会怎么样**：首屏图片流量与解码时间下降；OpenDota 配额释放出来给赛事数据；`image-fallback` 首字母回退的触发率下降（用户观感改善最直接）。
- **风险**：低。新增代理域名须同步加进 `downloadFile 合法域名`。

### P0-4 · 首屏"快照先渲染"策略一致性核查

- **为什么优化**：列表页主链在 [leagues.js](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/pages/leagues/leagues.js#L553-L588)：`api.getLeagues()` + `windowsP` 用 `Promise.all` 汇聚后才 `setData`。v8.4 已加 build-time 快照，但**是否真的在 `onLoad` 同步首帧渲染、还是仍被网络主请求阻塞骨架屏**，需要复核。
- **做什么**：核查 `tryLocalUpcoming` / `leagues-local` 的命中时机是否早于任何网络 await；若否，把快照渲染提到 `onLoad` 最前、网络刷新后置。
- **优化后会怎么样**：**感知首屏**（骨架屏→真实内容）从"等网络"变成"同步出图"，收益最直接、成本最低。
- **风险**：低（快照是既有的，仅调序）。

### P1-1 · 长列表虚拟化

- **为什么优化**：赛事列表、战队比赛历史、选手比赛历史目前是 `wx:for` 全量 `setData`，**没有任何虚拟化**。列表越长，`setData` payload 越大（详情页对阵卡还含 players/logo 数组），低端机直接掉帧。
- **做什么**：优先用微信官方 `recycle-view`（**要求 item 固定高**，本项目卡片高度不齐 → 需改造为等高行或加固定高容器）；Skyline `scroll-view type="list"` 效果更好但须升基础库 + 兼容降级 → 建议先做单页 A/B。
- **优化后会怎么样**：长列表滚动帧率与内存占用改善；`setData` 数据量从"整页"降到"在屏节点"。
- **风险**：中。等高改造会动视觉；Skyline 会改渲染模式，风险中高 → 必须灰度。

### P1-2 · Liquipedia 实时依赖收敛

- **为什么优化**：Liquipedia 是**模块级全局串行 2.2s 限流**（合规要求，不能靠并发突破），最坏 `15 × 2.2s = 33s`。这是"用户等不了"的量级。而 `阶段6` 已经把 LP 缓存**每日通过 GH Actions 灌进 Supabase**。
- **做什么**：把"本地解析优先 + 灌表"从赛程扩到更多 action，让上线路径变成**纯读 Supabase**；实时抓取只留在 CI/sync 脚本侧（那里的等待不占用用户时间）。
- **优化后会怎么样**：最坏 33s 的串行等待从**用户路径上消失**（变成 CI 的批处理时间）；这同时也减少了一次网络抓取的合规暴露面。
- **风险**：中。需保证灌表新鲜度（`阶段6` 已有 Sync LP Cache 每日两次的机制，可复用）。

### P1-3 · 请求合并与配额治理

- **为什么优化**：OpenDota 滑动窗口 `maxPerMin = 50`（对比限流 60）。详情页同时触发 leagueMatches + teamNames 批量 + logo + 英雄表时，窗口满即串行等待 → 首屏被拖长。EF 侧已有 `getLeagueDetailBundle` 聚合模式可复用。
- **做什么**：把详情页的多次请求合并为一次聚合调用（复用 bundle 模式）；logo 查询批量化。
- **优化后会怎么样**：详情页网络往返次数与窗口排队概率下降。
- **风险**：低（模式已验证）。

### P1-4 · setData 治理

- **为什么优化**：需盘出两类点 —— 单次大 payload（含 `players`/logo 数组）与高频 setData（首页每秒自绘倒计时、LIVE 30s 轮询）。
- **做什么**：盘出后改局部路径更新（`list[i].score`）与降频。
- **优化后会怎么样**：渲染层压力下降，低端机受益最明显。
- **风险**：低。

## 3. 数据准确度方向

### 3.1 结构性瓶颈：独立校验源不足（最重要）

- **为什么这是瓶颈**：项目宣称"多源交叉验证"，但 [consensus.js](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/consensus.js#L13-L26) 的权重表是：

  ```
  liquipedia 4 > curation 3 > steam 2 > stratz 1.5 > opendota 1 = community 1
  ```

  **其中 Steam / STRATZ / OpenDota 全部是 Valve 派生数据**。真正独立于 Valve 的只有 **Liquipedia 与人工 curation**。也就是说：在没有 Liquipedia 覆盖的赛事上，"交叉验证"实质是**同源自证** —— 权重差只是给不同包装的同源数据加权，共识置信度会**虚高**。
- **雪上加霜**：**LPDB v3 API 申请被拒**，Liquipedia 一侧退回自写 `wikitext` 解析器，而 Liquipedia 已升级为 Matchlist + LPDB 动态查询 → 旧解析器会返回 0 场。这是当前准确度的**天花板**。
- **做什么**：① 在 consensus 里**诚实标注"同源族"**（Steam/STRATZ/OpenDota 归为一族，不互相计为独立票）；② 把独立源扩容当成长期投入（自建 haglund 实例 / 接入第二个独立 wiki 类源 / 持续补齐 curation 覆盖）；③ 修掉已知 quirk —— `communityTierFromName` 命中时把 grade 记成 `source:'opendota'`，导致社区正则命中的赛事被**重复计权**。
- **优化后会怎么样**：共识置信度**从虚高变为可信**（数字可能变低，但更真）；漏掉独立验证的赛事会被显式标记而不是伪装成"多源一致"。
- **风险**：低（标注类改动）。**但这是唯一能真正抬高准确度上限的事** —— 没有捷径。

### 3.2 队名归一化脆弱

- **为什么**：[names.js](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/names.js#L40-L85) 的 `normTeamName` 是"小写 + 去非 ASCII"，`normTeamNameLoose` 额外剥 `esports/gaming/team/club/dota` 后缀。纯规则剥离应对不了 `Team Liquid` vs `Liquid` vs `Team Liquid™`、中文名、常见缩写。
- **做什么**：把 curation 里已有的 `CURATED_TEAMS` 别名表**从兜底提升为主路径** + 编辑距离兜底。
- **优化后会怎么样**：H2H 匹配率上升、跨源合并失败率下降（直接改善"同一场比赛出现两张卡"）。
- **风险**：中（归一化改宽会引入误合并，需配合去重测试）。

### 3.3 BO 判定复杂度已到临界

- **为什么**：[sources.js](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/sources.js) 的 `buildBoContext / resolveBoType / applyBo / patchNullSeriesId / _orphanPairMerge / groupSeries` 已经历 **S1–S6 信号优先级 + 根因 G/H/I 多轮修复**。复杂度本身成了回归风险源。
- **做什么**：先补**边界用例的回归测试**（2-0 未完赛、弃赛、bo3 被拆两段、BO2 打满），把已有测试沉淀成"改不动"的护栏，再谈简化。
- **优化后会怎么样**：后续任何动 BO 的改动有护栏，不再靠"改完靠人看"。
- **风险**：低（测试先行）。

### 3.4 phase / status 判定散落多处（靠"字节级镜像"维持）

- **为什么**：`haglund.js` / `liquipedia-parse.js`（client + cloud 双份）/ `league-detail.js` 三处必须一致（铁律 G14），curation `status` 硬覆盖守卫又要求 `leagues.js` + `league-detail.js` 两处字节一致。**这种一致性靠纪律而不是靠结构保证**。148 个提交**没有归档**这一事实本身就说明纪律在失效。
- **做什么**：把 phase / status / BO 各自收敛为**单一纯函数模块**（client 与 cloud 共享同一份，cloud 侧由 sync 脚本镜像），配单测。
- **优化后会怎么样**：从"三处改三遍、怕漏"变成"改一处、测试兜底"。**这是给未来的自己减负最大的一项**。
- **风险**：中（动的是热路径，需逐步迁移 + 测试先行）。

### 3.5 收录漏收（已知的结构性缺口）

- **为什么**：收录门槛是 `rank >= 1` + curation 数据；OpenDota `/leagues` 只返回**已开赛**赛事 → **未开赛且未写 curation 的 S/A 级赛事必然漏收**，只能靠 `scripts/ops/curation-coverage.js` 人工补。
- **做什么**：把 coverage 检查纳入 CI 定时（现在 CI 已首次变绿，具备条件），漏收即告警。
- **优化后会怎么样**：漏收从"用户发现"变成"CI 发现"。
- **风险**：低。

## 4. 后端 Supabase 方向评估（本轮重点）

> 直接回答："**现在用的后端 Supabase 方面优化是否方向（正确）？**"

### 4.1 结论先行

**大方向正确，但执行路径有三处需要纠偏。** 简单说：

- ✅ **选 Supabase 是对的** —— 它解决了云开发解决不了的三件事（见 4.2）
- ⚠️ **但"把 GitHub Actions 当生产调度器"是弱选择**（4.3-①②）
- ⚠️ **7 个未迁 action 卡住的原因不是工作量，而是架构分层错了**（4.3-③）

### 4.2 为什么这个方向是对的（四个真实收益）

1. **拿到真正的数据库能力**。云开发数据库是文档型、聚合查询弱；而本项目**大量需要 SQL 聚合**（证据：项目专门有 `utils/sqlFragments.js`、`LEAGUE_WINDOWS_SQL` 按 leagueid 聚合 min/max/last_end/count）。Postgres + PostgREST 让这类聚合回到数据库做，而不是拉到客户端算。**这是本项目选 Supabase 最硬的理由。**

2. **Edge Function 跑 Deno → 可以设置 User-Agent**。Liquipedia 强制要求描述性 UA，而微信小程序 `wx.request` **禁止设置 UA** —— 这是项目历史上所有 Liquipedia 架构决策的根因。EF 与云函数都能设 UA，但 EF 更轻、冷启动更快、与数据面同平台（少一次跨平台跳转）。

3. **摆脱微信云开发锁定**。云开发与微信账号强绑定，不可迁移、不可多端复用。Supabase 是**开源且可自托管**的，符合项目"免费开源"硬约束，且为未来多端（Web/其他小程序）留了门。

4. **调度从"黑盒触发器"变成"可版本化的 CI"**。云开发定时触发器不透明、无法 code review、无历史日志；GH Actions 的 workflow 进 git、有运行历史、可手动 Run、可告警。`阶段6` 记录 CI 在 2026-09-19 10:13 **首次真正变绿**（21s / 8 步），这本身就是治理水平的提升。

### 4.3 需要纠偏的三处

#### ① 调度器选型：GitHub Actions 做生产调度是弱 SLA 选择

- **问题**：定时任务全部押在**个人 GitHub 仓库**（`re-toke/dota2-esports`）上。GH Actions 的 cron **不保证准点**（高峰期会延迟甚至跳过）、private repo 有额度限制、仓库一旦改名/转移/权限变更或账号异常，**整个调度静默死亡**。国内网络访问 GitHub 本身也不稳定。
- **证据**：`阶段6` 记录 9/17 "Sync Liquipedia Cache 有 1 次失败（次日自愈）"、"发现 CI 从未变绿（3 个阻塞点）" —— 说明这条链路确实在抖。
- **建议**：评估 **Supabase 自带的 `pg_cron` + `pg_net`**（同一平台内的原生定时方案，免跨平台、免 GitHub 依赖）替代部分 GH Actions 职责；GH Actions 保留给"需要跑 Node 脚本 + 提交产物"的批处理。**（须先核实免费版是否开放 `pg_cron`）**
- **另外必须加**：**调度心跳看门狗** —— 如果超过 N 小时没有任何 workflow 成功记录就告警。目前 `EF Health Check` 只检 EF 健康、不检调度本身。

#### ② 单点依赖：没有明确"谁在兜底调度"

- **问题**：云开发触发器**已停**（9/15 17:14），职责移交 GH Actions，但**没有留存第二调度器**。这是单点。
- **建议**：至少保留一个**低频**的云开发触发器作为"兜底心跳"（成本极低），或者接受单点但补上 ① 的看门狗。`阶段6` 里 `schedulePreheat` 被标注为"**唯一无替代品**"却仍先停 —— 这个决定值得回看。

#### ③ 7 个未迁 action：根因是分层错误，不是工作量

- **问题**：`收尾清单` 写明未迁原因是"**契约不兼容（EF 是薄代理，云函数侧含解析/聚合逻辑）**"。这意味着 **Liquipedia 的 wikitext 解析逻辑被放在了云函数侧**，而不是可复用的纯函数里。所以每迁一个 action 就要"重写契约"，迁不动。
- **证据**：项目**已经有了正确做法的样板** —— `utils/liquipedia-parse.js` 是纯函数且做到 **client/cloud 双源字节一致（G14 闸门）**。既然客户端和云函数都能共享同一份纯函数，**Deno EF 同样能**。
- **建议**：不要把"再迁 7 个"当成任务；**把 `liquipedia-parse` 抽成 EF 可 import 的共享模块（`.ts`）**，则 `liquipediaScheduledMatches`（文档标注"收益最大"）、`liquipediaLeagueMeta`、`liquipediaListTournaments` 等会**自然变得可迁**。这是同一个动作同时解决"迁移收尾"和"Liquipedia 收敛"两件事。
- **注意**：G14 闸门是"双源字节一致" —— 引入 EF 侧第三份副本会**扩大该闸门的作用域**，必须同步扩测试，否则会制造新的漂移源。

#### ④ 合规与延迟残留（我上一轮担忧的准确版本）

- **合规**：项目已把 `https://gkticzdaicpdtxheyxsd.supabase.co` 加入 request 合法域名（`收尾清单` ✅）。**但**：微信官方文档明确"**域名必须经过 ICP 备案**"，而 `*.supabase.co` 的备案主体是 Supabase 而非开发者 → 这是一个**存在但不一定被执行**的规则。目前能加进去，不代表未来审核不追溯。
- **延迟**：EF 实测 `getLeagues 1.1s / getHeroes 1.3s / getProMatches 1.4s / getLiveMatches 2.9s`（**Node 环境**）。对比云函数走微信内网通道，海外 EF **大概率更慢**。而 `阶段6` 自己声明"**不能完全替代真机**"。
- **建议**：① 做一次**真机 A/B**（同一 action：EF vs 云函数 TTFB），用数字决定哪些链路值得放 EF、哪些该留云函数；② 真机勾掉 `阶段6 §①` 那个"⬜ 待用户"的确认项；③ 若延迟差距显著，考虑 **EF 前置一层国内可达的代理**（但这会削弱"解耦"收益，需权衡）。

### 4.4 方向正确性判定

| 判断维度 | 结论 |
|---|---|
| 技术选型（Supabase vs 云开发） | ✅ **正确**。Postgres 聚合能力 + Deno 可设 UA + 开源可自托管，三条都是真需求 |
| 迁移方式（数据面走 EF） | ✅ **正确**。18 个 action 已迁、观察期绿 |
| 调度方式（GH Actions 替代云开发触发器） | ⚠️ **方向可接受，选型偏弱**。建议评估 `pg_cron` + 补心跳看门狗 |
| 迁移收尾（7 个未迁） | ⚠️ **方式错误**。应"解析逻辑下沉共享模块"而非"逐个重写契约" |
| 云开发退役策略 | ⚠️ **未定义**。双链路并存 + 触发器已停 + 无兜底调度 = 当前最大架构风险 |
| 合规 | 🟡 **已缓解但有残留**（备案 + 真机确认 + 延迟未量化） |

**一句话**：**方向对，但现在是"半程状态最危险"的时刻** —— 旧的拆了一半、新的还没立稳，且这个状态已经持续 11 天（9/15 → 9/26）而没有收口。
