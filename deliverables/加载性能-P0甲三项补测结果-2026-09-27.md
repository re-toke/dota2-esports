## ① 首页（关注 15 队）

### 实测时间线（两次运行）
| 运行 | 管线调用 | followCards 终值 | 关键时间点 |
|---|---|---|---|
| A | **4 次**（rows 0 → 0 → 5 → 10），每次 **6/18/7/10ms** | **10 / 15** | 首次非空 +178ms |
| B（固定等 40s，不提前退出） | —（插桩已还原） | **6 / 15** | +427ms → 5 张；**+18115ms → 6 张**；之后 23s 无变化 |

⇒ 两次终值不同（10 / 6）⇒ **结果不稳定**（网络/失败的非确定性）。

### 代码核对（为什么不是"加载慢"）
- `loadFollowCards()`：`FOLLOW_CAP = 15`，**首批 5 个并发 `getTeamMatches`**，其余**每批 5 个串行**；
  每批完成都调 `_kickMatchFlow()` → `_applyMatchSources()`（实测 4 次，每次 **6~18ms**）。
- `_renderFollowCards()` → `buildFollowCard()`：**`if (!list.length) return null;`**
  ⇒ **卡片数 = "有比赛数据的战队数"**，6/15 属**按设计过滤**（我注入的 15 队里部分已不活跃）。
- ★ **但这里有一个真实缺陷**：
  ```js
  api.getTeamMatches(String(t.id)).then((ms) => ({ t: t, ms: ms || [] }))
    .catch(() => ({ t: t, ms: [] }))     // ← 请求失败 → 空数组 → 该战队**静默消失**
  ```
  ⇒ **"取数失败"与"确实没有比赛"被合并**：失败的战队**没有卡片、没有提示**，
  且 `followLoading=false` **掩盖了它**（用户只看到"关注了却少几张"）。
  ★ 这与项目一贯警惕的**静默失败**是同一类问题。

### ⇒ ① 的结论
- **CPU 不是问题**（管线 6~18ms × 4 次 ≈ 40ms）
- **"慢/不全"的机制 = 网络分批串行（首批 5 并发，其余每批 5 串行 ⇒ 晚批次到 +18s 甚至不到）+ 失败静默丢弃**
- 优化方向：**① 区分"失败/无比赛"；② 分批策略与并发度；③ 失败可见化**

## ③ 751 条的真实分布

```
status = { ended: 747, upcoming: 3, ongoing: 1 }        （合计 751）
grade  = { S: 306, A: 166, B: 279 }
gradeCounts.all = 747   ← updateGradeCounts 排除 defunct ⇒ 751 → 747
```

⇒ **751 条里只有 4 条非 ended** ⇒ 「进行中」tab **1 条**、「即将到来」**3 条**。

★ 含义：用户感到"加载不全 / 没内容"，**可能与"真实数据里几乎没有进行中的赛事"有关**，
而不是加载缺陷。（当前是 9/27，赛程淡季。）

## 诚实边界

- 两次首页运行终值不同（10 / 6）⇒ **有非确定性**，故"到底差几张"**不可复现**；
  但"分批到达 + 失败静默丢弃"的**机制已由代码确认**（不是推断）。
- 运行 B 未打插桩（已还原）⇒ **管线调用次数为 0 属预期**，该次只测「卡片是否到齐」。
- 模拟器数据；**未测真机网络**（真机 RTT 更长 ⇒ 分批问题只会更明显）。
- **未测失败率本身**（需在 `fetchBatch` 加统计）—— 这是下一步。
- 注入的 15 队取自 `CURATED_TEAMS`（含已不活跃队伍）⇒ 6/15 的**比例**不代表真实用户；
  但**机制问题与比例无关**。
