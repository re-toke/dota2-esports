# 隐私指引驳回整改方案 + 微信登录问题澄清（2026-09-10）

> 驳回反馈：① 设备信息接口说明内容不符合接口使用场景 ② 读取你的剪切板接口说明内容不符合接口使用场景
> 真机问题：微信账号无法登录，点击直接设置昵称

---

## 一、先定性：驳回的是「**用途描述**」，不是「不该声明」

微信的驳回话术 `XX接口说明内容不符合接口使用场景` 在社区里是**高频驳回原因**，
官方运营/审核的回应口径一致（摘录）：

> 「**驳回的通知里已说明是哪个隐私接口描述不明确！建议重新描述下与隐私接口相关的具体用途**」
> 「**建议把多余的描述删除**」
> 「要**从 API 的本身用途出发，不要说通过这个 API 实现的结果**」
> 「**简单点就行，不用太复杂**」

官方《微信开发者合规开发指引》给的错误案例：

| 错误类型 | 例子 |
|---|---|
| 填写不明确 | 调用麦克风接口为了「获取你的麦克风权限」← 同义反复 |
| **结果导向** | 写「通过这个 API 能实现什么」而非「API 本身的用途」 |
| 过度重复 | 所有接口描述都一样 |
| 语句不通顺 | 与表单前后缀拼起来读不通 |

**结论**：两项都**保留声明**，但必须重写用途描述。**唯一的例外见第三节（设备信息可能是多余的）**。

## 二、剪切板：必须保留，用途改具体

### 为什么必须保留

WeChat 后台表单是「开发者**读取**你的剪切板，用途是 ____」。
虽然我们只用 `wx.setClipboardData`（写入），但**官方隐私接口映射表把 `wx.setClipboardData`
明确列入「读取你的剪切板」**，且社区有大量真机报错实证：

```
"errMsg": "setClipboardData:fail api scope is not declared in the privacy agreement", "errno": 112
```

→ **取消勾选会让「复制链接」在正式版直接失败**（开发态工具会预勾，看不出来）。

### ❌ 之前的问题（我给的文案）

> 「用于将赛事/对局链接复制到剪贴板，**方便您转发分享给好友**」

两个毛病：
1. 「方便转发分享」是**结果**，不是接口用途
2. 提及「分享」可能额外触发审核关注（诱导分享是审核红线之一）

### ✅ 改成

```
复制赛事或对局链接
```

（表单拼出来读作：「开发者读取你的剪切板，用途是**复制赛事或对局链接**」）

这正是官方自己的示例句式 —— 官方模板里就是「开发者读取你的剪切板，用途是：**复制报错信息**」。
社区运营也建议：「剪切板是为了**复制 xxx 内容**」「简单点就行」。

## 三、设备信息：建议**取消勾选**（这是本次的关键判断）

### 为什么

1. **官方隐私接口映射表里没有「设备信息」这一项对应的任何 API**
   （对照 miniprogram-intro 的完整映射，只有昵称头像/位置/地址/发票/运动/手机号/车牌/
   照片视频/文件/麦克风/摄像头/蓝牙/相册/通讯录/日历/四类传感器/剪切板）
2. 我们实际调用的 `wx.getDeviceInfo` / `wx.getAppBaseInfo` / `wx.getWindowInfo`
   是**官方推荐的「不触发授权」新接口**（旧 `wx.getSystemInfo` 才是「会获取系统权限」的那个）
3. 我们的用途是**纯客户端渲染适配 + 判断是否开发者工具**，**没有任何信息离开设备**
   → 不构成「处理用户个人信息」的场景，声明它属于**过度声明**

> ⚠️ **我此前建议「设备信息建议勾上」是错的** —— 当时的理由是「漏勾代价 > 多勾代价」，
> 但没考虑到「无对应隐私 API 的声明反而会触发审核问询」。本次驳回证实了这一点。

### 已同步做的代码整改（本仓库）

为让「不声明设备信息」站得住脚，已把代码里**废弃的 `wx.getSystemInfoSync` 引用清零**：

| 文件 | 改动 |
|---|---|
| `utils/monitor.js` | `inDevtools()` 移除 `getSystemInfoSync` 兜底，只用 `getDeviceInfo`/`getAppBaseInfo` |
| `pages/leagues/leagues.js` | 屏幕高度改用 `wx.getWindowInfo()`，取不到用 667 保守值 |

两处都已确认无功能影响（取不到时走保守分支）。

### 如果后台把「设备信息」标为**必填**、无法取消

说明微信按接口调用自动检测到了。此时按顺序尝试：

**选项 A**：用途写**真实且具体**的场景（不要写「分析系统稳定性」这类不实描述）
```
识别运行环境与屏幕尺寸，用于适配界面显示
```

**选项 B（更彻底）**：**移除相关代码**，让它不再被自动检测到：
- `utils/monitor.js` 的 `inDevtools()` → 直接去掉该判断（或改用不读设备信息的替代方案）
- `pages/leagues/leagues.js` 的 `_winH` → 改用固定阈值或 CSS 方案
- `components/chart/chart.js` 的 `pixelRatio` → 固定 2，或从 `wx.getWindowInfo` 换掉

> 我已完成废弃接口清理（为 A/B 铺路）。**若选项 A 再被驳回，直接说，我做选项 B。**

## 四、真机「无法登录」——定位到具体症状了

### 症状来源：订阅入口的登录 gate

`pages/follow/follow.js` 的 `onSubscribe()`（点「赛前通知」触发）：

```js
if (!auth.isLoggedIn()) {
  wx.showToast({ title: '正在登录…请稍后重试', icon: 'none' });
  auth.ensureLogin().catch(() => {});
  return;                      // ← 直接返回，不等登录结果
}
```

**问题**：登录失败时**静默回到同一状态**。用户反复点击只会看到同一句
「正在登录…请稍后重试」，**无法区分「首次预热（再点一次就好）」与「登录链路真的挂了」**。

→ 你看到的「微信账号无法登录」，很可能就是这一句 toast 反复出现。

### ✅ 已改（本仓库）

1. **补登录日志**（`utils/auth.js`）—— 此前 `ensureOpenId` **全程静默**，真机失败无从诊断。
   现在会打印：
   ```
   [auth] wx.login OK，调 Edge Function wechat-auth…
   [auth] openid OK via=supabase+jwt (312ms) oid=a1b2c3d4…
   ```
   失败路径也会明确打印（`wx.login 失败` / `wechat-auth EF 失败` / `云开发 getOpenId 失败`）。
2. **补失败可见**（`follow.js`）—— 登录返回 null 时提示「登录失败，请检查网络后重试」，
   不再让用户困在无信息的循环里。

### 真机复测时看 Console 这几行就能定位

| Console 输出 | 含义 | 处置 |
|---|---|---|
| `openid OK via=supabase+jwt` | ✅ 正常 | 无需处理 |
| `openid OK via=cloud` | ⚠️ EF 挂了但云开发兜住了 | 查 Supabase 域名白名单是否生效 |
| `wechat-auth EF 失败，回退云开发` + `云开发 getOpenId OK` | ⚠️ 同上 | 同上 |
| `openid NULL`（两条路径都失败） | ❌ 真·登录失败 | 查云函数 `aggregation` 是否部署 + 网络 |

> 最可能的单点原因：`https://gkticzdaicpdtxheyxsd.supabase.co` 未加入后台 request 合法域名。
> 但**即使它没生效，云开发兜底也能拿到 openid** —— 所以若两条都失败，重点查云函数部署状态。

## 五、关于「点击直接设置昵称」——这是**设计如此**，且是微信现行规范

### 现状（代码证据）

`pages/follow/follow.js:44` 注释写得很明确：

> 「用户卡身份升级为 chooseAvatar + 昵称 input，**仅存本地 storage（无服务端账号体系）**。
> **openid 登录保留（订阅前置），不再驱动用户卡 UI**。」

| 能力 | 现状 |
|---|---|
| 用户卡（头像/昵称） | 纯本地 storage，**不参与账号体系** |
| openid 静默登录 | `app.js` onLaunch 调用 `ensureLogin()`，**无 UI、无按钮** |
| openid 用途 | 仅作「赛前通知」订阅推送的前置（`follow-profile` / `smart-reminders`） |

### ⚠️ 更关键的认知：微信**已经不允许**小程序自动获取昵称头像

自 2022 年起微信**回收了 `wx.getUserInfo` / `wx.getUserProfile`**，第三方小程序
**无法再静默拿到微信昵称/头像**。官方指定的唯一替代方案就是：

```html
<button open-type="chooseAvatar">   <!-- 用户主动选头像 -->
<input type="nickname">             <!-- 微信一键填充昵称 -->
```

**这两样正是你「点击设置昵称」看到的东西** —— 它是**微信现行规范下唯一合规的
「获取用户头像昵称」方式**，不是我们做错了。

所以现在小程序里**不存在可见的「微信登录态」**：拿不到昵称头像，openid 又完全静默。
硬做一个「登录按钮」，用户点了也只能得到一个 openid，没有可展示的信息。

### 如果你要的是「有账号感 / 能看出已同步」

建议做**状态提示**而不是「登录按钮」，例如用户卡下方显示：

> 「已同步 · 换机后关注与提醒可恢复」 / 「未同步 · 换机后需重新设置」

判断依据：`auth.isLoggedIn()`。改动小、符合微信规范，但**依赖隐私指引先通过**
（未授权时 `<input type="nickname">` 会降级为普通文本框）。
