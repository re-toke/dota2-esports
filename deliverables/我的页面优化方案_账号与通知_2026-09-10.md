# 「我的」页面优化方案（账号 + 关注通知）

> 日期：2026-09-10 ｜ 页面：`pages/follow/follow.*` ｜ 状态：**待评审**
> 范围：本页**账号相关**与**关注通知相关**功能的优化；不含关注列表卡片本身的视觉改造

---

## 一、现状梳理

### 页面结构（自上而下）

```
① 身份卡（user-card）
   ├─ 头像（<button open-type="chooseAvatar">） + 昵称（<input type="nickname">）
   │  └─ 副文案：「资料仅保存在本机」
   ├─ 云同步开关（v8.41 新增，四态）
   └─ 统计行：关注战队 N | 关注赛事 N | 赛事提醒[已开启/未开启] ← 点击滚动到段三

② 关注阵容
   ├─ 分段控件（战队 / 赛事）
   └─ 列表（卡片 + 删除）+ 空态 / 加载更多

③ 赛前提醒
   ├─ 模板未配置 → 降级行（点击跳**隐私页**）
   └─ 正常态：卡头（标题 + 订阅徽章 + 开启/关闭 pill）
        └─ 已订阅才展开：今日推送 X/Y · 提前量 chips · 提醒级别 chips · 提示语 · 重新授权

④ 推送记录（折叠，默认收起）

⑤ 系统配置：隐私与协议 / 清除本地缓存 / 关于我们(v1.1.0) / 图标素材署名
```

### 关键数据源

| 字段 | 来源 | 说明 |
|---|---|---|
| `profile` | 本地 storage | 头像/昵称，**纯本机** |
| `sync` | `cloudSync.getState()` | 四态：off/syncing/synced/failed |
| `subStatus` | `subscribe.getSubStatus()` | `{ subscribed, time }` |
| `subReady` | `!!subscribe.TMPL_ID` | 模板是否配置 |
| `sendHistory` / `todayCount` / `dailyLimit` | `subscribe.*` | 推送记录与配额 |

## 二、问题诊断

### A. 账号类

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **A1** | ★★ **文案与事实矛盾（合规风险）** | `follow.wxml:15` 固定写「资料仅保存在本机」；`:181/:182` tip 写「**关注数据仅保存在本机**」——**都没随云同步开关变化** | 开启同步后关注数据**已在云端**，页面却仍宣称「仅保存在本机」→ **不实告知**。隐私指引刚因描述问题被驳回过，此处同类风险 |
| **A2** | ★★ **「清除本地缓存」会造出云端数据孤儿** | `clearCache()` 用 `wx.clearStorageSync()`，**连 `dota2_cloud_sync` 开关状态一起清掉**，但**完全不动云端** | 用户清缓存后：开关显示「未开启」+ 本地无 JWT，而**云端画像仍在**；且弹窗只说「清除关注列表、缓存数据与登录态」，**未提云端** → 用户以为清干净了，实际云端仍存；也**无法再用开关删除它**（开关已显示关闭） |
| **A3** | 头像/昵称无重置入口 | `follow.wxml:7-14` 只有「选头像」「填昵称」 | 选错只能再选一次；昵称要清空得手动删字符，无「恢复默认」 |
| **A4** | 隐私授权状态不可见 | 无相关 UI；官方明确：隐私未授权时 `input type="nickname"` **降级为普通文本框** | 用户点击昵称发现「填不出微信昵称」，不知是权限还是 bug → 困惑 |
| **A5** | 信息架构混层 | 身份卡内同时装：**本机资料**（头像/昵称）+ **账号能力**（云同步）+ **数据统计**（关注数/提醒态） | 三类语义挤一张卡，用户无法区分「哪些是本机、哪些上云」 |
| **A6** | 开关缺「同步了什么」的说明 | `follow.wxml:27` 副文案只说「换设备也能恢复关注与提醒」 | 用户对「上云」有顾虑却看不到具体范围（关注战队 / 提醒策略 / 订阅授权状态），不利于转化 |

### B. 关注通知类

| # | 问题 | 证据 | 影响 |
|---|---|---|---|
| **B1** | **核心功能位置靠后** | 「赛前提醒」在**关注列表之后**（段三）；列表长时要滚很久 | 提醒是本页第二核心功能，却被长列表压在下面 |
| **B2** | **未订阅时看不到价值** | `follow.wxml:121` `<block wx:if="{{subStatus.subscribed}}">` 才展开提前量/级别 | 未开启的用户看不到「能设提前多久 / 只看哪些级别」→ 缺少开启动力 |
| **B3** | 「重新授权 ›」文案含糊 | `follow.wxml:150` | 用户不知「重新授权什么、为什么需要」 |
| **B4** | 推送记录无失败原因、无重试 | `:170-172` 只有「成功/失败」 | 失败后用户无从处置（是网络？模板？授权？） |
| **B5** | ★ 配额重置时间**不是 0 点** | `subscribe.getTodayCount()` 用 `new Date().toISOString().slice(0,10)` 按 **UTC 日**过滤 | 对北京用户实际是**次日 08:00 重置**，与直觉（0 点）不符；文案写「每日 0 点重置」会是错的 |
| **B6** | **降级态跳隐私页（语义错位）** | `:158` `bindtap="openPrivacy"` | 「模板未配置」属**开发者侧配置问题**，跳隐私页解决不了任何事 → 用户困惑 |
| ~~B7~~ | ~~关闭提醒后云端 subs 残留~~ | **★ 核查后修正：此判断有误** | `unsubscribe()` 内**有** `syncSubStatus()` 清理（`subscribe.js:80`）；残留风险仅为代码已注明的 fire-and-forget 竞态窗口（可接受） |
| **B9** | ★★ **关闭云同步后「赛前提醒」仍显示「已开启」→ 静默失效** | `onSyncToggle → disable()` **不会同步关闭提醒**；而服务端推送依赖云端 profile | 用户：开启提醒 → 后来关闭同步 → 卡片仍显示「已开启」，但**推送已死**且无任何提示 → 最容易被投诉成「提醒没用了」 |
| **B8** | 无提醒可用性自检 | 无 | 用户无法确认「我这条链路到底通不通」 |

### C. 信息架构类

| # | 问题 | 说明 |
|---|---|---|
| **C1** | 页面过长且优先级倒置 | 身份 → **关注阵容** → 赛前提醒 → 推送记录 → 系统配置。**关注阵容是浏览型内容，却夹在两个配置型模块之间** |
| **C2** | 「赛事提醒」两套入口 | 统计行第三格 `scrollToReminder` + 段三的开关，功能重复 |
| **C3** | 「系统配置」混装无关项 | 隐私 / 清缓存 / 关于 / 图标素材署名 同类平铺，无分组 |

## 三、优化目标与原则

1. **诚实**：凡涉及「数据在哪」的文案，必须**随云同步状态动态变化**（A1、A2 是合规底线）
2. **可理解**：账号能力用用户语言表达（「云同步」而非「登录」），并说明**同步了什么**
3. **可恢复**：任何破坏性操作都要有明确后果说明与撤回/补救路径（A2、A3）
4. **核心前置**：关注通知作为核心功能，缩短触达路径（B1）
5. **降级友好**：不可用状态要给出**正确指引**，而不是跳到无关页面（B6）

## 四、优化方案

### 4.1 账号区重构（对应 A1–A6）

**改动一：身份卡拆分为两张卡**

```
┌─ 我的资料（本机） ────────────────┐
│  [头像]  昵称输入框        [重置] │   ← 新增「重置」入口
│         仅保存在本机，不上传       │
└──────────────────────────────────┘
┌─ 云同步 ─────────────────────────┐
│  换设备也能恢复你的关注与提醒  [⚪]│
│  ┌ 同步内容（点「详情」展开）      │
│  │ · 关注的战队                    │
│  │ · 提醒策略（提前量/级别）        │
│  │ · 订阅授权状态                  │
│  └ 不含：头像、昵称（仅存本机）     │
│  最近同步：3 分钟前      [详情 ›]  │
└──────────────────────────────────┘
```

**要点**：
- **物理分组**本机资料 vs 云同步 → 直接解决 A5（用户一眼看出边界）
- 「同步内容」明细 → 解决 A6；**明确写出「不含头像昵称」**，这是最容易被误解的点
- 「重置」入口 → 解决 A3（清空头像回默认图 + 清空昵称）
- 副文案「仅保存在本机，不上传」→ 替代原「资料仅保存在本机」，范围更明确

**改动二：文案随状态动态化（A1，合规必需）**

| 位置 | 现状（固定） | 改为 |
|---|---|---|
| 身份卡副文案 | `资料仅保存在本机` | 固定「仅保存在本机，不上传」（因为**确实**不上传，表述为范围限定） |
| 段三 tip | `关注数据仅保存在本机` | 按状态：未开启 → 「关注数据仅保存在本机」；**已开启 → 「关注数据已同步至云端，可在上方关闭并删除」** |

**改动三：隐私授权状态提示（A4）**

检测 `wx.getPrivacySetting` → 若 `needAuthorization` 为真，在昵称输入框下方提示：
> 「需先同意隐私协议才能使用微信昵称一键填充 →  查看协议」

### 4.2 清除缓存语义修正（A2）—— 建议优先做

**问题本质**：`wx.clearStorageSync()` 会连同步开关一起清，导致云端孤儿 + 用户误以为清干净了。

**方案**：改为**两项独立操作**，并明确各自范围

```
┌─ 数据管理 ────────────────────────┐
│  清除本地缓存                      │
│  仅清除本机缓存与搜索历史，不影响云端 ›│
│  ─────────────────────────────────│
│  删除云端数据（关闭云同步）          │
│  删除云端保存的关注与提醒             │
│  ─────────────────────────────────│
│  重置全部（本机 + 云端）             │
│  清除本机数据并删除云端数据           ›│
└──────────────────────────────────┘
```

实现要点：
1. 清本地时**保留 `dota2_cloud_sync` 开关状态**（按 key 删除，而非 `clearStorageSync`）
2. 若同步处于开启态，「清除本地缓存」需提示「云端数据保留，下次进入会自动恢复」→ **反而成为同步的卖点展示**
3. 「重置全部」= 先 `cloudSync.disable()`（删云端）再清本地

### 4.3 关注通知区重构（对应 B1–B8）

**改动四：位置前移 + 未订阅也展示价值（B1、B2）**

将「赛前提醒」从段三**上移到身份卡之后、关注阵容之前**：

```
① 我的资料 / 云同步
② 赛前提醒          ← 上移
③ 关注阵容          ← 下移
④ 推送记录（并入②）
⑤ 系统配置
```

并把提前量/级别 chips **改为常显**（未订阅时置灰不可点），让用户看到「能怎么配」：

```
┌─ 赛前提醒 ──────────────────  [未开启] ┐
│  开启后，关注的战队开赛前会收到微信提醒   │
│  提前量   [15分] [30分] [1小时] [2小时]  │  ← 置灰不可点
│  提醒级别 [S] [A] [B]                    │  ← 置灰不可点
│  [ 开启提醒 ]                            │
└──────────────────────────────────────────┘
```

**改动五：文案与状态修正（B3、B5、B6）**

| # | 现状 | 改为 |
|---|---|---|
| B3 | `重新授权 ›` | `重新授权微信提醒 ›`（并加一行说明为什么可能失败：授权有有效期/被系统屏蔽） |
| B5 | `今日推送：X / Y 条` | `今日已推送 X / Y 条（每日 0 点重置）` |
| B6 | 降级态跳隐私页 | 改为**不跳转**的说明行：「赛事提醒功能暂未开放」+ 移出系统配置区（属开发者侧状态，不该占据用户视野） |

**改动六：推送记录可处置（B4）**

失败项增加可展开的原因与建议（如「用户未授权 → 点击重新授权」/「网络异常 → 稍后自动重试」）。

**改动七：消除「提醒开 / 同步关」的静默失效（B9）—— ★ 优先级等同 P0**

**问题本质**：v8.41 把「云同步」做成开关后，产生了一个**新的耦合缺口** ——
赛前提醒**依赖云端推送**，但两个开关可以处于矛盾状态：

| 同步 | 提醒 | 实际结果 | 界面显示 |
|---|---|---|---|
| 开 | 开 | ✅ 正常推送 | 正常 |
| 关 | **开** | ❌ **推送已死** | ⚠️ 仍显示「已开启」← **静默失效** |
| 关 | 关 | 一致 | 正常 |

**方案（双保险）**：

1. **关闭同步时联动询问**（主路径）
   ```
   关闭云同步？
   赛事提醒依赖云端推送，关闭后提醒将同时停止。
   [ 关闭同步与提醒 ]  [ 仅关闭同步 ]  [ 取消 ]
   ```
   选「仅关闭同步」→ 提醒也标记为不可用，并在提醒卡上显示警示：
   > ⚠️ 云同步已关闭，赛事提醒暂时无法推送　[重新开启同步]

2. **提醒卡增加前置检查**（兜底）
   `subStatus.subscribed === true && !cloudSync.isEnabled()` → 卡片显示「⚠️ 需开启云同步」而非「已开启」

> 这条是本轮**最该修**的一项 —— 它直接造成「用户以为开着提醒却收不到推送」的投诉场景。

**改动八：配额重置说明修正（B5）**

现状按 **UTC 日**重置（北京用户实际 08:00 重置）。两个选择：
- **改文案**（低风险）：「每日按 UTC 0 点重置」—— 但用户不关心 UTC
- **改逻辑**（推荐）：改用 `config.time.bjOffsetSec`（项目已有北京时间单一来源）按**北京时间 0 点**重置，同时文案写「每日 0 点重置」

**改动九：订阅链路自检（B8）**

新增**「发送测试提醒」**入口（服务端一次自检，返回链路各环节状态）：
```
测试结果：登录 ✓ → 同步 ✓ → 模板 ✓ → 授权 ✓
```
对排查「为什么收不到推送」极有价值（本页最高频的困惑）。

### 4.4 信息架构整理（C1–C3）

- **C1/C2**：位置调整见改动四；统计行第三格「赛事提醒」保留为**状态徽章 + 快捷跳转**（与段二开关不重复，一个跳转一个操作）
- **C3**：「系统配置」分组：
  ```
  数据管理（清缓存 / 删云端 / 重置全部）  ← 见 4.2
  关于（隐私与协议 / 关于我们 / 图标素材署名）
  ```

## 六、验收标准

- ☐ 开启云同步后，页面**任何位置**都不再出现「关注数据仅保存在本机」
- ☐ 关闭云同步后，出现「已同步至云端，可关闭并删除」类提示
- ☐ 点「清除本地缓存」后，**云同步开关状态保留**；云端数据未被删除，且界面明确告知
- ☐ 「重置全部」后，云端与本地均清空（可用 openid 查 Supabase 验证）
- ☐ **关闭云同步时，若提醒处于开启态，必须出现联动提示；选择仅关同步后，提醒卡显示「需开启云同步」而非「已开启」**（B9）
- ☐ 未订阅状态下能看到提前量与级别选项（置灰）
- ☐ 模板未配置时，点击降级行**不发生跳转**，且文案说明是功能未开放
- ☐ 隐私未授权时，昵称输入框下方出现可点击的提示
- ☐ 配额按**北京时间 0 点**重置（跨 0 点实测）

## 七、待确认（需你拍板）

| # | 决策点 | 我的建议 |
|---|---|---|
| 1 | 赛前提醒是否**上移到关注阵容之前** | **上移** —— 它是配置项，与账号区同属「设置」，放浏览内容前更符合心智；但若你认为「关注阵容」是页面主角，可保持原位只加锚点 |
| 2 | B9 关闭同步时的联动方案：**三选一弹窗**（关同步+提醒 / 仅关同步 / 取消）vs **二选一**（同时关 / 取消） | **三选一** —— 尊重用户只想关同步的意愿，但必须让「提醒会失效」可见 |
| 3 | 「清除本地缓存」是否保留「重置全部」这一更重的入口 | **保留** —— 否则同步开启的用户没有一次性清空的手段 |
| 4 | B5 是改文案还是改逻辑 | **改逻辑**（按北京时间 0 点）—— 项目已有 `config.time.bjOffsetSec` 单一来源，改文案会引入「UTC」这种用户不可理解的表述 |
| 5 | B8「发送测试提醒」是否本轮做 | **P2 再说** —— 价值高但要动服务端（subscribe-send），本轮先做前端闭环 |
| 6 | 本轮范围 | 建议 **P0 + P1**（P0 是合规底线 + 静默失效，P1 是优化主体） |
