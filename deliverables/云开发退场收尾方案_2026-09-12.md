## ① EF 监控 / 告警 ✅ 已完成

| 产物 | 说明 |
|---|---|
| `scripts/ops/probe-ef.js` | 探测 7 个关键 EF，输出可用性与延迟；**失败退出码 1** |
| `.github/workflows/ef-health.yml` | 每 2 小时（+ 手动）跑一次 |

**告警通道 = GitHub 失败通知邮件**（零成本，不接第三方）。job 失败即代表有 EF 故障。

**探测口径（避免噪音，已实测调优）**：

```
「活着」= 有任何 HTTP 响应（含 400/401 —— 只证明函数被调度起来了）
「故障」= 超时 / 网络错 / 5xx        → 退出码 1，触发告警
「慢」  = 超 8s                     → 仅打 🐢 标记，不告警
```

**★ 调优过程中修掉 3 个探针自身的误报**（先测的价值）：

| 误报 | 原因 |
|---|---|
| liquipedia-proxy 超时 32s | 探针漏传 `cacheOnly` → EF 真去抓 LP（429 重试）→ 还平白骚扰 LP |
| bundle-aggregator 502 | 用了不存在的 leagueId=1（502 是设计内响应）→ 改用真实 id 19944 |
| opendota-proxy 超时 | 冷启动 + `/leagues` 大响应 → 单独放宽超时到 30s，且慢不算故障 |

**实测结果：7/7 健康**（opendota-proxy 8s 标记为 🐢，属冷启动正常范围）。

## ② getCuration 迁表

**现状**：`utils/remoteCuration.js` → 云函数 action `getCuration` → 读云开发 collection。

**目标表已存在**：`curation_events(league_id, data)` / `curation_teams` / `curation_meta`，
且 RLS 已允许 anon 读（001-init.sql 的 `anon_read_events` 等）。

**改法**：`remoteCuration.js` 改为「PostgREST 直读优先 → 云函数回落」，与通用 KV 完全同构
（已有 `_sbKvGet` 的写法可参考）。

**⚠️ 前置验证（必做，别重蹈 KV 那次覆辙）**：
1. **表里到底有没有数据？** 001-init 只做过一次性迁移；此后 `adminWriteCuration` 是否持续写入？
   → 若表是空的/过期的，迁了反而读到旧数据。
2. **写入方在哪？** 若写入仍在云开发，而读取迁到 Supabase → **两边分叉**，
   必须先决定：写入也迁（云函数写 Supabase）或保留云开发写入 + 定期同步。

**难度**：低（读逻辑同构）｜**风险**：中（取决于上面前置项的答案）

## ④ getUpcomingSchedule 预聚合（最复杂，放最后）

**现状**：`pages/leagues/leagues.js` 调云函数 `getUpcomingSchedule`，由**服务端聚合**多个
curation 赛事的「即将开始」对阵后一次性返回。

**为什么不能简单照搬前几次的做法**：它不是「读一个缓存 key」，而是**服务端聚合计算**
（要跨赛事拉 OD/Steam/LP 数据再合并）。

**候选方案**：

| 方案 | 做法 | 评价 |
|---|---|---|
| **A. GH Actions 预聚合写表** | 在同步脚本里聚合 → 写 `upcoming:aggregate`（TTL 6h）→ 客户端直读 | ★ 推荐：与 LP / 通用 KV / 队标同一套路，已验证三次；且 GH 出口不受限 |
| B. 客户端循环调 EF | 客户端对 N 个赛事各调一次 EF 再合并 | ❌ N 次往返，首页变慢；且要重写聚合逻辑 |
| C. 保留云函数 | 不动 | ❌ 与「退场」目标冲突 |

**A 的实施要点**：
- 复用现有的 `buildLpUpcomingSeries` 等纯函数（客户端已有一份，注意与云函数镜像）
- 聚合结果含全部赛事 → payload 可能偏大，需评估（见 ⑥ 的同类问题）
- 快照兜底：客户端已有 `upcoming-local.json`，可作为表未命中时的兜底

**⚠️ 前置验证**：先量化它的实际贡献 —— 若 `upcoming-local.json` 快照 + 客户端
`getScheduledMatches` 已能覆盖绝大部分场景，**这项可以不做**（收益/复杂度比最低）。

**难度**：高｜**风险**：高（动首页核心数据流）

## ⑤ 死代码清理（零风险，建议最先做）

**客户端侧已确认零引用**的云函数 action：

| action | 为什么是死代码 |
|---|---|
| `saveFollowProfile` / `getFollowProfile` | 已被 follow-profile EF 完全取代（回退走 `setCached`/`getCached`）|
| `sendSmartReminders` | **从未接线**（部署了但客户端零引用）|
| `liquipediaListTournaments` | 调用方 `listAllTournaments` 已于 O-11 移除 |
| `getLiquipediaUpcoming` | 零引用 |
| `liquipediaPrewarm` | 零引用（预热已由 GH Actions 承担）|

**清理策略（保守）**：
1. **先做客户端侧**：删无用 wrapper（如 `liquipediaListTournamentsProxy` 已删）
2. **云函数 action 暂留**：无害（不调用不产生费用），等观察期过了再删
   → 因为删 action 需重新部署，且**「零引用」的审计此前出现过假阴性**
   （有的 action 是通过 `wx.cloud.callFunction` 直调，不走 `call()`，容易被 grep 漏掉）

**难度**：低｜**风险**：极低（客户端侧纯删除）

## ⑥ search_index 瘦身（需产品确认）

**现状**：GH Actions 灌表后 `search_index` payload = **472.7KB**（10192 个联赛）。

**影响**：每次「SB 未命中 + 本地缓存过期」都要下载并解析 ~470KB JSON。
**非迁移引入的回归**（云函数原实现也是全量），但值得优化。

**改法**：`buildSearchIndex` 加过滤，只保留 tier ∈ {professional, premium} 或命中 curation 的联赛
→ 预计降到几十 KB。

**⚠️ 这是产品决策**：会改变搜索覆盖范围（冷门联赛搜不到）。
**必须先确认产品是否接受**，不能擅自改。

**难度**：低｜**风险**：中（影响搜索体验，需产品拍板）
