# 复核补充：前两轮为什么「不全面」

> 本文是对 `云后台迁移整体复核报告_2026-09-12.md` 的**自我修正**。
> 触发问题：这次复核是否真的了解小程序当前情况？是否全面？有无遗漏？
> **诚实回答：不全面。** 前两轮都停在「代码 + 表」层面，漏掉了几个更基础的面。

## 🔴 遗漏 1（最严重）：云开发的**定时触发器**，前两轮完全没看到

实测 `config.json`（**此前从未打开过这两个文件**）：

```
cloudfunctions/aggregation/config.json
  · cacheRefresh     "0 0 */6 * * *"     → 每 6 小时
  · schedulePreheat  "0 */30 * * * *"    → 每 30 分钟

cloudfunctions/cron-discover-tournaments/config.json
  · dailyDiscover    "0 0 3 * * * *"     → 每天 03:00
```

### 这意味着什么

前面两轮把云开发的角色概括为「回退链路 + LP 抓取出口」，**这是错的**。云开发还在承担
**三个服务端定时任务**，它们与客户端调用完全无关，grep 客户端代码**永远查不到**：

| 触发器 | 推测职责 | 关停后 |
|---|---|---|
| `cacheRefresh`（6h） | 预热 `search_index` / `teams_hot`（我们以为只有 GH Actions 在灌） | 停 |
| `schedulePreheat`（30min） | 赛程预热（影响首页/详情页冷启动） | 停 |
| `dailyDiscover`（每天 3:00） | **赛事发现**（`discoverOpenDotaTournaments`） | 停 |

### ★ 这直接改变了方案②的结论

我上一轮推断「curation 远程覆盖机制**可能从未启用**」——依据只是「Supabase 三表全空」。

但 `cron-discover-tournaments` 每天在跑 `discoverOpenDotaTournaments`，**它很可能就是往
云开发 DB 的 curation 集合写数据的那个进程**。也就是说：

- **云开发侧的 curation 很可能有数据**（不是「从未启用」）
- 那么 ② 的正确动作**不是下线，而是「把这条写入链路也迁走」** —— 否则赛事发现会断

⚠️ 仍需用户去云开发控制台确认，但**我上一轮的推断依据不足，应降级为「存疑」**。

### 前两轮为什么漏了

我只审了「客户端会调哪些 action」，**从没问过「服务端自己会定时做什么」**。
定时触发器不在客户端代码里、不在我写的调用清单里，所以两轮都完美地绕过去了。

**前两轮都没碰这个面** —— 我只审了「功能能不能跑通」，没审「数据出境后合规声明是否还成立」。

**这是本次复核里唯一可能触发「提审被拒 / 合规整改」的项**，优先级应高于所有技术项。

## 🟡 遗漏 5：没有「页面 × 数据源」矩阵

前两轮都是**按数据源**审（LP / KV / curation / 队标），
**从没按页面**清一遍：赛事列表 / 详情 / 战队 / 队员 / 对战历史 / 关注中心 / 我的 / 搜索
—— 每个页面的每个数据依赖，分别走哪个后端？有没有页面**完全没被迁移覆盖**？

按数据源审容易自以为「覆盖面全了」，按页面审才能发现「某个页面整条链路没碰」。

## 🟡 遗漏 6：生产配置前置（域名白名单）

Supabase 直读要在**真机**生效，依赖 MP 后台的 `request 合法域名`（含 `supabase.co`）。
`project.config.json` 里只在本地配置层面出现 supabase，**真机白名单无法从仓库确认**。
项目记忆里这本来就是「提审硬阻塞」项 —— 若未配置，**所有 SB 直读在正式版都会失败**，
而开发工具里（可勾选「不校验域名」）却是好的 —— 典型的「开发环境验证通过、上线全废」陷阱。

## 🟡 遗漏 7：迁移的实际收益从未被测量

迁移的**初衷是「比赛页加载慢」**。现在做完了：LP 走 EF、KV 直读、队标预抓……
但**没有任何前后对比数据**：首页/赛事页冷启动耗时、请求数、字节数。
没有基线，就无法判断这一整轮投入是否真的解决了最初的问题。

## 🟡 遗漏 8：没有回滚预案

方案决定「接受 EF 单点」，但配套只有监控告警，**没有回滚/降级剧本**：
EF 挂 2 小时怎么办？PostgREST 直读失败时客户端降级成什么？云开发兜底还在不在（答案是：在，但没写明何时启用）？

## 🟡 遗漏 9：新路径无集成测试

离线套件（test-canonical / test-bo 等）覆盖的是**纯函数**。
新引入的 SB 直读、`_sbKvGet`、`_sbLogoGet`、本地解析优先等**链路级行为没有测试**，
回归只能靠真机手工观察 Console 日志。

## 结论：前两轮「不全面」的根因

| 前两轮的做法 | 漏掉的 |
|---|---|
| 只审「客户端会调哪些云函数」 | **服务端定时触发器**（3 个）—— 不在客户端代码里 |
| 只审 `aggregation` | **第二个云函数** `cron-discover-tournaments` |
| 只审「函数调用」 | **云开发其它能力**（DB / 存储 / 云调用）—— 本次检测失败，仍未知 |
| 按数据源审覆盖 | **按页面审覆盖**（可能有整页未碰） |
| 只审「功能通不通」 | **数据出境的合规声明是否仍成立** |
| 只审「代码/表状态」 | **生产配置（域名白名单）与真实收益测量** |
| 只审「怎么做」 | **出问题怎么回滚** |

**一句话**：前两轮是「**代码级 + 数据级**」复核，缺的是「**运行级 + 场景级 + 合规级**」。

## 🔴🔴 重大修正：第二个云函数不是「辅助」，而是**内容运营链路**

实测 `cloudfunctions/cron-discover-tournaments/index.js`（**776 行，前两轮从未打开**）：

```
每天 03:00 自动执行（timer: dailyDiscover）
  步骤 1  拉 Liquipedia 全量赛事（带年份）
  步骤 2  筛出 DOTA2 相关赛事
  步骤 3  对比云开发 DB 的 curation_events 集合 → 找出未收录的新赛事
  步骤 4  ★ 把新赛事写入 curation_events（upsert 幂等）
  步骤 5  ★ 分级同步 syncTiers：读 status='pending_review' 的赛事 → 抓 LP 分级 → 写回 curation_events
  步骤 6  写 admin-logs（action='cron_discover'）
  步骤 7  有发现时写告警（cron_discover_alert / cron_tier_sync_alert）→ 管理后台告警源
```

关键常量：`CURATION_EVENTS_COLL = 'curation_events'`、`ADMIN_LOGS_COLL = 'admin-logs'`

### 这推翻了我上一轮的两个判断

**① 「curation 远程覆盖机制可能从未启用」—— 错了**

我上一轮的依据只是「**Supabase** 三表全空」。但真正在写数据的是**云开发 DB 的 curation_events 集合**，
且**每天都在写**（新赛事入库 + 分级同步）。

→ 所以 `getCuration`（客户端读远程 curation）**大概率一直有数据**；
→ 方案② 的正确动作**不是「下线」，而是「把整条链路迁走」** —— 见下。

**② 「云开发只剩回退链路 + LP 出口」—— 严重低估**

云开发还在承担**内容运营链路**（前两轮 grep 客户端代码永远查不到，因为它是服务端定时任务）：

| 云开发承担 | 关停后 |
|---|---|
| 新赛事自动发现入库 | **停止** —— 不再有新赛事进库 |
| 新赛事自动分级同步 | **停止** —— 新赛事永远 pending_review、拿不到 tier |
| 管理后台告警源（admin-logs） | **断源** —— `admin/` 后台的告警列表失效 |
| 缓存预热（cacheRefresh 6h） | 停止 |
| 赛程预热（schedulePreheat 30min） | 停止 |

### 连带：**管理后台也是云开发依赖方**

`admin/`（Vite 管理端）读云开发 DB 的 `admin-logs` / `curation_events`。
前两轮的「云开发退场」分析**只考虑了小程序，完全没考虑管理后台**。

### 云开发「非函数」能力：这次重测干净了（好消息）

排除临时文件干扰后重测 251 个文件：

```
云数据库        ⚪ 未用（客户端不经 wx.cloud.database）
云存储 上传/下载 ⚪ 未用
微信开放接口     ⚪ 未用
云函数调用       🟡 pages/leagues/leagues.js 等
云开发初始化     🟡 app.js 等
```

→ **客户端侧只有「云函数」一种依赖**，没有云存储/云数据库的额外面。
关停的复杂度集中在**服务端定时任务 + 管理后台**，不在客户端。

## 修正后的「云开发退场」真实范围

前两轮把这件事理解为「把客户端的数据读取从云函数搬到 Supabase」。**实际范围是**：

```
客户端读取          ← 前两轮已覆盖（EF + SB 直读）
服务端定时任务 ×3   ← 🆕 从未考虑（cacheRefresh / schedulePreheat / dailyDiscover）
第二个云函数        ← 🆕 从未审计（776 行：赛事发现 + 分级同步）
云开发 DB 集合 ×2   ← 🆕 curation_events（每天写）/ admin-logs（告警源）
管理后台 admin/     ← 🆕 从未纳入（依赖上述集合）
```

**其中「赛事发现 + 分级同步」是有真实业务价值的自动化** ——
它决定了「新赛事能不能被自动收录、能不能自动拿到分级」。

### 迁移它意味着什么（新的方案②）

```
把 cron-discover-tournaments 的职责迁到 GH Actions（与 LP / KV / 队标同一套路）：
  · 每日拉 Liquipedia 全量赛事 → 对比 → 新赛事写入 Supabase curation_events
  · 分级同步 syncTiers → 写回 Supabase
  · 告警写入 Supabase（或改由 GH Actions 失败通知替代）
  · 客户端 getCuration 改读 Supabase curation_events（此时「迁表」才成立）
```

**且必须先决定**：管理后台 `admin/` 怎么办（改读 Supabase？还是它本来就不常用可以暂时不动）？

## 🔴🔴 连带挖出「比赛页慢」的机制性根因

读 `cloudfunctions/aggregation/index.js` 的 `handleGetCuration` 实现：

```js
function handleGetCuration(event) {
  const clientVersion = event.params.clientVersion || '';
  // L1 命中且版本一致 → { unchanged: true }        ← 唯一「省流量」的分支
  // 版本不一致 → return { data: _curationL1Cache, version }   ← ★ 全量返回
  // L1 未命中 → loadCurationFromDB() → 全量返回
}
```

### 关键发现：**clientVersion 是「全有或全无」开关，不是真增量**

- 版本号一致 → 返回 `{unchanged}`（省流量 ✓）
- **版本号只要变了 → 返回全量 2,414 条**

而版本号**每天 3:00 的 `dailyDiscover` 发现新赛事时就会变**（写库即改版本）。

→ **机制**：每天凌晨新赛事入库 → 版本变更 → **次日所有客户端首次打开都要重新下载 2,414 条全量**。

### 量级估算（需实测确认）

```
2,414 条 × 每条约 1~3KB（canonical/aliases/年份/赛期/tier/status/奖池/参赛队…）
  ≈ 2.4 ~ 7 MB 单次响应
```

而且客户端会 `cache.set(CACHE_KEY, ...)` 落到本地 Storage ——
**小程序 Storage 总上限 10MB**，这里可能一次占掉大半。

### 这很可能就是「比赛页/首页慢」的真凶之一

项目最初的迁移动机就是「比赛页加载慢」。前两轮我把原因归给「LP 抓取慢 / 跨境网络」，
但**这个「每日全量重拉数 MB curation」的机制**从未被提及 —— 而它恰好命中了「每天第一次打开特别慢」这种典型症状。

⚠️ 需实测确认（我无法直接测量真机）：
- 真机 Console 里 `getCuration` 的响应大小与耗时
- 本地 Storage 占用（`wx.getStorageInfoSync()`）

## 修正后的 ② 方案（从「迁读」变成「迁链路 + 顺带治病」）

```
第一步  存量迁移：2,414 条 backfill 到 Supabase curation_events（一次性脚本）
第二步  读取改造：客户端改读 Supabase
         ★ 顺带优化：不再全量拉取，改为「按年份 / 按状态 / 分页」按需拉
           —— 这一步才是真正解决「比赛页慢」的动作
第三步  写入迁移：把 dailyDiscover（赛事发现 + 分级同步）迁到 GH Actions
         （与 LP / KV / 队标同一套路：GH 出口不受限 + 写 Supabase）
第四步  管理后台：admin/ 改读 Supabase（或先不动，但需明确）
第五步  下线：以上都验证后，才谈关停云开发
```

### 顺带要回答的产品问题

2,414 条里 **有多少是真正会展示的**？赛事列表页有没有按 tier/status 过滤？
如果没有过滤，那「拉全量再本地筛」这个设计本身就是慢的来源 —— 应该在**查询层**过滤。
