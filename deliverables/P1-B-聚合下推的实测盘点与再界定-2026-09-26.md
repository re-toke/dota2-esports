## 1. 方案前提纠错（**第 6 处方案事实错误**）

方案 §6 `P1-B` 写道：

> 项目有 `utils/sqlFragments.js`，说明尚有聚合在客户端算 → 可下推为 **Postgres 视图 / RPC** 函数。

**实测（读 `utils/sqlFragments.js` 全文 38 行）**：

```js
function LEAGUE_WINDOWS_SQL(nowSec) {
  return "SELECT leagueid, min(start_time) AS earliest, max(start_time) AS latest, "
       + "max(start_time + duration) AS last_end, count(*) AS n "
       + "FROM matches WHERE start_time > " + floor + " GROUP BY leagueid";
}
```

| 方案假设 | 事实 |
|---|---|
| 这是"客户端聚合" | ❌ 它是**客户端生成 SQL 文本**（字符串拼接），不是对已取回数据做聚合 |
| 目标是 Postgres | ❌ 目标是 **OpenDota 的数据库**（`FROM matches` 是 OpenDota explorer 的表；该 SQL 经 EF 转发到 `api.opendota.com/api/explorer`）⇒ **无法"下推为 Supabase Postgres 视图"**（两套库） |
| 是"尚待优化"的部分 | ❌ 它**已被治理过**：v8.31 把函数表达式下界改为**整数秒常量**（走索引，16566ms/500 → 1215ms/200），并把下界**对齐当日 00:00 UTC** 让缓存 key 稳定（实测「source=fresh 永不命中」的根因） |

> 该文件顶部还写着"供 api.js 与**云函数**共享"——那是已退役的 `cloudfunctions/aggregation` 的历史遗产。

## 2. 客户端真正做的"重活"是什么（实测）

不是 SQL 聚合，而是**跨源融合**（全在 `utils/sources.js`）：

```
groupSeries（按 series_id 分组）
  → patchNullSeriesId（series_id 缺失时按"队名+时间窗"软关联）
  → _orphanPairMerge（簇合并）
  → 跨源去重 + absorbSettledGames（把 OpenDota 已结算局注入 LP 系列）
  → BO 判定（resolveBoType 多信号）
```

**能否下推到 PG？判据是"源数据在不在 PG 里"**：

| 数据 | 在哪 | 能否下推 |
|---|---|---|
| OpenDota 比赛/联赛 | OpenDota（经 EF 转发） | ❌ 不在 PG |
| Liquipedia 赛程/元数据 | LP（经 GH Actions 灌表 + 客户端直读） | ⚠️ **缓存行**在 `aggregation_cache` / `upcoming_schedule`，但**原始语义**（分页/修订）已丢 |
| curation | PG（`curation_events`） | ✅ 在，但它本就是**目标数据**而非待聚合源 |
| Steam / STRATZ | 各自 API | ❌ 不在 PG |

⇒ **跨源融合无法下推**（要下推就得先把三个外部源全量同步进 PG = 重造数据仓库，成本远超收益）。
⇒ 方案把"**跨源 join**"当成了"**SQL 聚合**"——这是两项完全不同的事。

## 4. 建议

1. **`P1-B` 降级为「不做」** —— 保留本文作为"为什么不做"的留档，避免后续会话重复提出。
2. 若要做，只做 **b/c 中的一个**，且**必须先用 `P0-B` 的指标量化收益**（否则无法判断是否值得）。
3. **真正的性能着力点回到 `P2-A`**（`patchNullSeriesId` 含回滚重分组 / `_orphanPairMerge` / BO 判定都在主线程）
   —— 这也是复核意见 `D.2-②` 的结论：长列表虚拟化解决的是"渲染节点数"，**解决不了"融合计算量"**。
4. 方案 §5.2 对 PostgREST 的**定位**（"真正价值不是'引入'，而是'用足'"）方向正确 ✅ ——
   但**举错了例子**；"用足"的真实实例是 `diag_report`（本轮新增）与缓存表（早已在用）。
