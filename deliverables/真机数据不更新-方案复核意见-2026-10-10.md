## 1. ★ 我独立做的受控探测（**替代 R1，且比 R1 更强**）

沙箱与真机处于**同一网络环境**（都报 ECONNRESET）⇒ 可在沙箱做受控探测，**无需用户切换网络**。
探针内容：DNS 解析 → TLS 握手（含证书链）→ 真实 HTTP 请求。

| 主机 | DNS | TLS | HTTP |
|---|---|---|---|
| `gkticzdaicpdtxheyxsd.supabase.co` | 104.18.38.10 / 172.64.149.246（**Cloudflare，正常**） | **❌ `ECONNRESET`** | ❌ `ECONNRESET` |
| **`api.opendota.com`** | **103.73.220.77**（⚠️ **不是** Cloudflare 的 IP） | **❌ `DEPTH_ZERO_SELF_SIGNED_CERT`（自签证书）** | ❌ 同左 |
| `dota.haglund.dev` | 104.21.65.246 / 172.67.195.206（Cloudflare） | ✅ Let's Encrypt | **HTTP 200（18KB）** |
| `liquipedia.net` | 94.23.144.183 | ✅ Let's Encrypt | 可达 |
| `api.stratz.com` | Cloudflare | ✅ Google Trust Services | 可达 |

### 由此得到的两条**精确机理**（比 v3 的笼统"网络层"更硬）

**① `*.supabase.co` = SNI 阻断（TLS 握手被 RST）**
- DNS **能正常解析**到 Cloudflare ⇒ **不是 DNS 污染**；
- 但 **TLS ClientHello 一发出就被 RST** ⇒ 典型的**基于 SNI 的域名级阻断**。
- ★ **推论（决定方案）**：换 IP、改用 DoH/加密 DNS、加 hosts **全都无效** ⇒ **唯一解是"换一个不被阻断的域名"**。

**② `api.opendota.com` = DNS 劫持 + 自签证书**
- 解析到 `103.73.220.77`（真实 OpenDota 在 Cloudflare 上，不可能是这个 IP，也不会是自签证书）
- ⇒ **中间人/劫持** ⇒ 真机日志里的 `ERR_CERT_AUTHORITY_INVALID` 是**同一现象** ✓
- ★ **推论**：**客户端直连 OpenDota 这条路也废了** ⇒ "直连兜底"在本网络下**不再具备兜底能力**。

**③ 关键对照**：`dota.haglund.dev`（同为 Cloudflare）**完全正常** ⇒
⇒ **不是"整个 Cloudflare 被墙"，是"域名名单级阻断"** ⇒ **自建域名只要不在名单内即可用** ✓（这对 R2 至关重要）

## 3. ❌ R2 复核：**发现一处致命缺陷**（必须修正）

> 原 R2 写的是「**用国内服务器/云函数做反向代理**，自定义域名指向 Supabase」。
> **这条不成立** —— **国内服务器同样连不上 `supabase.co`**（阻断发生在国际出口/SNI 层，
> 与"是谁发起的请求"无关）⇒ **代理放在国内等于把断点后移一格，问题原样存在**。

### ✅ 修正后的 R2′：中转必须放在**境外/香港**，且使用**自有域名**

| 实现 | 做法 | 成本 | 评价 |
|---|---|---|---|
| **R2′-a（推荐先试）** | **Cloudflare Worker + 自有域名**，同时反代 ① Supabase EF/PostgREST ② OpenDota（保留 `/leagues` 裁剪） | **免费额度**（10 万次/天），无运维 | ★ 最省事；但**依赖"自有域名在 Cloudflare 上不被阻断"** —— 需**先做可达性实测**（§1 已证 Cloudflare 本身可达 ✓，域名级才是变量） |
| **R2′-b（最稳）** | **香港/新加坡轻量服务器** + Nginx/Caddy 反代 + 自有域名 HTTPS | 一台轻量 + 域名 | 稳定性最好；需自己运维与续费 |
| ❌ R2′-c | 国内服务器反代 | — | **不可行**（见上） |
| ❌ R2′-d | 只给 Supabase 配 Custom Domain | 免费 | **不保险**：边缘仍在境外 Cloudflare，域名若被列入名单则同样被 RST |

**R2′ 的落地要点（都要验证，别想当然）**：
1. **中转域名必须**：① 国内可达（不被 SNI 阻断）、② HTTPS 证书有效、③ 加进小程序后台 **request 白名单**；
2. **路径规划**：客户端现在有两个目标域名（`config.supabase.url` 与 `api.js` 的 `BASE`）
   ⇒ 建议统一到一个中转域名下用**路径前缀区分**（如 `https://<my>/sb/…` 与 `https://<my>/od/…`），
   客户端只改**两处常量**，改动面最小；
3. **`/leagues` 裁剪要保留**（否则每次拉 1MB）；
4. **鉴权**：中转对 Supabase 的请求需带上正确的 anon key（见 R3）；对 OpenDota 无需 key；
5. **⚠️ 备案问题需你确认**：小程序 request 域名指向**境外服务器**通常无需 ICP 备案，
   但微信平台对域名合规有自身要求 ⇒ **上线前用一个小号版本实测白名单 + 请求是否被拦**（成本低，别跳过）。

## 6. 新增 R5：**拆掉对 Supabase 的"读取依赖"**（降低单点，强烈建议）

既然 `*.supabase.co` 在国内被阻断、而**中转是单点**，那么应尽量**减少必须走中转的东西**：

| 数据 | 性质 | 建议 |
|---|---|---|
| **curation（赛事情报/别名/分级）** | **低频变更、体积小** | **由 CI 烘焙进包**（CI 在境外可读 Supabase ⇒ 生成快照 ⇒ 提交 ⇒ 随版本发布）；客户端优先读本地，远端仅作热更新 ⇒ **彻底摆脱对 Supabase 的实时依赖** |
| **schedule（赛程，需实时）** | 高频 | 保留经中转读取；同时保留 haglund/LP **直连兜底**（已证可达 ✓） |
| **OpenDota 各类数据** | 高频、体量大 | 经中转（含裁剪） |
| **远端队标 `aggregation_cache`** | 低频 | 已由 `team-logo-local-data.js`（140KB 本地快照）覆盖 ⇒ 可**直接停用**远端读取 |

⇒ 目标：**"中转挂了也能用"的最小可用集**（curation 烘焙 + haglund/LP 直连 + 本地队标快照）。

## 9. 一句话复核结论

**根因判定正确（网络层域名阻断），但方案有一处致命错**：代理**不能放国内**（国内同样连不上 Supabase）
⇒ 必须**境外/香港中转 + 自有域名**；同时把"直连兜底"的目标从被劫持的 `api.opendota.com` 换成
**已实测可达的 haglund/LP/STRATZ**，并把 curation 类**低频数据烘焙进包**以弱化单点。
R1 不可行**不影响结论** —— 我已用同网络的受控探测把机理钉死（**SNI 阻断 + DNS 劫持**）。
