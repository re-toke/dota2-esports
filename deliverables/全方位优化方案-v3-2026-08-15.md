## 二、三维度总审查（对 4 份扫描的交叉把关）

### 2.1 合理性维度（收益 × 时机 × 成本）

**采纳的排序逻辑**：
1. **用户感知优先**：B1（下拉刷新失效）是 TI 期间最高频的可感知缺陷，且 B3（SQL 缺 `last_end`）导致「进行中」判定回退 start_time 误判——两 bug 同源同修，半小时内完成。
2. **数据源安全其次**：LOAD-7（Liquipedia 重试不占 2.2s 槽位）有历史 IP 被封教训，属合规刚需。
3. **架构项区分「重要度」与「时机」**：架构扫描将三大文件拆分（ARCH-1）标为最高重要度，但 TI 期间回归风险 > 收益——**接受其重要性评级，推迟其执行时机至 9 月**。这与 v2.0 结论一致，本方案维持。

**对扫描结论的 3 处修正**：
- **降级 PERF-1 中"require 提顶层"子项**：性能扫描实测 `require` 有模块缓存（首次后近零成本），v1.1 高估了该项收益；真正的瓶颈是 `find()` 双向 indexOf 线性扫描（O(赛事数×events数)），**修复重点是 Map 索引而非 require 位置**。leagues.js 内 3 处 require（L591/919/1070）保持现状可接受。
- **降级 PERF-2（倒计时降频）**：已有 hasChange 守卫 + 路径式 setData，实测仅秒级文本变化才触发渲染，收益边际化，从 v1.1 第二梯队降为 P2 顺手项。
- **维持 P1-3 虚拟列表缓做**：分页（pageSize=20）+ onReachBottom + hero-icon lazy-load 已落地，首屏负担大幅降低；遗留问题是 appendPage/refresh 全量 setData 重传（PERF-3/5），改路径式 patch 成本低于引入 recycle-view 依赖。

**对 STRATZ 处置的决策**（REDUN-13 二选一）：采用**方案 A（标注停用 + 调用点短路注释）**而非整体删除——Cloudflare 403 属外部不可控因素，未来恢复成本低；且云函数 stratzGql handler 仍部署，整体删除会造成客户端/云端不对称。375 行保留但运行时零成本。

### 2.2 逻辑性维度（方案正确性 × 依赖关系）

**关键修复的逻辑约束**（实施时必须遵守）：
1. **B1 修复必须与写入侧 key 逐字符对齐**：`cache.remove(_v() + '/leagues|{}')`，且 explorer key 必须复用 `sqlFragments.LEAGUE_WINDOWS_SQL` 常量构造——手拼 SQL 会再次漂移（B3 的教训就是第三份手拼拷贝）。**B1 与 B3 是同一处代码，一次修复**。
2. **B2 修复必须复用 cached() 的 key 构造与 TTL 表**：云成功路径写本地缓存若独立实现 key 拼接，会引入第四种 key 形态（现已有 cached 带版本 / cloudCache 裸 key / leagues 手拼三种）。建议在 api.js 内部新增 `writeThrough(path, data, ttl)` 私有函数，云/直连两条路径共用。
3. **LOAD-9（cloudCache 裸 key）与 B1 同族**：修复时统一从 api.js 导出 `_v()`，cloudCache.js 引用同一实现，禁止复制粘贴版本计算逻辑。
4. **死代码删除的测试联动**（冗余扫描已标注，此处定为硬规则）：D4 `getLeagueName` 删除必须同步修改 test-sources.js:354 用例；D1 保留 `playerWon`（test-formatters 覆盖）；D8 删除 config 字段但**不动** cloudProxy.js PARAM_MAP 与云函数 handler（防御性保留）。**每次删除后跑 `npm run test:all` + lint**（husky 会强制执行）。
5. **REDUN-12（倒计时去重 7 处）合并前提**：各处分档阈值需先比对一致（天/时/分三档边界），抽 `util.formatCountdown(sec)` 时以 leagues.js 现行为准，index.js fmtCountdown 保持独立（它含"即将开始"文案逻辑，不应强行合并）。
6. **ARCH-6（魔数入 config）零行为约束**：BJ_OFFSET 重复 5 处收敛为 `config.time.bjOffsetSec`，值必须保持 `8*3600` 不变——这是纯提取重构，任何行为变化都视为错误。

### 🔴 O-26（P0 · 新增）· 云函数管理 action 无鉴权

**位置**：[cloudfunctions/aggregation/index.js:1926-1983](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/cloudfunctions/aggregation/index.js#L1926)（exports.main 入口）+ 三个危险 handler

**证据**（逐行实证）：
- `exports.main` 入口对 HANDLERS Map 路由的 28 个 action **无任何统一鉴权层**——拿到云函数名即可直接调用
- `adminWriteCuration`（L1377）：无 OPENID 校验，任何客户端可执行 `upsertEvent`/`deleteEvent`/`upsertTeam` 篡改/删除 curation_events / curation_teams
- `setCached` / `getCached`（L1184/L1177）：接受任意 `key` 参数，任何客户端可**读写任意云缓存 key**——写入伪造的 `/leagues` 数据将污染**所有用户**的共享缓存
- `sendSmartReminders`（L1677）：接受任意 `openid` 参数，可给他人发送订阅消息（骚扰向量）

**风险评级依据**：小程序包可被解包提取云函数名（函数名不是秘密）；curation 篡改影响全体用户的数据正确性；虽有 admin-logs 审计可事后恢复，但事前无防线。

**修复方案**（约 30 行，TI 期间可做——不碰数据链路，纯入口加锁）：
```javascript
// exports.main 入口，HANDLERS.get(action) 命中后、执行前：
const ADMIN_ACTIONS = new Set(['adminWriteCuration', 'setCached', 'getCached', 'sendSmartReminders', 'buildSearchIndex', 'buildTeamsIndex', 'discoverOpenDotaTournaments', 'refreshTeams']);
if (ADMIN_ACTIONS.has(action)) {
  const wxContext = cloud.getWXContext();
  const ADMIN_OPENIDS = ['<管理员 OPENID>']; // 云函数环境变量更佳
  if (!ADMIN_OPENIDS.includes(wxContext.OPENID)) {
    return { error: makeError(ERROR_CODES.FORBIDDEN, 'unauthorized') };
  }
}
```
- 管理员 OPENID 通过 `getOpenId` action 自查后填入；建议用云函数环境变量 `process.env.ADMIN_OPENIDS` 管理
- `getCached` 若被客户端正常功能使用，可降级为白名单 key 前缀校验（仅允许 `follow_profile_` 前缀）

**三维度**：合理性 高（30 行防全体用户数据污染）；逻辑性 高（纯入口拦截，零业务改动）；合规性 高（微信云开发最佳实践）。
