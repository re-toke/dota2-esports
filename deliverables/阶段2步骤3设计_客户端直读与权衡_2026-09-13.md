## 一、③ 要改什么

`utils/remoteCuration.js` 的 `load()`：
**现在**：调云函数 `getCuration` → 拿 `{events, teams, tiContestantIds, version}`
**改为**：PostgREST 直读三张表 → 拼出同样形状

映射（已验证等价）：

```
curation_events  →  events = rows.map(r => r.data)
                    ← 云函数当年也是「去掉 _id/updatedAt 后的 doc」，形状一致
curation_teams   →  teams = { [row.team_id]: row.data }
curation_meta    →  tiContestantIds = row.value.ids
version          →  由「行数 + 最大 updated_at」派生（用于本地缓存失效判断）
```

## 二、⚠️ 必须先拍板的权衡：拉多少？

**现状**：客户端经云函数只能拿到 **500 条**（`.limit(500)`，无排序）。
**全量拉**：2414 条 ≈ **690KB** —— 比现状**多 5 倍数据**。

而刚查明的数据质量事实：

| | 条数 |
|---|---|
| 全部 | 2414 |
| 有 `year` | 1050（44%）|
| **有可用 `start` 赛期** | **11** |
| 有 `leagueId` | 1600 |
| 完整策展（有奖池/参赛队） | ~35 |

**→ 直接全量拉，会让「每日首开慢」的问题雪上加霜**（这正是项目最初的痛点）。

### 三个选项

| 方案 | 拉取量 | 说明 |
|---|---|---|
| **A. 等价替换**（全量拉） | ~690KB | 行为与现状一致（但比现在的 500 条更多），**只验证「脱离云开发」**，性能单独优化 |
| **B. 一次到位**（按需拉） | 视过滤而定 | 直读 + 只拉有意义子集（如 `year >= 2025` 或 `start 非空`）→ 几十 KB |
| **C. 先 A 后 B** | —— | 分两步走，每步可验证 |

### 我的建议：**C（先 A 后 B）**

理由：
1. **A 是「等价替换」** —— 只把数据源从云函数换成 PostgREST，**行为不变**，出问题容易定位（只可能是「直读本身」的问题）
2. **B 会改行为**（远程条目变少 → 赛事列表内容变化），风险与 A 不是一类事，**不该混在一次改动里**
3. 但 A 会让数据量从 500 → 2414，**必须紧接着做 B**，不能停

### 若你选 B/C 的过滤条件，需要定的规则

候选（可组合）：
```
year >= 2025                     → 83 条
或有 start（有赛期）              → 11 条
或 leagueId 非空且 year 近 3 年   → ?
```
⚠️ 关键问题：**赛事列表的「已结束」tab 需要历史赛事吗？**
如果需要，过滤就得放宽（否则历史 tab 空掉）。
