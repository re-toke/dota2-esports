### 2.2 为什么会错（根因，三条）

**根因一：把「文档口径」当成了「代码事实」。**
v1 的主要证据源是 `README.md`（2026-07-24）、`PROJECT_OVERVIEW.md`（2026-07-30）、`CODE_WIKI.md`（2026-07-24）、`deliverables/*`。这些是**时点快照**，而本项目以**每天数个提交**演进 —— 我读的是**两个月前的世界**。整合版技术文档停在 v8.51（2026-09-10），也已经落后 2 周。

**根因二：拿子代理的「片段清单」当结论，没有追证。**
本轮之前的三次子代理调用，返回的都是 `Relevant Code Snippets`（代码片段清单）而不是完整分析结论。**我把"它指出了哪几行"误当成了"它已经论证清楚了"**，于是没有回到源头核验。典型：我看到 `config.js` 里 `supabase.enabled: true`，就推断"这是灰度"——但**从没去 `ls cloudfunctions` 看那 7 个 action 的宿主还在不在**。

**根因三：没有做最基础的一步 —— 以仓库状态为第一证据。**
`git log --oneline 2ebce62..HEAD`（148 提交）和 `ls cloudfunctions`（空）这两条命令，**任意一条**都能在一个回合内推翻 v1 的核心判断。我却在第二轮才跑。

### 2.3 方法论纠偏（写成本文的使用纪律）

> **证据优先级铁律（v2 起生效）**
> 1. **代码 / 仓库状态 / `git log` > `deliverables/` > README / PROJECT_OVERVIEW / CODE_WIKI > 整合版技术文档**
> 2. 任何"现状"结论，必须能指向**代码行或提交号**；只由文档支撑的结论必须标注"**待代码核验**"
> 3. 提出"建议做 X"之前，**先 `grep X`**，确认它还没被做过
> 4. **每轮调研的第一条命令固定为**：`git log --oneline <上次基线>..HEAD` + 目录结构

**已核实事实**：
- 微信云开发**零残留**（`git ls-files cloudfunctions` = 0，且客户端已无 `wx.cloud` 调用）

- `admin-write`：要求 `x-admin-token` = `ADMIN_TOKEN`，仅 POST，支持 `upsertEvent/deleteEvent/upsertTeam/deleteTeam/updateMeta/upsertUpcoming`

| 6 | **Supabase Realtime** | 项目 `config.realtime.url` 仍为空、降级 30s 轮询（自建 WebSocket 骨架 `utils/realtime.js`）。Realtime 是 Supabase 成熟能力，**可直接替代自建 wss 后端**。⚠️ 需评估：小程序 WebSocket 需 **wss 合法域名**（仍是同一备案约束），且需核对国内延迟 |
| 7 | **Supabase Vault** | 官方推荐用于存放 `pg_cron` 调 EF 的凭据。可用于 `ADMIN_TOKEN` / `WX_APPSECRET` 的集中管理 |
| 8 | **`Egezenn/dota2-datawrapper`** | TS/浏览器向，不能直接进小程序；**仅可借鉴其字段归一化与占位符/枚举解析实现** |
| 9 | **`supabase/supabase`（自托管）** | Apache-2.0，可自托管。但自托管需自配 `pg_cron`/备份/运维，成本高 → **当前不建议**，仅列长期选项 |

### 5.3 不适用（含否决理由）

| # | 项目 | 原因 |
|---|---|---|
| 10 | **`odota/core`** | MIT，但架构是**微服务集群**：`svc/parser.ts`（Java replay 解析）+ `store/cassandra.ts` + `store/redis.ts` + Postgres。自建成本极高，且数据 100% 派生 Valve → **不解独立校验问题** |
| 11 | **`dotabuff/d2vpkr`** | 是**数据仓库**（Valve 官方 KV 镜像），非代码库；同为 Valve 派生 |
| 12 | `liquipydia` / `liquipediapy` | Python + **均需 LPDB API key（本项目申请被拒）**；仅 model 字段定义可参考 |
| 13 | `Liquipedia/Dota2WebApi` | 是装在 **Liquipedia 站点上的 MediaWiki 扩展**，非客户端库 → 无法自建 |
| 14 | `lootmarket/esport-team-logos` | 队标图片仓库，**授权状态不明**，与"免费开源 + 遵守 ToS"硬约束冲突 |
| 15 | `rapier` / `@deademx/dota2` / replay parsers | 小程序无 replay 需求；GPL-3.0 / 重量级 |
| 16 | **`supabase-js`** | 项目自写 `supabaseClient.js`（`wx.request` + 按 EF 分桶熔断）已满足需求。换官方 SDK 需自定义 fetch adapter，**收益为负** → 不建议 |

**第二轮结论**：**仍然没有"拿来即用"的项目能整体优化本项目。** 真正有价值的复用点收敛为三条：
1. **`dotaconstants`（MIT）** —— 常量字典层（需裁剪 + 不可作独立校验源）
2. **`pg_cron` + `pg_net` + Vault** —— 库内调度层（**但要认清它同样会静默失败**）
3. **PostgREST 视图/RPC + Supabase Realtime** —— 平台内已有能力，去"用足"而不是"再造"

## 6. 修正后的优化方向

### P0-1 · 补"调度心跳看门狗"（最高优先，v1 判断不足的一项）

- **为什么**：现在调度全押 **GitHub Actions**，而 `ef-health.yml` 只探 **EF 健康**，**不探调度本身是否在跑**。`pg_cron` 若引入也**同样没有告警**（官方文档明确：无重试、非 2xx 不告警、项目暂停即静默停摆）。**"静默死亡"是这个架构唯一的系统性脆弱点**。
- **做什么**：① 加一个独立的"心跳"机制 —— 每个关键 workflow 成功后写入一张 `job_heartbeats` 表；② 由一个**来源不同**的探针检查"最近 N 小时内是否有心跳"，超期即告警；③ 探针本身不能放在同一个 GitHub Actions 里（否则一起死）。
- **优化后会怎么样**：从"几天后用户发现数据不更新"变成"几小时内收到告警"。**这是投入产出比最高的一条。**
- **风险**：低。

### P0-2 · 文档口径清洗与对齐（v1 保留，且更严重）

- **为什么**：`README.md`（7/24）、`PROJECT_OVERVIEW.md`（7/30）、`CODE_WIKI.md`（7/24）三份**已严重失真**（README 写"5 个 tab / STRATZ 已停用 / 进行中＝7 天"，三项全错），整合版技术文档停在 v8.51 而代码已到 v8.93+。**v1 的错误就是被它们直接导致的** —— 只要它们还挂着，下一个人（或下一次的我）会重复犯错。
- **做什么**：① 把三份旧文档**显式标记为归档**（加"已过时，见整合版"横幅）或重写；② 整合版补齐 v8.52 → v8.93+ 与云开发退役全过程；③ 修正 §1.3/§1.4 快照与提交链。
- **优化后会怎么样**：恢复"文档可信"，后续所有工作有共同坐标系。
- **风险**：低（整合版在工作区外，须脚本写入 + 先备份）。

### P1-1 · 长列表虚拟化（v1 唯一未被推翻的性能项）

- **为什么**：赛事列表、战队比赛历史、选手比赛历史仍是 `wx:for` 全量 `setData`。主包内 `league-detail.js` 177KB、`leagues.js` 113KB，列表渲染量是首屏后的主要瓶颈。
- **做什么**：`miniprogram-recycle-view`（需等高改造）起步；Skyline `scroll-view type="list"` 做单页灰度。
- **优化后会怎么样**：`setData` 数据量从"整页"降到"在屏节点"；长列表滚动与内存改善。
- **风险**：中（等高改造动视觉；Skyline 改渲染模式，须灰度）。

### P1-2 · 把聚合下推到 PostgREST 视图 / RPC

- **为什么**：项目有 `utils/sqlFragments.js`，说明部分聚合仍在客户端/客户端侧拼装。Supabase 的 Postgres 能直接提供视图与 RPC，**传输量能下降且逻辑单点化**。
- **做什么**：盘点仍由客户端聚合的查询，改为 Postgres 视图 / RPC 函数，客户端只做读取。
- **优化后会怎么样**：网络 payload 下降；聚合逻辑从"多处客户端代码"变成"数据库单一实现"。
- **风险**：中（改 SQL 契约，需与 `sqlFragments.js` 保持单点）。

### P1-3 · 启动期与主包体积继续治理

- **为什么**：`f461a0f` 已消除启动期 ~1000ms 长任务，但主包仍含 `sources.js` 157KB、`league-detail.js` 177KB、`team-logo-local-data.js` 140KB、`curation.js` 82KB。
- **做什么**：① 继续盘启动期长任务；② 评估把 P0 之外的模块（如 `curation.js` 的完整表）改为"分包/云端读取 + 精简本地兜底"；③ `deliverables/`、`admin/dist`、`rollback/*.zip`（约 30MB）确认为**不入包且不入库**。
- **优化后会怎么样**：冷启动更快、主包更小。
- **风险**：低（需先测，避免又造"分包不能 require 主包 JSON"那类约束）。

### P1-4 · `smart-reminders` EF 的去留（技术债清理）

- **为什么**：`收尾清单`（2026-09-10）记录该 EF **已部署但客户端零引用（未接线）**。这是典型的"部署了但没人用"的债，会让"哪些 EF 是活的"变得不可判断。
- **已核实（本轮）**：`smart-reminders` **并非死代码** —— 它是**服务端消费者**，契约由客户端上传的 `follow_profile_<openid>` 承担（`utils/subscribe.js:571` 明确注释「smart-reminders EF 依赖 `for (tid of profile.teams)` 调 `/teams/{tid}/matches`，改成对象会破坏该服务端链路」，`utils/subscribe.js:599` 亦说明其为推送侧唯一消费者）。因此「客户端零引用」是**设计使然，不是债**。
- **做什么（修正后）**：核实其**定时触发/调度是否真的在跑**（`refresh-wx-token` 是定时 EF，`smart-reminders` 需确认调用方）→ 若无人调用则接线，若已接线则只需补一条契约注释。
- **风险**：低。

### P2-1 · 独立校验源扩容（结构性，唯一能抬高准确度上限的事）

- **为什么**：`consensus` 权重是 `liquipedia 4 > curation 3 > steam 2 > stratz 1.5 > opendota 1 = community 1`，其中 **Steam / STRATZ / OpenDota 全是 Valve 派生** → 真正独立的只有 **Liquipedia + 人工 curation**；LPDB API 又被拒 → 这是**准确度的天花板**。此项**未被任何提交改变**，仍是 v1 中最有价值的判断。
- **做什么**：① 在 consensus 里**显式标注"同源族"**，不让同源数据互相计为独立票；② 长期扩容独立源（自建 haglund 实例 / 第二个独立 wiki 类源 / 持续补齐 curation）。~~③ 核实 `communityTierFromName` 的重复计权 quirk~~ → **本轮已核实为已修复，无需再做**（`sources.js:184`/`:731` 正确标 `source: 'community'`）。
- **优化后会怎么样**：共识置信度**从虚高变可信**（数字会变低但更真）；缺独立验证的赛事被显式标记。
- **风险**：低（标注类）。

### P2-2 · 用 Supabase Realtime 替代自建 WebSocket

- **为什么**：`utils/realtime.js` 是自建 WebSocket 骨架，`config.realtime.url` 仍为空 → 实际一直在 30s 轮询。Supabase 原生 Realtime 可省掉一个自建后端。
- **做什么**：评估小程序侧可行性（**wss 合法域名 + 国内延迟**），先做单页灰度。
- **优化后会怎么样**：去掉自建 wss 后端；比分更新从 30s 轮询变为推送。
- **风险**：中高（wss 域名约束 + 延迟未知 + Skyline 式灰度成本）。

### P2-3 · `dotaconstants` 的常量层替换评估

- **为什么**：本地 `heroes.js`/`items.js`/`neutralItems.js`/`itemZh.js` 是手工字典，维护成本高且易漂移；`dotaconstants` 是 MIT 且持续更新。
- **做什么**：**build-time** 裁剪出小程序所需子集（英雄 id/名、物品 id/名/合成关系），不打包全量。
- **优化后会怎么样**：字典准确度与维护成本改善；`itemZh` 等手工表的漂移风险下降。
- **风险**：中（体积控制 + 与现有 `itemZh` 中文名需对齐）。

### C.3 v2 的三处逻辑漏洞

**漏洞 1 · P0-1 核心设计问题未答，且"加告警"收益被高估。**
- v2 写"探针不能放同一个 GitHub Actions（否则一起死）"，但项目调度 **100% 在 GitHub Actions（同账号/同平台）** → **"不同来源"的落点未给**，A1 因此不是"低成本可立即做"。
- **反证**：`ef-health.yml` **本来就会失败发邮件**，但 `阶段6` 记录显示 9/17 已有失败、**9/18 才由人工检查发现"CI 从未绿过"（近 11 次全失败）**。
- ⇒ 真问题不是"没有告警"，而是 **"告警无人消费"**。加告警 ≠ 解决静默死亡。

**漏洞 2 · P1-1 长列表虚拟化的收益预期可能达不到。**
- `config.js` **`pageSize: 20`**，且已有"渲染分阶段快速路径" → 20 条卡片 setData **不是主瓶颈**。
- 真正开销在**主线程数据融合计算**：`groupSeries` + `patchNullSeriesId`（含回滚**重分组**）+ `_orphanPairMerge` + 跨源去重 + BO 判定，全在 `sources.js`（157 KB）JS 主线程。
- ⇒ 虚拟化解决"渲染节点数"，**解决不了"融合计算量"**。

**漏洞 3 · 牵出 v2 最大的未验证假设（风险等级被低估）。**
- 微信要求域名 **ICP 备案**；Supabase 域名（`*.supabase.co`）**是否备案未核实**。v2 只写"需评估 wss 域名"，却在"附 B"里把域名问题标为"仍无法核实"。

- ⚠️ **反证线索**：用户反馈的是"数据**错误**"而非"数据**全空**" → 说明请求实际能通 ⇒ 可能①仅开发版/未真机，或②域名确实可用。**这一点必须先澄清。**

### C.4 优先级排序问题

v2 §7 把 **P2-1（同源族标注 / 独立校验源）排在 D 批（最低）**。但它是 v2 中**唯一能真正抬高准确度上限**的一项，而用户明确"数据准确性很重要" ⇒ **应上提至 A/B 批**。

### C.5 v2 缺的第 4 条主线（建议补入 §6）

**「权威判据层」—— 把启发式从"主力"降级为"末位"：**

1. **权威身份**：`series_id` 可用时**绝对优先**；启发式仅在 null 时启用，且**必须显式打标**（`identitySource: 'series_id' | 'heuristic'`）

### D.2 逻辑性（自洽不自洽）

**① `P1-A`「数据管道双轨」是伪双轨 —— 按现方案落地会得到"看起来双轨、实际单轨"。**

- 事实：管道逻辑是 **Node 脚本**，由 GitHub Actions 执行 —— `sync-upcoming.yml:41` `run: node scripts/sync/fetch-liquipedia-upcoming.js`。
- `pg_cron` 只能经 `pg_net` 发 **POST JSON**（不支持 PATCH/PUT，官方 beta 限制），因此它 **无法自己"跑管道"**，只能"触发别人"。
- 触发对象只有两种可能，**两条都不成立**：
  - ① 触发同一个 GitHub workflow ⇒ **与 GitHub 同生共死**（GH 高峰期丢任务时，`repository_dispatch` 一样丢）⇒ 不是备份；
  - ② 直接调 EF ⇒ **得先把 LP 抓取/写表逻辑搬进 EF** —— 而这正是项目**已主动撤回**的路线（`b5d228f Revert` + `bfe7c7f`「撤回不必要的 LP 迁移」）。
- ⇒ **`P1-A` 缺一个未声明的前置依赖**。要么补上"管道逻辑可被 EF 调用"这一层（= 重开已否决的路），要么**明确降级为"仅互补触发、不声称独立"**。

**② §9.2 的两条 SLO 与现有代码阈值直接冲突，指标自相矛盾。**

| SLO（§9.2） | 代码现状 | 冲突 |
|---|---|---|
| 状态收敛延迟 **≤5min** | `STALE_LIVE_MAX_SEC = 3 * 3600`（[sources.js:1220](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/sources.js#L1220)）→ 超时降级路径**最短 3h** | 只有"比分达 BO 上限"硬判据路径能到 5min；**降级路径物理上不可能 ≤5min** |
| 快照年龄 **≤24h** | `SNAPSHOT_MAX_AGE_SEC = 7 * 86400`（[leagues.js:60](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/pages/leagues/leagues.js#L60)）→ 代码容忍 **7 天** | 一个是"目标值"、一个是"降权阈值"，**口径不同却用同一个名字**，会被误判为达标 |

⇒ 必须拆成：**收敛延迟（硬判据路径）≤5min** + **收敛延迟（降级路径）≤3h**；并把"快照年龄"明确为"目标值 24h / 降权阈值 7d"两个量。

**③ 「重复卡率目标 = 0」存在原理性不可达。**

`series_id` 缺失时，`patchNullSeriesId` 靠"队名 + 时间窗"软关联；而**同日同两队的两场不同比赛**（BO2 循环赛 / 同一天双败赛程）在该信号下**原理上不可区分**。设 0 等于要求启发式 100% 正确。
⇒ 目标应改为「**≤ 基线 + 全部例外可解释**」，并配合 `P0-A` 的 `identitySource` 标注逐条归因。

**④ `P0-C` 客户端探针**不能替代**开发者告警**。
"我的"页显示"数据更新时间"解决的是**让用户看见**；客户端请求失败时该时间**不会更新**，开发者依然**不知情**。⇒ 它只补了 C.3 漏洞 1 的一半（消费侧），**告警侧仍是空的**。
