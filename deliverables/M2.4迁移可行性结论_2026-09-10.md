# M2.4 剩余 action 迁移结论（2026-09-10 实测）

> 起因：收尾清单第 ⑦ 项「M2.4 剩余 7 个 action 迁移」。本次做了**可行性实测**，结论与预期不同。

---

## 一、结论速览

| action | 能否迁 EF | 原因 |
|---|---|---|
| `liquipediaScheduledMatches` | ❌ **不能** | LP 出口被限流（见下） |
| `liquipediaLeagueMeta` | ❌ 不能 | 同上 |
| `liquipediaTeamLogo` | ❌ 不能 | 同上 |
| `liquipediaListTournaments` | ❌ 不能 | 同上 |
| `getLiquipediaUpcoming` | ❌ 不能 | 同上 |
| `getUpcomingSchedule` | ⚠️ 待评估 | 依赖 STRATZ/多源，非纯 LP |
| `health` | ✅ 可迁 | 无 LP 依赖，但价值极低 |

**净结论：M2.4 在 LP 相关 action 上已到架构边界，不是「待办」而是「死路」。**

---

## 二、实测证据（推翻旧假设）

### 旧假设（2026-09-09 记录）

> 「Supabase 出口被 LP **Cloudflare 挑战页**拦截」

### 实测结果（2026-09-10）

```
请求 action=liquipediaFetchRawWikitext，pageName=ESL One Hamburg 2018（未缓存）

HTTP 500  7262ms  ERR=Liquipedia 429
```

**关键差异**：错误从「Cloudflare 挑战页」变成了 **HTTP 429（Too Many Requests）**。

→ 说明 Supabase 出口 **能到达 Liquipedia**（请求已抵达 LP 并被其限流），
只是 **Supabase 共享出口 IP 被 LP 持续限流**。

### 排除「自己打自己」

为排除「是我连续测试触发的限流」，做了对照实验：

```
静默 60 秒（限流窗口过期）→ 只发 1 次请求
  HTTP 500  7262ms  ERR=Liquipedia 429     ← 仍然 429
```

单次、静默 60s 后仍 429 → **是 IP 级持续限流**（Supabase 免费版出口 IP 被大量项目共用，
该 IP 在 LP 侧已超配额）。**无法从我们这侧修复**。

## 三、为什么「迁移不难」但「迁移无意义」

### 技术上：迁移本身很简单

客户端**已有**完整的「EF 抓 raw wikitext + 本地解析」路径：

```
utils/liquipedia.js  fetchScheduledLocal(slug, cacheKey)
  ├─ fetchPageWikitext(slug)  → cloudProxy.liquipediaFetchRawWikitextProxy  → EF ✅ 已迁
  └─ LiquiParse.parseScheduledMatches(wikitext)  → 客户端纯函数（G14 双源覆盖）
```

也就是说：**解析逻辑早就在客户端**，EF 只需吐 wikitext。把 `fetchScheduledLocal`
提为主路径即可完成「迁移」。

### 但为什么不做

| 问题 | 说明 |
|---|---|
| EF 只能吃表缓存 | 未命中时现抓 → 429 → 500 → 回落到云开发（白付 7s 延迟） |
| 表谁来灌 | 设计上是 **GH Actions**（`sync-liquipedia.yml`），但**仓库无 git remote → 永不执行** |
| 灌了也收益有限 | 客户端本就有 SWR 缓存（6h stale）；云函数侧也有 24h 缓存。冷启动才有差别 |
| 风险 > 收益 | 切换主路径后，未缓存赛事反而多付 7s 429 超时再回落 |

**一句话**：把 LP 请求从云开发搬走，前提是「有另一个能抓 LP 的出口」——
而 Supabase 出口被限流、客户端 wx.request 禁设 UA 必被拦。
**目前唯一能稳定抓 LP 的出口就是微信云函数本身。**

## 四、对 ⑥ GitHub 仓库 的影响（重新评估）

原本认为 ⑥ 是「解锁 LP 自动同步」的收益项。实测后修正：

- ✅ 仍值得做：让 `lp:w:*` 表保持新鲜，使 EF 缓存路径可用
- ❌ 但**不足以**据此迁移 `liquipediaScheduledMatches`
  （表只能覆盖已知赛事页，冷门/新赛事必然 miss → 仍要回落云开发）

→ ⑥ 的定位从「迁移前置」降级为「**可选优化**」。

## 五、🎯 意外收获：修掉一个潜伏的真实缺陷

本来是评估迁移，结果在验证「EF 会不会返回旧数据」时**挖出一个真 bug**。

### 缺陷：EF 抓取漏了 `redirects=1`

| 抓取方 | 是否带 `redirects=1` |
|---|---|
| 云函数 `aggregation`（L549） | ✅ 有 |
| 客户端本地 `liquipedia.js`（L251） | ✅ 有（2026-07-28 专门修过这个 bug） |
| **EF `liquipedia-proxy`（L68）** | ❌ **漏了** |

而 EF 的注释还写着「与云函数同参数」—— 实际早已不成立。

### 实测证据

LP 上不少赛事主页面是**重定向页**：

```
The International 2026  →  36 字节，内容 = "#REDIRECT [[...]]"
```

### 后果链（为什么严重）

```
EF 抓到 36B 重定向文本
  → 写入 lp:w:<slug>（TTL 24h）
  → 读取端 getAnyCache **不过滤 expire_at**（v8.22 有意设计「表里有就用」）
  → 该 key **永久被污染**（永不自愈）
  → 客户端 parseScheduledMatches 找不到任何 {{Match}}
  → 赛程/对阵**静默空白**
```

**当前状态：潜伏** —— EF 出口被 LP 限流（429），极少写入，所以尚未发作。
一旦限流解除，就会静默发作，且症状与之前那串「首页赛程缺失」高度相似、极难定位。

### 已修复（2026-09-10，EF 已部署）

1. **补 `redirects=1`** —— 与云函数/客户端同口径
2. **新增 `isUsableWikitext()` 双向防线**（读写两侧共用同一判定）：
   - **写侧**：不可用文本不返回、不入缓存
   - **读侧**：不可用则视为 miss，继续现抓；仍失败返回 null 由客户端回落
   - 这样**即便表里已有修复前写入的污染条目，也不会再被读出**
3. 判定覆盖：空/非字符串/纯空白/`#REDIRECT` 占位（<500B）→ 不可用；正常内容（含正文提及 redirect 字样）→ 可用

**验证**：判定表 9/9 通过；部署后回归 `The International 2026` / `DreamLeague Season 24` /
`PGL Wallachia Season 9` 均仍 `source=cache` 且内容完整（30214B / 32137B / 21286B）。
