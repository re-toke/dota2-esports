## 1. 与方案 §9.2 的差异（4 处修订，均有依据）

| # | 方案原口径 | 修订后 | 依据 |
|---|---|---|---|
| 1 | 状态收敛延迟 ≤ **5min** | 拆两条：**硬判据 ≤5min** / **降级路径 ≤3h** | `utils/sources.js` 的 `STALE_LIVE_MAX_SEC = 3*3600` ⇒ 降级路径**物理上不可能 ≤5min**，同口径自相矛盾 |
| 2 | 快照年龄 ≤ **24h** | 拆两量：**目标 24h** / **降权阈值 7d** | `pages/leagues/leagues.js` 的 `SNAPSHOT_MAX_AGE_SEC = 7*86400` —— 一个是目标值、一个是降权阈值，**同名不同义**会被误判达标 |
| 3 | 重复卡率目标 **0** | 严格键 **0** + 宽松键**只建基线** | 同日同队两场（BO2 循环 / 同天双败）在"队名+时间窗"信号下**原理不可分** ⇒ 设 0 等于要求启发式 100% 正确 |
| 4 | 指标落点 = 本机日志 + 「我的」页 | **写入方改为 CI**（见 §3） | `curation_meta` 的 RLS 是 `anon_read_meta`（**只读**）⇒ **客户端无写权限**；而 CI 持有 `SUPABASE_SERVICE_KEY` |

另：`heuristicRate`（启发式降级率）**先只建基线不设阈值** —— 它依赖 `P0-A` 引入的 `identitySource` 字段，字段未上线前计为「未采集」，**不虚报为 0%**。

## 3. 采集 / 消费路径（**修正了方案的一处不可行设计**）

```
客户端  pages/index  ──► diagnostics.computeCardMetrics  ──► 一行汇总日志（常开）
CI      scripts/ops/*   ──► 同一纯模块算指标 ──► 写 curation_meta（SERVICE_KEY）
客户端  「我的」页      ──► 读 curation_meta（anon 只读）──► 展示"数据更新时间 / 降级率"
```

★ **为什么写入必须走 CI**：`supabase/migrations/001-init.sql` 的 `curation_meta` 只有 `anon_read_meta` 策略
（只读）；客户端**无法**写入，也不该把 admin token 打进包里。CI 的 `secrets.SUPABASE_SERVICE_KEY` 已具备写权限
（`sync-upcoming.yml` 正在用同一凭据）。**且指标本就是 Node 侧跑同一套融合代码算出来的**，口径天然一致。
