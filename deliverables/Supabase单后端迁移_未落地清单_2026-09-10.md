**为什么 A 类最大的一块（通用 KV）没迁 —— 有个真实约束**：

`follow_profile_*` 能走 EF，是因为它**按 openid 分桶**、可用 JWT 鉴权。
而通用 KV（搜索索引、热门战队等）是**公共数据、不带用户身份**：
- 客户端直连 PostgREST 读 → 需要 `aggregation_cache` 对 anon 开放 → **表里同时存着用户画像**，会泄漏
- 客户端直连写 → 需要 service key → **绝不可放客户端**

→ 所以通用 KV 要迁，**必须新增一个 EF**（如 `cache-kv`，读开放、写校验），无法靠直连解决。
这是它能一直留着的真实原因，不是遗漏。

## 四、建议的补齐顺序

### P0（1 项，真问题 —— 一致性/数据丢失，非合规）

> ⚠️ **先说一处自我纠正**：本清单初稿曾断言「`cloudCache` 回退路径绕过 `cloudSync.isEnabled()` 守卫，
> 未开启同步仍可能把画像写到云开发」。**核查后此判断为错** ——
> 逐条验过所有 `follow_profile_*` 读写调用点，**全部有同步守卫**：
> `saveFollowProfile`（`subscribe.js:594`）✓ / `syncSubStatus`（`:545`）✓ /
> `restoreFollowFromCloud`（`:635`）✓ / `restoreSubFromCloud`（`:550`，且在 guarded 函数内）✓
>
> 核查过程反而发现了**另一个真问题**（见下）。

**★ 回退写入是「写进黑洞」：写进云开发，但读取端永远读不回**

```
写：EF 失败 → cloudProxy.call('setCached', ..., 'follow_profile_<openid>')
              → 落到【微信云开发 DB】

读：cloudCache.getCached(key)
      → _sbFollowGet(key)（EF → Supabase Postgres）
      → .catch(local)            ← 只 catch 异常，**不查云开发**
      → 且 EF 正常返回 null（Supabase 里确实没有）也不会去查云开发
```

**结论**：回退写入的数据**没有任何读取路径能取回**。
即「EF 失败 → 回退写云开发」这个设计**只提供心理安慰**，实际等于**静默丢数据**：
用户以为保存成功了（接口返回 ok），但下次读是空的。

**影响面**：EF 偶发失败时，用户的关注/提醒策略变更会**静默丢失**（无任何提示），
且**不会自愈**（本地有兜底副本，但换机/清缓存后彻底没了）。

**修法（二选一）**：
- **A（推荐，最小改动）**：回退写入失败时**明确返回 `ok:false`**，让上层提示「同步失败，可重试」——
  即**把静默失败变成显式失败**（与刚修完的 `disable()` 报假成功是同一类问题的另一面）
- **B（彻底）**：读路径补一次云开发查询（`getCached` 失败/未命中时也查云开发）——
  但会让读取变慢且引入双后端读依赖，**不推荐**

### P1（2 项，让迁移真正收尾）

1. **新增 `cache-kv` EF**，接管通用 KV（`getCached`/`setCached` + 搜索索引 + 热门战队）——
   这是剩余最大的一块，做完后**通用缓存不再依赖云开发**
2. **GitHub 仓库 + Secrets** → 让 `sync-liquipedia.yml` 能跑，LP 表保鲜

### P2（3 项，清理与收尾）

3. 迁 `getExperiments` / `getCuration` / `health`（低难度，补齐后仅剩 LP + 回退链路）
4. **决定 `smart-reminders` 的去留**：接线（补服务端推送）或 **明确不接线并删除 EF**（避免「部署了却没用」的认知负担）
5. 核对 `cron-job.org` 双 Job 配置

## 五、迁移终点的准确描述

做完 P1 后，架构会是：

```
Supabase EF（数据面）          微信云开发（仅剩）
├─ opendota-proxy              ├─ liquipedia*（7 个，架构边界）
├─ steam-proxy                 ├─ 回退链路（4 个，设计如此）
├─ stratz-proxy                └─ 服务端/管理（4 个）
├─ liquipedia-proxy（读表）
├─ haglund-proxy
├─ bundle-aggregator
├─ cache-kv（新增）
├─ wechat-auth
├─ follow-profile
└─ subscribe-send
```

**即「数据面走 Supabase，LP 抓取与回退留在云开发」** —— 这个终态是**可达成且合理**的；
LP 那 7 个不是没做完，而是**实测不可迁**（已出结论文档）。
