## 3. 设计原则

1. **单一事实源**：同一语义只允许一个字段（数字 vs 数组、状态 vs 赛期），跨源冲突用**显式优先级表**，不再靠 `Object.assign` 隐式覆盖。
2. **结构与内容分离**：对战表的「轮次/分区/槽位」来自 wikitext 骨架，「对阵双方/比分/时间」来自 Match 页与 OpenDota；两者独立失败、独立降级。
3. **数据可解释**：每块数据标注来源与更新时间；冲突时展示“以谁为准”（而非静默取舍）。
4. **先准确、再美观**：UI 改造不得掩盖数据问题；占位/待定必须有明确视觉语义。
5. **零新依赖优先**：小程序无 DOM；不引入前端 bracket 库、不引入 HTML 解析依赖，只借鉴其数据模型与算法。
6. **可回退**：淘汰赛表独立数据入口，失败时回退到「小组积分 / 小组赛战绩」，不白屏。

### 4.2 「赛事信息」重构（合并溯源 / KPI / 概述 / slug）
**目标**：一个卡片说清“这是什么赛事、在哪、何时、多少钱、谁办的、几支队、现在什么状态”。

```
┌ 赛事信息 ────────────────────────────────┐
│ EWC 2026        [S 级] [进行中]           │
│ 2026-07-08 ~ 2026-07-19 · 利雅得 · 24 队   │
│ 奖金 $2.0M · BO3/BO5 · 主办方 Esports F.   │
│ 数据：Liquipedia + curation · 更新于 2h 前 │
│ [展开：赛制说明 / 来源明细 / LP 链接]      │
└─────────────────────────────────────────┘
```
- **合并为一张卡**：卡内 2 列 key-value（赛期/地点/奖金/参赛队数/赛制/主办方）；底部一行来源 + 更新时间 + 展开。
- **去重规则（明确）**：分级与状态**只在这张卡内展示一次**；头部只保留赛事名 + 关注按钮（避免与卡片重复）。
- **赛事概述（已锁定）**：**结构优先 + 可选摘要**。默认不渲染段落；仅当 `metadata.format` 长度 >14 字符时，在**展开区**生成一句「赛制说明」（如“循环小组赛 Bo2 + 突围赛 Bo3 + 单败淘汰”），不复述 KPI 网格中已有的事实。若日后需要“介绍感”，用 curation 可选 `summary`（人工撰写），不用模板拼接。
- **赛期唯一**：以 `eventWindow` 为唯一来源；缺失显示「待公布」，不显示 `? ~ ?`。若要把 LP 日期纳入链（§5.1 的优先级表），**必须先改 `mergeEventPeriod` 的入参**，否则文档口径与代码不一致。
- **币种修正**：`$→USD / €→EUR / £→GBP / ¥→CNY`；展示做单位缩写（≥1M 显示 `$12.5M`），原始值放在展开区（小程序无 tooltip）。
- **颜色 token 化**：分级置信度用 **`--status-ongoing`（高）/ `--status-upcoming`（低）**；分级 S/A/B/C 用 `--tier-*-text`；星标用 `--dota-gold` / `--text-3`；info 图标用 `--text-2`；链接用现有品牌色 token。注意 `t-icon` 的 `color` 是内联属性，建议改用 class 或样式变量覆盖，避免 `var()` 在属性里失效。

### 4.3 「对阵」与「参赛队伍」UI
**对阵（matches）**
- 保留三段式（LIVE / UPCOMING / RECENT），卡片改为两行紧凑结构：① 阶段/轮次 + 时间 + BO；② 两队 Logo/名 + 比分 + 胜者高亮；小场比分保留现有就地展开。
- **来源 chip**：需在 P1 的合并流程中**新增 provenance 字段**（当前 series 没有来源标记，只有 `_aggregated`）。建议枚举 `od` / `lp` / `od+lp`，不要用语义含糊的“聚合”。
- TBD 一方统一显示「待定」+ 虚线描边，不参与胜负高亮；已结束对局显示 `W.O.`（弃权）标记（现有 `aForfeit/bForfeit` 已有，改为统一文案）。
- 「仅看淘汰赛」筛选：**直接复用现有 `s.stageKey`**（`playoff` / `grandFinal`，见 [sources.js#L1602-L1607](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/sources.js#L1602-L1607)），零新增字段。

**参赛队伍（teams）**
- 合并优先级：**LP participants > curation 数组 > 比赛推导**。
- 去重：`team_id` 优先，其次规范名；可复用 `sources.dropDuplicateNameIds(teamMap, teamCount)`，但**签名是 id→名映射并返回待丢弃 id 数组**，需先构造映射，不能直接喂队伍数组。
- **group 推导**：LP 未提供 group，可用 `parseGroupStandings` 的「组名 → 队名」映射反查（TI/EWC 都能命中）；`region` 无 LP 来源，只能取 curation 或留空。

- UI：按 Group 分组（有分组时）+ 搜索框 + 队伍 chip；补「直邀/预选/待定」徽标（`status` 已可用）。
- **数量口径**：KPI 的参赛队数与队伍 Tab 的 `participantsList.length` 必须统一取 `participantsCount`，否则会出现 16 vs 24 两个数字。

## 5. DM 方案 · 数据模型与准确性

### 5.1 统一 `LeagueMeta` 模型
```js
{
  canonical, tier, status, start, end,          // 唯一事实源
  location, organizer, format,
  prizePool: { amount, currency, display },     // 详情页内部派生对象
  participantsCount,                            // 数字，供 KPI
  participants: [{ id, name, group, region, status }],  // 数组，供列表
  sources: [{ key, fields, updatedAt }],
}
```
- **禁止类型复用**：`participantsCount` 与 `participants` 分离。**落地注意**：`metadata` 结构同时被 `leagues.js` 列表页消费（`list[].prizePool` 仍是字符串），所以：
  - `prizePool` 对象只在**详情页内部派生**，不改 `buildCurationFallback` / `parseLeagueMetadata` 的返回形状；
  - `participants` 改为数组后，所有 `{{metadata.participants}}` 模板引用（wxml L69/L90、js L2680）统一改为 `participantsCount`。
- **合并优先级表**（写入代码常量，不再 `Object.assign` 隐式覆盖）：
  | 字段 | 优先级（高→低） |
  |---|---|
  | 展示名 | curation canonical > 多源共识 > OpenDota |
  | 赛期 | curation 完整周期 > **LP 完整周期（需新增入链）** > OpenDota 真实窗口 |
  | 奖金 | LP > curation（保留币种与原始文本） |
  | 参赛队 | LP 数组 > curation 数组 > 比赛推导 |
  | 状态 | 由赛期 + 比赛实况推导（不再读取第二来源） |

### 5.2 系列赛 `Series` 归一模型
- 现有合并在 `league-detail.js` 内跨 800+ 行，规则（TBD 去重、占位覆盖、BO 推断、phase 归一）散落。
- **模块落位（P1a~P1b-2 已落地）**：`utils/seriesNormalize.js`（纯函数）提供 `scoresOf` / `isDecided` / `normalizeTerminal`、`isTbd` / `normalizeTeamNameForDedup` / `dedupeKey` / `fuzzyMatchName` / `placeholderCoveredByReal`、`hasKickoffProof` / `isSeriesEndedByBoLimit` / `filterLiquipediaCardsByWindow`、`normalizeOpenDotaSeries`（注入 `groupSeries`+`fmt`）/ `mapLiquipediaCards`、`addSource` / `unionSources`、`validateSeries`、`MERGE_PRIORITY`。**P1b-3**：页面只剩「吸收 / BO 上下文 / 分段排序」编排，可按需再收敛。
- 输出：
  ```js
  { key, stageKey: 'group'|'playoff'|'grandFinal', roundLabel, phase, start, bo,
    teamA:{id,name,tbd}, teamB:{id,name,tbd}, scoreA, scoreB, finished, walkover,
    matchIds, sources:['od','lp'], confidence }
  ```
  与现有 `s.stageKey` 对齐，不另造 `stage`。
- 合并优先级：**LP 赛程/比分（淘汰赛权威） > OpenDota 结果（小组赛权威） > 聚合推断**；冲突时保留双方分数并标 `conflict`，UI 用“以 LP 为准”提示。
- 校验不变量（单测）：
  - `score <= bo`；`finished` 与比分/BO 一致；
  - 含 TBD 的场次**不得**判 live；
  - 同赛事同两队同日不得出现两条未合并记录（除 TBD 占位）；
  - 胜者唯一（弃权按 `walkover` 定向）。

### 5.3 参赛队伍准确性
- 用 explorer `teams`（`team_id, name, logo_url`）批量回填占位名（`loadStandings` 已有同款逻辑，可抽公用函数复用）。
- 以规范名做二次去重，但**保留原始 id 映射**避免误删。
- group 用 §4.3 的组表反查；region 无源则留空，不猜。
- 单测覆盖已知案例：EWC 2026（meta 16 / 实际 24）、Zero Tenacity 双 id、`Team {id}` 占位。

> 页面级空槽统计：EWC 2026 共 16 个 `{{Match}}` 其中 15 空；PGL S9 共 14 个全空；TI 2026 `/Main Event` 共 14 个其中 13 空。

**四条结论（决定 P3 方案）：**

1. **wikitext 只有结构，没有内容**：`{{Bracket}}` 里的 `{{Match}}` 基本全空 → 现有 `parseBrackets` 在 EWC Playoffs 上直接产出 **0 个 bracket**（`rounds.length === 0` 被丢弃），其余也只出 1 场。原定 A/B 路线（基于 wikitext 连线/解码 type）**不可能得到对战表**。
2. **内容在 `Match:ID_<bracketId>_R##-M###` 页**：形如 `{{MatchPage|opponent1={{TeamOpponent|…}}|opponent2=…|date=…|map1={{ApiMap|matchid=8900771154}}…}}`，单页约 380 字节。页面名的 `R##-M###` 正好对应 wikitext 的 `R#M#`（`R1M1 → R01-M001`），可直接映射槽位。
3. **分区/轮名不需要解码 `type`**：渲染 HTML 的 `.brkts-header` 给出权威文本（`Upper Bracket Quarterfinals` … `Lower Bracket Final`、`Grand Final`），且 wikitext 的 HTML 注释（`<!-- Upper Bracket Semifinals -->`）同源。`type`（`8L4D-4Q` / `8U4L2DSL1D`）编码复杂且样本少，不值得作为主依据。
4. **`R#` 在 Upper/Lower 共用编号**（PGL/TI 实测）：`R1M1-4` = Upper QF，`R1M5-6` = Lower R1，`R4M1` = Upper Final，`R4M2` = Lower Final，`R5M1` = Grand Final。**按 `roundNo` 分组会把 Upper/Lower 合成一轮**（现有实现的真实缺陷）→ 必须按「注释/表头」分组。

### 6.2 数据模型（S 路线）

```js
{
  bracketId, type, stageLabel, source: 'lp', updatedAt,
  sections: [
    { side: 'upper'|'lower'|'final'|'third'|'qualifier',
      rounds: [{ no, label }] }
  ],
  matches: [{
    key: 'R01-M001', side, round: 1, slot: 1,
    team1: { id, name, short, logo, tbd }, team2: { ... },
    score1, score2, winner: 'A'|'B'|null,
    bo, startTime, finished, walkover,
    matchIds: [8900771154, ...],     // 来自 ApiMap
    seriesKey,                       // 关联页面现有 series（比分/跳转）
  }]
}
```

- **不再使用单条 `next`**：双败中同一场的胜者与败者要分别去 Upper/Lower，`next:{matchId,slot}` 表达不了。布局只需要 `side + round + slot`：同侧 `slot` 按 `ceil(n/2)` 归并到上一轮；降级线由「Upper 第 r 轮 → Lower 对应轮」推导（用 header 文本建映射，见 §6.5）。
- `side` 来源：注释/表头文本分类（`upper` / `lower` / `grand final` / `third place` / `qualifier`）。
- **保留 `slotNo` 与 `comment`**，这是现有解析器必须补的两处（当前在输出前 `delete`）。

### 6.3 路线评估（含已否决项）

| 路线 | 结论 | 理由 |
|---|---|---|
| **L1** wikitext 同 bracket 配对（原 A） | ❌ 不可行 | 槽位为空，配对结果为空表 |
| **L2** 解码 `type` 补 Upper→Lower（原 B） | ❌ 不需要 | `type` 至少 3 种编码（`8`、`8L4D-4Q`、`8U4L2DSL1D`），且分区可由 header 文本直接得到 |
| **L3** 抓渲染 HTML（原 C） | ⚠️ 降为交叉校验 | 单节 HTML 350~750KB；EF 现抓当前 500（§9）；仅 CI 侧可选做比分校验 |
| **S** 结构(wikitext) + 内容(Match 页) | ✅ **采用** | 3 个赛事 4 个 bracket 填充率 88%~100%；单次批量请求；无新依赖；字段稳定 |

### 6.5 渲染方案（WXML/WXSS，不用 Canvas）

- 结构：`scroll-view(scroll-x)` → 内部绝对定位画布；**必须显式设置 canvas 宽高与 `scroll-view` 高度**，否则绝对子元素不撑高、区域塌陷。
- 尺寸：`CARD_W=280rpx`、列间距 `64rpx`、`H=132rpx`（104rpx 只能放两队名，放不下 BO/时间）、`G=24`。首轮 `y = i*(H+G)`；后续轮 `y = 平均(两条来源中心)`。
- 连线：每条边两段 `view`（水平 + 垂直），`2rpx` 边框，颜色 `--text-4`；已确定路径 `--dota-gold`。
- 分区：Upper / Lower 上下排列；Grand Final 只需一列，但 **y 由 Upper 决赛与 Lower 决赛中心平均得到**（不要固定居中，否则降级线断开）；Third Place 单独一列。
- 表头：轮名随列滚动（列头），**不做 `position: sticky`**（横向 scroll-view 内的纵向 sticky 在真机上不稳定）。
- 卡片：队名（超长省略）+ 短名兜底 + 比分 + 胜者高亮 + BO/时间；TBD 虚线；LIVE 呼吸点；点击 → 有 `seriesKey` 跳 match-detail，否则 toast「未开赛/待定」。
- 移动端：默认 2 列（`280*2+64=624`，加页边距 48 仍 < 750），右侧加渐隐/箭头提示可横向滚动；「显示赛程」开关控制时间行；「只看当前轮」用 `scroll-into-view` 定位列 id。
- 性能：布局在 JS 纯函数预计算坐标数组（单位 rpx），WXML 只 `wx:for`；30 场规模无压力。

## 9. 风险与对策

| 风险 | 对策 |
