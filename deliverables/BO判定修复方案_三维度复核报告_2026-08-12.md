## 二、合理性复核

### 2.1 ✅ 根因识别准确

通过抓取 TI 2026 Group Stage 真实 wikitext 验证，确认 6 级信号全部失效的根因成立：
- 页面无 `==Format==` 段（采用瑞士轮 `{{Matchlist}}` 格式）
- 44 个 `{{Match}}` 模板全部无 `bestof` 字段
- 无 infobox、无 "Bo3" 文本

### 2.2 ⚠️ "map 槽 = BO 结构铁证"表述过度绝对

报告原文称 map 槽是"BO3 的结构铁证"。实测验证后发现此表述需降级：

**实测事实**（TI 2026 Group Stage wikitext）：
- 44 个 Match 模板**全部**有 `map1` + `map2` + `map3`（无 map4/map5）
- 每个 Map 模板为**空壳**（`{{Map|team1side=|t1h1=|...|winner=}}`，所有字段值为空）
- `parseMatchFields` 的 `_mapCount` 统计**非空值**（`if (!_mv) continue`），因 `{{Map|...}}` 字符串非空 → `_mapCount=3` → 方案 A 有效

**但不可推广为"铁证"**的原因：
- map 槽预留是 **Liquipedia 编者习惯**，非 API 契约保证
- 不同编者可能：BO3 横扫 2:0 只填 map1+map2（map3 省略）→ `_mapCount=2` → 误判 BO2
- 或预留 map4（"如果需要"）→ `_mapCount=4` → 映射表无 4 → S2b 不触发

**修正建议**：将"铁证"改为"**强启发式信号**"，并补充适用前提：编者按赛制完整预留 map 槽。

### 2.3 ✅ S2b 信号优先级位置合理

方案 A 将 mapSlots 信号插入 S2（赛制文本）之后、S3（series_type）之前。合理性：
- mapSlots 来自 Liquipedia（与 S1/S2 同源），优先于 OpenDota 信号（S3-S5）符合双源分层
- 弱于 S2 文本信号（parseBoFormat 是编者显式声明，mapSlots 是结构推断）

### 2.4 ✅ 方案 B curation 补充合理且即时

curation boFormat 是人工策展的显式声明，优先级最高（走 S2 信号），立即生效无需代码发布。对 TI 2026 开赛在即的场景是最佳即时补丁。

### 2.5 ⚠️ 方案 A+B 信号优先级未定义冲突场景

若 curation 声明 `boFormat.group='BO3'` 且 mapSlots=5（编者预留了 5 槽但实际 BO3），S2 先用 boFormat=BO3 返回，mapSlots 不触发。此场景无冲突（S2 优先）。但若 curation 缺失而 mapSlots 与实际赛制不符（如 5 槽但 BO3），方案 A 会误判 BO5。

**修正建议**：方案 A 代码注释补充"mapSlots 信号弱于 curation/parseBoFormat，仅作 S2 失效后的结构推断兜底"。

## 三、逻辑性复核

> **[元复核补注 · 2026-08-12]** 本章节列出的 5 项逻辑性问题均**成立且正确**，但发现一个**未提及的根本性问题**：方案 A 描述的 `mapSlots` 字段在当前代码中**完全不存在**——`parseMatchFields`（`liquipedia-parse.js` L556-665）的返回对象字段为 `{team1Name, team2Name, score1, score2, walkover, startTime, boType, boDeclared, finished, phase, matchIds}`，**无 `mapSlots`**；`_mapCount` 仅在函数内部用于判 finished，未输出。`resolveBoType` 入参 `series` 同样无 `mapSlots`。因此方案 A 不是"改 3 文件"，而需新增贯穿链路：`liquipedia-parse.js` 输出 → 云函数传输 → `liquipedia.js` 接收 → `groupSeries` 注入 → `resolveBoType` 消费 + 云函数重部署。**详见 §六.2**。

### 3.1 🔴 [须修] consistent() 对 UPCOMING 形同虚设

**问题**：方案 A 代码 `if (slotBo && consistent(slotBo)) return finalize(slotBo)` 中的 `consistent()` 对 UPCOMING 卡恒返回 `true`，守卫无实质作用。

**实测 `consistent()` 逻辑**（[sources.js#L1176](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/utils/sources.js#L1176)）：

```javascript
const isFinished = phase === 'recent' && pending === 0 && (played > 0 || (scoreA + scoreB) > 0);
const consistent = (bo) => {
  if (!BO_MAX[bo]) return false;           // BO_MAX['BO3']=3 → OK
  if (played > BO_MAX[bo]) return false;   // UPCOMING: played=0 → 不触发
  if (maxScore > BO_WIN[bo]) return false; // UPCOMING: maxScore=0 → 不触发
  if (isFinished) { ... }                  // UPCOMING: isFinished=false → 跳过终局校验
  return true;                              // ← 恒返回 true
};
```

**影响**：若编者预留了 5 个 map 槽但实际赛制是 BO3，mapSlots=5 → 映射 BO5 → `consistent('BO5')` 返回 true → 误判 BO5。TI 2026 不受影响（3 槽对应 BO3 正确），但通用场景有风险。

**修正建议**：方案 A 不应单独依赖 `consistent()` 守卫。可增加 map 槽数与 `BO_MAX` 的合理性校验，或明确文档化"mapSlots 信号仅在 S2 全失效时兜底，接受其启发式性质"。

### 3.2 🔴 [须修] mapSlots 统计逻辑与方案描述不一致

**问题**：`_mapCount` 当前统计的是**值非空**的 map 槽（`if (!_mv) continue`），而非**字段存在**的 map 槽。

**场景差异**：

| 编者写法 | `fields['map1']` 值 | `_mapCount` 统计 | 方案 A 效果 |
|---------|---------------------|------------------|------------|
| `\|map1={{Map\|...}}` | `{{Map|...}}`（非空） | ✅ 计入 | ✅ 有效 |
| `\|map1=`（空值） | `''`（空字符串） | ❌ 跳过 | ❌ 失效 |
| 不写 `\|map1=` | `undefined` | ❌ 跳过 | ❌ 失效 |

TI 2026 实测为第一种（`{{Map}}` 空壳，字符串非空）→ 方案 A 有效。但其他赛事若编者用 `\|map1=`（空值无 Map 模板），方案 A 静默失效。

**修正建议**：方案 A 的 `mapSlots` 统计应改为检测**字段是否存在**（`_mapKeys[_mi] in fields`），而非**值是否非空**：

```javascript
// 修正版：统计字段存在性（而非值非空）
var _mapCount = 0;
for (var _mi = 0; _mi < _mapKeys.length; _mi++) {
  var _key = _mapKeys[_mi];
  if (_key in fields && fields[_key] !== undefined) {  // ★ 字段存在即计入
    _mapCount++;
  }
}
```

### 3.3 ⚠️ [建议] map 槽→BO 映射表缺 4 的处理

方案 A 映射表 `{ 1:'BO1', 2:'BO2', 3:'BO3', 5:'BO5' }` 不含 4。注释说"4 槽是 BO3 的预留第 4 局（罕见），保守判 BO3"，但映射表未体现。

**修正建议**：补充 `4: 'BO3'`（保守降级）：

```javascript
const slotBo = { 1: 'BO1', 2: 'BO2', 3: 'BO3', 4: 'BO3', 5: 'BO5' }[series.mapSlots];
```

### 3.4 ✅ S2b 插入位置正确

方案 A 将 S2b 插在 `fmtBo`（S2）之后、`st`（S3）之前，逻辑正确：mapSlots 来自 LP，与 S1/S2 同源，应优先于 OpenDota 信号。

### 3.5 ✅ P0-1 isDraw 重算逻辑正确

```javascript
series.isDraw = (bo === 'BO2' && isFinished && (series.scoreA === series.scoreB));
```

- `isFinished` 限定仅 RECENT 阶段 → LIVE/UPCOMING 不误标
- `bo === 'BO2'` 限定仅 BO2 赛制 → BO3/BO5 的 1:1 进行中不误标
- 逻辑正确，通过

## 四、合规性复核

### 4.1 ✅ 不违反数据源 API 限制

- mapSlots 来自 Liquipedia wikitext 解析，不增加 API 请求
- curation boFormat 是本地配置，不涉及 API
- 均符合 OpenDota/Liquipedia 速率限制和 ToS

### 4.2 ✅ 符合"数据源独立验证"约束

- mapSlots 和 curation boFormat 均来自 Liquipedia，不依赖 Valve/OpenDota
- 符合 project_memory "数据源必须提供独立验证"约束

### 4.3 ⚠️ mapSlots 依赖 wikitext 模板格式（非 API 契约）

**风险**：map 槽预留是 Liquipedia 编者习惯，非 API 契约保证。若 Liquipedia 模板变更（如废弃 `{{Match}}` 模板的 map 槽字段），mapSlots 信号会静默失效。

**缓解**：方案 A 是 S2 失效后的兜底信号，失效时退化为 S3-S6（与当前行为一致），不引入新错误。但应在文档中标注此依赖。

### 4.4 ⚠️ [须确认] curation boFormat 与 fetch:upcoming 流程的同步

**风险**：project_memory 约束"upcoming-local 数据必须存储在 JS wrapper + JSON + 自动同步 via npm run fetch:upcoming"。若 `boFormat` 仅加在 `curation.js` 而 `fetch:upcoming` 流程不同步，新赛事的 boFormat 会缺失。

**待确认**：`fetch:upcoming` 是否读取 curation 的 boFormat 字段？若否，需扩展同步流程。

### 4.5 ✅ 符合"保守只漏判不误判"原则

- mapSlots 是强信号（3 槽→BO3 的误判概率极低）
- curation boFormat 是人工策展（可靠性最高）
- 均不会引入"误判 BO5 为 BO1"这类方向性错误

### 4.6 ✅ 不违反"新事件未在 curation 必须触发 alerts"约束

方案 B 为 TI 2026 显式添加 boFormat，符合"curation 必须覆盖高频赛事"的约束方向。新赛事未被 curation 覆盖时，方案 A 的 mapSlots 作为通用兜底。
