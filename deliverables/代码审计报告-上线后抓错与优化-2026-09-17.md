## 一、审计方法与判定标准

### 1.1 方法
1. **代码原文优先**：所有结论基于 Read 工具读取的当前工作树真实内容，不采信注释、不采信历史文档口径（本项目历史上多次出现"注释与实现不一致"，见 §四 4.9）。
2. **交叉验证**：对每个疑似缺陷，独立验证"写入侧 vs 读取侧""生产侧 vs 消费侧"两端，避免单点误判。
3. **可复现**：每条问题附带触发条件，工程上可构造用例复现。
4. **宁缺毋滥**：无法用代码证据支撑的，进 §五「待复核」而非结论区。

### 1.2 分级标准
| 级别 | 定义 |
|------|------|
| **P0** | 功能不可用、数据错误、或提审/合规风险。已上线环境下必现或高概率触发 |
| **P1** | 明显的体验损失、性能损失或可靠性下降；有明确触发条件，用户可感知 |
| **P2** | 隐患、可维护性缺陷、不一致；当前不一定触发，但会在特定条件下演变为 P0/P1 |

### 1.3 本次审计的特别视角（批判性）
本项目已迭代 v8.x 全系列、沉淀了大量铁律，**新增代码的质量高、历史 bug 修得也扎实**。因此本次批判聚焦三个"迭代自身引入的"盲区：
- **修复引入的新回归**（本次抓到 2 个，均为近期修复的副作用）
- **跨层契约不一致**（字段名/归一化/熔断策略在多层重复实现）
- **"注释声称"与"代码实际"的背离**（死分支、失效守卫）

### 【P0-2】🔴 隐私协议声明与实际采集行为矛盾（合规风险）

**位置**：
- 声明侧：`subpackages/detail/privacy/privacy.wxml:17-18`
- 实际侧：`pages/follow/follow.wxml:9,14`

**代码原文**：
```html
<!-- privacy.wxml:17-18 -->
<view class="para">本小程序 <text class="em">不收集</text> 用户的个人敏感信息，包括但不限于：</view>
<view class="list-item">· 不调用 wx.getUserInfo / wx.getUserProfile（不获取微信昵称/头像）</view>
```
```html
<!-- follow.wxml:9,14 -->
<button class="hero-avatar-btn" open-type="chooseAvatar" bindchooseavatar="onChooseAvatar">
<input class="hero-name" type="nickname" value="{{profile.nickname}}" bindblur="onNicknameBlur" />
```

**推导**：
- 协议括号内的结论句「**（不获取微信昵称/头像）**」与实际「通过 `chooseAvatar` 采集头像、通过 `type="nickname"` 采集昵称」直接冲突。
- 严格论：协议前半句列举的 API 名（`getUserInfo`/`getUserProfile`）**确实未被调用**——技术上不算错；但括号内是**结论性表述**，它对用户的承诺（不获取昵称/头像）与实际行为不符。
- 佐证：项目自审文档 `deliverables/隐私指引勾选核对表_2026-09-10.md` 已记录后台**必须勾选**「用户信息（微信昵称、头像）」，依据正是 `follow.wxml` 这两行——即**项目自身已认知到在收集，只是协议文案未同步**。

**第二处不一致**：`privacy.wxml:24-28` 的「本地存储数据」清单列了搜索历史 / 缓存 / 关注列表，**未列头像与昵称**，而 `utils/storageReset.js:50` 明确把 `user_profile`（头像/昵称）列为需清理的用户数据。

**影响面**：
1. 微信审核按「后台声明 ↔ 实际接口调用」自动比对，页内公开否认存在**虚假陈述**风险；
2. `app.json:60` 启用 `__usePrivacyCheck__: true` 时，若隐私声明与接口不匹配，可能触发 `errno 112` 导致 `chooseAvatar`/`nickname` 降级 → 用户昵称一键填充失效。

**触发条件**：提审自动比对；或正式版用户点击头像框（隐私接口校验分支）。

**修复方向（仅供参考）**：把 `privacy.wxml` 的否认句式改为「**在你主动设置头像/昵称时采集，仅用于本机展示与（开启云同步时）跨设备同步**」，并在本地存储清单补列 `user_profile`。注意：改动隐私文案需**同步后台隐私指引**，存在提审成本——建议与下一次版本提审合并处理。

### 【P1-3】🔴 首页翻周后日历无高亮、比赛流不切换

**位置**：`pages/index/index.js:355-361`

**代码原文**：
```js
onWeekShift(e) {
  const dir = e.detail.dir;
  const next = this._weekOffset + dir;
  if (next < -2 || next > 12) return;
  this._weekOffset = next;
  // 翻周后：若原选中天不在新周窗口，回到该周周一
  const days = this.data.weekDays;                    // ← 读取的是【旧周】的 weekDays
  if (days.length) {
    const inWindow = days.some((d) => d.key === this.data.selectedDateKey);
    if (!inWindow) this.setData({ selectedDateKey: '' });   // ← 恒不执行
  }
  this._buildWeekDays();                              // ← 用新 weekOffset 重建 days
}
```

**推导**：
1. `days` 取的是**旧周**的 7 天，而 `selectedDateKey` 正是用户**在旧周里选中**的日期 → `inWindow` **必然为 true** → 清空分支**永不执行**。
2. 随后 `_buildWeekDays()` 按新的 `_weekOffset` 重建日历，但 `selectedDateKey` 仍是旧周日期，而 `_buildWeekDays` 内部只在 `selected` 为**空**时才兜底为今天：
```js
// pages/index/index.js:328-333
let selected = this.data.selectedDateKey;
if (!selected) { selected = todayKey; this._selectedIsToday = true; }   // ← selected 非空，不兜底
this.setData({ weekDays: days, selectedDateKey: selected });
this._renderMatchFlow();
```
3. 结果：新周日历中**不存在**该选中日 → 无高亮；`_renderMatchFlow` 用旧 `dateKey` 过滤 → 比赛流仍显示旧日数据。

**触发条件**：点击周日历左右翻周，必现。

**修复方向（仅供参考）**：先 `this._buildWeekDays()` 重建，再基于**新** `weekDays` 判断并清空选中日；或直接把判断改为「选中日的周偏移是否等于新 `_weekOffset`」。

### 【P1-4】🔴 首页轮询定时器可泄漏、可叠加

**位置**：`pages/index/index.js:1405-1406`（置空）、`1450/1454`（重新武装）、`1460-1465`（停止）

**代码原文**：
```js
// L1402-1406
_startMatchPolling() {
  if (this._pollTimer) return;              // ← 依赖 _pollTimer 非空做"已启动"判据
  this._pollFails = this._pollFails || 0;
  const tick = () => {
    this._pollTimer = null;                 // ← tick 一开始就置空（进入异步窗口）
    ...
// L1450（成功路径）
      this._pollTimer = setTimeout(tick, delay);   // ← 异步回调重新武装
// L1460-1465
_stopMatchPolling() {
  if (this._pollTimer) {                    // ← 异步窗口内 _pollTimer===null，条件不成立
    clearTimeout(this._pollTimer);
    this._pollTimer = null;
  }
}
```

**推导（两个方向都会出问题）**：
- **泄漏**：tick 执行期间 `_pollTimer = null`，此窗口内用户切 tab 触发 `_stopMatchPolling()` → `if (this._pollTimer)` 为假 → **空操作**；随后在途请求回调执行 `setTimeout(tick, delay)` → **定时器复活**，对已隐藏/已销毁页面继续 setData。
- **叠加**：同一异步窗口内（`/live` 请求 1.4–12s）若 `onShow` 再次触发 `_startMatchPolling()`，因 `_pollTimer === null` 而**不会 return** → 启动第二条 tick 链 → 双倍请求、双倍 `_applyMatchSources`。

**触发条件**：切换 tab 与在途请求时间窗重叠（在 3G/弱网下 `/live` 耗时数秒，极易命中）。

**修复方向（仅供参考）**：引入独立状态标志（如 `_pollRunning`）或代际计数 `_pollEpoch`，在 tick 入口与 `setData` 前校验 `this._pollEpoch === epoch`；`_stopMatchPolling` 置 `_pollEpoch++` 使在途回调失效。

### 【P1-8】🔴 `hasOdMatchId` 正则双反斜杠 → R3 保护失效

**位置**：`utils/sources.js:1741-1744`

**代码原文**：
```js
var hasOdMatchId = card.matchIds.some(function (id) {
  return typeof id === 'number' || /^\\d+$/.test(String(id));   // ← /^\\d+$/ 而非 /^\d+$/
});
if (hasOdMatchId) return;   // R3 保护：保留（不降级 S1）
```

**推导**：在 JS 正则字面量中，`\\` 转义为**一个字面反斜杠字符**，故 `/^\\d+$/` 匹配的是「反斜杠 + d」形式的字符串（如 `"\\d"`），**不匹配纯数字串** `"8955197224"`。因此对字符串形态的 OpenDota matchId，`hasOdMatchId` 恒 `false`。

**后果**：R3 保护（L1744 的 `return`）失效 → 本应保留的上游同源卡被**降级到 S1 队名+时间窗吸收**（L1746+），存在误吸收 / 双卡风险。该保护的设计意图见 L1735-1736 注释：「仅当 matchIds 含『OpenDota 同源数字 match_id』时保留 R3 保护」。

**触发条件**：`matchIds` 中 OpenDota match_id 以**字符串**形态传入时（JSON 序列化 / 不同上游路径下的形态差异）。

**修复方向（仅供参考）**：`/^\d+$/`。

### 【P1-9】🔴 live 去重 standalone key 错位 → `undefined` 入数组并中断下游

**位置**：`utils/sources.js:2550-2557`

**代码原文**：

**修复方向（仅供参考）**：统一为同一变量：
```js

```

## 六、优化方向与理由

> 本节回答「**为什么**要优化」——每条都对应上文已确证问题暴露出的**结构性成因**，而非泛泛而谈。

### 6.1 【最高优先】补齐页面交互层的测试覆盖（结构性盲区）

**问题事实**：现有 `test:all` 为 **11 套件**（home-series / bo / sources / canonical / consensus / formatters / incremental / remote-curation / search-history / haglund / image），**全部是纯函数测试**。
本次抓到的 10 个确证问题中，**6 个位于页面层**（#1 #3 #4 #5 #6 + 待复核 #4/#5），**纯函数测试完全覆盖不到**。

**理由**：这不是"测试写得不够多"，而是**测试架构与风险分布错配**——项目把 100% 的测试投入投在了数据层（而数据层恰恰是历史沉淀最厚、最稳定的部分），而页面层的渲染/轮询/生命周期逻辑**零自动化覆盖**，只能靠"用户反馈 → 定位 → 修复"闭环，成本高且滞后（#1 这类必现 bug 本可在 CI 阶段拦下）。

**建议**（按性价比排序）：
1. **卡片工厂契约测试**（最小成本、最高收益）：对 `_cardFromSeries` / `_cardFromCuration` 的返回值做**字段清单断言**——先写下"消费侧读取了哪些字段"（可从 wxml + `_renderMatchFlow` 反推），再断言生产侧全部产出。本次 #1、以及待复核的字段名类问题都会被这条拦住。
2. **页面逻辑抽纯函数**：把 `_renderMatchFlow` 的"过滤 + 排序 + 计数"抽成纯函数（入参：卡数组/选中日/筛选器；出参：排序后列表 + 计数），即可纳入现有 11 套件体系。这是本项目**已被验证过的成功模式**（`sources.js` 的 BO 引擎正是这样沉淀下来的）。
3. **定时器/生命周期断言**：对 `_startMatchPolling` / `_stopMatchPolling` 做「start→stop→再 start」的序列测试，断言不产生第二条链（可用 fake timer + 计数桩）。

### 6.2 【高优先】建立"字段契约"这一层的防错机制

**问题事实**：本次 10 个问题中，**至少 6 个是"名称/形态不一致"类**：
- #1 `c.tier`（卡片无此字段）
- #5 `s.score1`（map 产物无此字段）
- #7 缓存 key 前缀（读写不一致）
- #8 `/^\\d+$/`（正则笔误）
- #9 `__standalone_N` vs `__standalone_(N-1)`（键错位）
- 待复核 #4（归一化规则两套）

**理由**：这类错误的共性是**编译器/静态检查抓不到**（JS 无类型、字符串键无校验），但**人工 review 也容易漏**（因为"看起来是对的"）。项目已为另一类风险建立了机制（颜色 token 越界有 `check-token-overreach` 守卫），但**字段契约层还没有对应守卫**——而它的出错频率明显更高。

**建议**：
1. 在 `scripts/` 增加一个**静态契约检查脚本**（类比既有的 `check-token-overreach`）：扫描关键工厂函数的返回体字段清单，与消费侧（wxml 绑定 + 读取点）比对，不一致即告警。可先从 `_cardFromSeries` / `_cardFromCuration` 两个函数做起。
2. 对**跨文件/跨形态字段**（如 `scoreA` vs `score1`、`tier` vs `tierLabel`）建立一份字段字典文档，放在 `deliverables/` 并纳入 review checklist。

### 6.3 【高优先】统一三套容灾策略（熔断器/归一化/超时）

**问题事实**：项目内同类机制存在**多套不一致实现**：
| 机制 | 实现 A | 实现 B | 实现 C |
|------|--------|--------|--------|
| 熔断 | `cloudBreaker.js`（10min TTL） | `haglund.js`（HALF_OPEN） | `supabaseClient.js`（**无 TTL、无半开、不分桶**） |
| 归一化队名 | `sources.js _normTeam` / `_normTeamX` | `league-detail.js normName` | `league-detail.js normForCache` |
| 超时 | `cloudProxy.call`（ACTION_TIMEOUT_MS） | `api.cloudFetch`（CLOUD_ACTION_TIMEOUT） | `supabaseClient`（固定 25s） |

**理由**：#10（EF 熔断器）与待复核 #4（归一化）正是这种"多套并存"的直接产物——**新写的实现没有继承既有的成熟模式**。项目已有正确范式（`cloudBreaker` 的 TTL + `haglund` 的半开），但缺少"新代码必须复用既有容灾组件"的约束。

**建议**：
1. 把熔断器抽成**单一可配置组件**（`createBreaker({threshold, ttl, halfOpen, bucketBy})`），三处调用点改为实例化——既统一行为，也让 #10 的修复变成"传参"而非"重写"。
2. 归一化函数收敛到 `utils/` 单一导出（如 `normTeamName(s)`），页面/数据层一律引用。

### 6.4 【中优先】首页加载性能：定位并消除串行等待

**问题事实**（结合 09-16 用户反馈「首页明显变慢」）：
- `_fetchLpUpcoming` 的 `lpP`（`index.js:428`）**没有超时兜底**——15s 的 `Promise.race` 只包住了 pro/live（L440-442）。
- 而 Liquipedia 侧存在**模块级全局串行锁**（`liquipedia.js:140-144` 的 `lastCall`，配合 `config.js` 的 RATE_GAP_MS ≈ 2.2s）。5 个候选赛事即使 `Promise.all` 并发，**落到本地兜底路径时仍被串行化** → 最坏 ≈ 11s。
- 项目自身的注释已承认该锁的存在与局限（`config.js:58-60`）。

**理由**：这是"看起来并行、实际串行"的典型陷阱——`Promise.all` 给出并行**语义**，但被模块级限流锁降级为串行**执行**。用户感知的"变慢"因此不是玄学，而是**结构性的等待叠加**。

**建议**：
1. 给 `lpP` 补超时（与 pro/live 同规格），超时即用缓存/stale 渲染，不阻塞首屏；
2. 评估把 5 个候选的 LP 查询**降级为"逐个按需"**（首屏只查最相关 1–2 个，其余交给轮询补齐）——项目已有轮询补齐机制（L1424-1434），改动风险低；
3. 若长期需要多赛事并行，应把限流锁从**模块级**下沉到**单域名请求队列**（保留 2.2s 间隔但允许不同赛事排队），而非全局互斥。

### 6.5 【中优先】错误可观测性：让线上问题"看得见"

**问题事实**：
- `app.js:117-131` 已落地全局 `onError` / `onUnhandledRejection` / `onMemoryWarning`（O-27）✅
- 但上报依赖 `wx.reportAnalytics` 的**自定义事件名**（`utils/monitor.js:36-47`），代码内**无事件名注册清单**；若后台"自定义分析"未建同名事件（`js_error` / `js_unhandled_rejection`），`report()` 会**静默丢弃**。

**理由**：本次审计中，#9 的后果（首页"进行中"整段消失）会被 `.catch(() => [])` 静默吞掉，与"当前确实没有比赛"**在表现上完全一致**。这意味着**线上真实故障可能长期不被发现**——而项目刚上线、正在观察期，这正是最需要"看得见"的阶段。

**建议**：① 补一份事件名对照文档并确认后台已创建；② 对关键链路的 `.catch` 增加**分级日志**（区分"预期降级"与"异常吞没"），避免 `catch(() => [])` 这种无差别兜底继续掩盖问题。

### 6.6 【中优先】云开发下线前必须收敛的双后端风险

**问题事实**：当前处于观察期（三个定时触发器已停用，云函数保留）。
- EF 熔断器缺陷（#10）在云函数下线后由 P1 升为 **P0**（全站数据链路中断）；
- 08 号文档《阶段6_下线确认清单》已识别「EF 单点」风险，但 #10 说明**该单点的自愈能力不足**。

**理由**：双后端冗余之所以能容忍当前缺陷，**正因为云函数还在**。"能回落"是现状，不是设计保证——一旦按计划删除云函数，回落目标消失，此时熔断器无 TTL 的缺陷会立刻显性化。

**建议**：**把 #10 列为下线前置条件**（而非"上线后再优化"）。同时建议在观察期日志中主动构造一次"EF 连续失败"场景，验证降级行为与恢复路径是否符合预期。

## 七、审计方法学反思

### 7.1 本次抓错有效性最高的三种手段
1. **"读侧 vs 写侧"对读**——#7（key 前缀）、#9（键错位）都是把两端代码并排就立刻暴露。凡是有"写入-读取"配对的逻辑，都值得强制做这一比对。

3. **"来源穷举"**——#1 的定案依赖"穷举 `_allMatches` 的所有写入点 + 确认 `grep "tier:"` 零命中"。对 P0 级结论，必须做到**排除所有反例路径**，不能只找到一条证据链。

- **值得肯定**：铁律沉淀机制（MEMORY.md + 日志）在本项目运转良好，多个历史坑（`cache.get` 副作用、`git rm` 清目录、curl 误判）都有明确记录且被规避。本次审计未发现这类历史坑复发。
