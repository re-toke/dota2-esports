# 账号体系重新设计（PRD · v1.2）

> 触发：真机反馈「微信账号无法登录，点击只设置昵称」+ 隐私指引驳回整改后重新审视
> 日期：2026-09-10 ｜ 状态：**待拍板**

---

## 一、问题诊断（基于代码事实，非推测）

| # | 问题 | 代码证据 |
|---|---|---|
| 1 | **无可见登录态** | openid 静默获取（`app.js` onLaunch），UI 上无任何体现 |
| 2 | **登录失败静默** | `follow.js` onSubscribe: `ensureLogin().catch(()=>{})` → 用户反复点击只见同一 toast（已补日志/提示，但交互仍不佳） |
| 3 | **用户卡语义混乱** | `follow.js:44`「仅存本地 storage（**无服务端账号体系**）」→ 头像/昵称是本地资料，但长在「我的」页顶部，用户自然读成「账号」 |
| 4 | **关注/提醒自动上云，无显式同意** | `syncProfile()` 在 5 处被无条件调用（follow 变更 ×1、提醒变更 ×3、onShow ×1），上传关注战队 + 提醒策略 |
| 5 | ★ **上传了但从不下载** | 只有 `restoreSubFromCloud()`（恢复**订阅态**），**没有恢复关注列表** → 「换机恢复」这个价值**不存在**；云端数据唯一消费者是 `smart-reminders` 服务端推送 |
| 6 | ★ **撤回同意 / 删除云端数据无法实现** | `follow-profile` EF **只有 `save` 与 `get`，没有 `delete`**；而 `privacy.wxml` 承诺的删除路径是「通过意见反馈联系开发者」—— **该功能并不存在** |

> 问题 4-6 是**合规硬伤**：声称可删除但无实现路径；有数据上云但用户无显式开关。

---

## 二、平台硬约束（设计必须接受，不可绕）

| 约束 | 说明 |
|---|---|
| **拿不到微信昵称头像** | `wx.getUserInfo` / `wx.getUserProfile` 自 2022 起**已回收**。唯一合规路径是 `<button open-type="chooseAvatar">` + `<input type="nickname">`，且**必须用户主动手势** |
| **openid 只能静默拿** | `wx.login` 不弹窗、无 UI，也没有「授权登录」这个界面了 |
| **不得强制登录** | 合规指引明令：不得「首页打开即要求授权登录」「拒绝授权则无法使用」；拒绝授权不影响非相关功能 |
| **隐私指引须先通过** | 未通过时 `<input type="nickname">` 会**降级为普通文本框**（官方明确） |

**结论**：**「微信登录」这个概念在 2026 年的小程序里已经不存在了** —— 没有可展示的授权界面，也没有可展示的身份信息。硬做「登录按钮」只会得到一个无内容的空壳。

---

## 三、设计主张：把「登录」重构为「**云同步**」

### 为什么这个方向对

用户真正在意的不是「登录」，而是**换设备不丢东西**。而 openid 恰好能提供这个（同一微信用户跨设备 openid 相同）。

| | 「微信登录」 | 「云同步」 |
|---|---|---|
| 用户预期 | 授权后能看到微信昵称头像 | 换设备数据能恢复 |
| 现实可交付 | ❌ 平台已不支持 | ✅ 完全可行 |
| 合规风险 | 高（易被判强制登录） | 低（自愿开启、可撤回） |
| 与现有代码 | 需重写 | 复用 openid + follow-profile 通路 |

### 核心价值主张（写进 UI 文案）

> **开启后，换设备也能恢复你的关注与提醒**

## 四、方案

### 4.1 状态机

```
        ┌──────────────┐
        │  未开启同步  │◀──────────┐
        └──────┬───────┘           │
               │ 用户点击开启       │ 关闭并删除云端
               ▼                   │
        ┌──────────────┐           │
        │   同步中…    │           │
        └──┬────────┬──┘           │
     成功  │        │ 失败          │
           ▼        ▼              │
   ┌──────────┐  ┌────────────┐    │
   │ 已同步   │  │ 同步失败   │    │
   │(显示时间)│  │ (可重试)   │────┘  重试/关闭
   └──────────┘  └────────────┘
```

### 4.2 UI（「我的」Tab · 用户卡内新增一行）

```
┌─────────────────────────────────────────┐
│  [头像]   昵称输入框                     │
│           资料仅保存在本机                │
├─────────────────────────────────────────┤
│  云同步                          [ ⚪──] │  ← 开关
│  换设备可恢复关注与提醒                   │
│  最近同步：今天 16:20                     │  ← 已同步时才显示
└─────────────────────────────────────────┘
```

**状态文案对照**：

| 状态 | 副文案 | 交互 |
|---|---|---|
| 未开启 | `开启后换设备可恢复关注与提醒` | 点击开关 → 开启 |
| 同步中 | `正在同步…` | 开关禁用 |
| 已同步 | `最近同步：{相对时间}` | 点击开关 → 弹确认 → 关闭+删除 |
| 同步失败 | `同步失败，点击重试` | 点击 → 重试 |

### 4.3 行为表

| 场景 | 行为 |
|---|---|
| **未开启同步** | 关注/提醒变更**只写本地**；`syncProfile()` 直接 return（不发起任何请求） |
| **开启同步** | 点击 → `ensureLogin()` → 成功则写一次全量 profile → 之后变更自动增量同步 |
| **开启「赛前通知」时** | ★ **必须上云**（服务端推送依赖 openid）→ 若同步未开启，弹窗说明「开启赛事提醒需要同步到云端」并请求开启 |
| **关闭同步** | 弹确认「将删除云端数据，换设备不再恢复」→ 调 EF `delete` → 本地保留 |
| **登录失败** | 状态置「同步失败」+ 可点击重试（不再静默） |
| **换机（新设备，同 openid）** | 开启同步后检测云端有 profile → 提示「发现云端有 N 个关注，是否恢复？」 |

> **「赛前通知」那一条是关键设计**：它给了同步一个**自然且必要的开启时机**（用户想要推送 → 推送本来就必须上云），而不是凭空弹一个「开启同步」的框。

### 4.4 需要新增的后端能力

| # | 改动 | 说明 |
|---|---|---|
| 1 | `follow-profile` EF **新增 `op: "delete"`** | 目前只有 save/get，**无法删除** → 撤回同意做不到 |
| 2 | 关注列表**恢复**能力 | 云端已有 `profile.teams`，但客户端从不读取 → 新增 `restoreFollowFromCloud()` |

### 4.5 文案修正（连带）

| 位置 | 现状 | 改为 |
|---|---|---|
| `privacy.wxml` | 「通过『意见反馈』联系开发者删除」 | 改为「在『我的 → 云同步』关闭同步即删除云端数据」（**功能真实存在**后再改） |
| 用户卡状态 | `资料仅保存在本机 · 换机不同步` | 与同步开关状态联动，避免两处信息打架 |

## 五、实施拆分

### P0（必做，合规+体验闭环）

1. **同步开关 + 四态展示**（未开启/同步中/已同步/失败）
2. **未开启时不上传**：`syncProfile()` 加开关守卫
3. **EF 新增 `op: "delete"`** + 关闭同步时调用
4. **「赛前通知」→ 引导开启同步**（自然时机）

### P1（把价值做实）

5. **关注列表恢复**：`restoreFollowFromCloud()` + 换机引导
6. 同步失败重试 + 最后同步时间
7. 隐私授权状态检测（`nickname` 降级时提示「需先同意隐私协议」）

### P2（打磨）

8. 同步状态可在「我的」页外查看（如设置页）
9. 云端 profile 结构版本化（避免后续字段变更导致兼容问题）

---

## 六、验收标准

- ☐ 未开启同步时，抓包**确认零** 数据上传（关注/提醒操作均不发请求）
- ☐ 开启后换设备（或清缓存后重登）能恢复关注列表与提醒设置
- ☐ 关闭同步后，Supabase `aggregation_cache` 中 `follow_profile_<openid>` **记录被删除**
- ☐ 登录失败有明确提示与重试入口（不再静默循环）
- ☐ 不出现任何「强制登录」：拒绝/不开启同步时，浏览、关注、搜索等**全部功能可用**

## 七、待拍板（3 个决策点）

| # | 决策 | 我的建议 |
|---|---|---|
| 1 | **同步默认开关**：默认关（用户主动开启）vs 默认开 | **默认关** —— 合规最优（显式同意 + 可撤回）；且「赛前通知」会自然触发开启，不损失转化 |
| 2 | **关闭同步时云端数据**：删除 vs 保留（仅停止同步） | **删除** —— 对应「撤回同意」，且协议书写的删除权必须真实可执行 |
| 3 | **本次范围**：只做 P0 vs P0+P1 | **P0+P1** —— 只做 P0 的话，「换机恢复」这个核心价值仍是空的（当前上传了却从不下载），账号概念还是立不住 |
