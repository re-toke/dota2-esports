## 二、M1（最高优先）· BUG-G 的修复选项①**事实上不成立**

**v1.2 原文**（P0-1 同批，BUG-G 条目）：「改法：二选一——① `EDGE_ACTIONS` 补 `getMatch: 'opendota-proxy'`（**须核实该 EF 已实现此 action**）」。

**审核结果**：已核实——**EF 未实现 `getMatch`**。
- `supabase/functions/opendota-proxy/index.ts:41-58` 的 `buildPath()` 是一个 `switch(action)`，其 case 仅覆盖 `getLeagues / getLeagueMatches / getTeam / getTeamPlayers / getTeamMatches / getPlayer / getPlayerMatches / getHeroes / searchTeams / getLeagueWindows / getProMatches / getLiveMatches`，**没有 `getMatch`**，`default: return null`（`:56`）。

**因此**：
1. 选项①**不是「补一个映射」**，而是「**EF 新增 getMatch handler（path `/matches/{id}`）+ 加映射 + 重新部署 + 加 L1/TTL**」的三段式改动，工作量与风险被低估。
2. **更严重**：若只按字面补映射而不改 EF，则每次 `getMatch` 会先发一次**必然失败的 EF 往返**（EF `buildPath` 返回 null → 报错）再回落直连——**比现状（直接 reject→直连）多一跳**，属**负优化**。
3. 现实推荐：**默认采用选项②**（从 `ACTION_MAP`（`api.js:381`）与 `PARAM_MAP`（`cloudProxy.js:214`）**移除 `getMatch`**，语义变为「getMatch 有意不经 EF」；这也正是 D8 守卫（`ACTION_MAP ∪ PARAM_MAP ⊆ EDGE_ACTIONS`）会强制的结果。

> 注：v1.2 用「须核实」做了对冲，方向正确；本审核把「未核实」**坐实为「不成立」**，请据此改写 BUG-G 的改法。

## 三、M2（方案最大逻辑漏洞）· P0-1 丢失了「recent 绕过 EF」这一关键机制，且 C 的覆盖范围被高估

**事实（源码核实）**：`utils/api.js:694-701`：

```js
const recent = (opts && Number(opts.recent) > 0) ? ... : 0;
if (recent) {
  return cached('/teams/' + teamId + '/matches?recent=' + recent, null, config.cacheTTL.teamMatches);
}
return tryCloudOrDirect('getTeamMatches', [teamId], function () {
  return cachedFreshIncremental('/teams/' + teamId + '/matches', 'team', teamId, 10 * 60, config.cacheTTL.teamMatches);
});
```

即：**带 `recent` 的分支走 `cached()`（纯直连 → 中转 `/od/api`），完全不经 EF**；**不带 `recent` 才走 `tryCloudOrDirect`（EF 优先）**。

**由此推出三个 v1.2 未说明的要点**：
1. `team-detail`/`h2h` **现状走 EF 主路径**（`opendota-proxy`）。而 **EF 不裁剪**（`api.js:687` 原注释、EF 无 trim 逻辑）⇒ 只要 EF 正常应答，返回的仍是**480KB 全量**。**「加 C（中转默认裁剪）」对这条 EF 主路径完全无效**——C 只作用于 `/od/api/*`（直连兜底）。
2. 所以 **A 方案（team-detail 加 `recent`）的真正作用，是把该调用从 EF 主路径切到「中转直连裁剪路径」**——它不是在 EF 里加裁剪。这一机制 **v1.1 有写（「绕过 EF，因 EF 不裁剪」），v1.2 被删掉了**，导致读者会误以为 `recent` 在 EF 上生效。
3. C 的价值因此**仅限「未来新调用点（走直连时）」的兜底**，**不是** `team-detail`/`h2h` 的直接修复手段；文档把 A / B′ / C 并列，未标注 C 的覆盖边界（仅 `/od/api`）。

**建议修订**：
- 明确写：**`getTeamMatches({recent})` 走 `cached()` 直连支路，绕过 EF**（引 `api.js:694-696`）。
- 明确写：**C（中转默认裁剪）只对 `worker.mjs` 的 `/od/api/*` 生效，对 `tryCloudOrDirect` 的 EF 主路径无效**；A 的本质是「把调用切到可裁剪的直连路径」。
- 若希望 **EF 路径也裁剪**，须在 EF（`opendota-proxy`）内实现（与 G14 镜像铁律相关），这一条 v1.2 完全缺失。

## 四、M3 · P0-1 外部实测的推断链不成立（证据强度）

**v1.2 推断**：「全量 2024ms、裁剪 602ms ⇒ 叠加 ~10s 基线 ⇒ 全量最坏 ~12s+、裁剪 ~10.6s ⇒ 逼近/超 20s」。

**问题**：
1. **26× 是「字节数」**（480.4/18.3），**端到端耗时只差 3.4×**（2024/602），且**一旦叠加 ~10s 固定基线，两者差距被稀释到 ~1.4s**（12s vs 10.6s）。⇒ 「加 C 消除超时风险」的**主要机制不是省时**，而是**避开中转上游 12s 超时（`worker.mjs:67`）与 20s 客户端预算**。文档句式「480KB→~18KB 量级，消除超时风险」未讲清「省时幅度受限」，易被误读。
2. **口径不一致未解释**：`api.js:678` 记录全量 **21~37s**，本次 node→中转仅 **2024ms**——相差一个数量级。二者若非同 team/同路径（直连 OpenDota vs 经中转缓存），不能互相印证。v1.2 未注明该差异。
3. 该实测是 **node→中转**，**不含**「小程序→中转 ~10s 基线」，因此**不能**用它反推真机耗时（文档自己也承认真机首屏仍待测——这点保留正确）。

**建议**：把结论改为「裁剪可**消除上游超时**并把 payload 降 26×；**端到端省时幅度受 ~10s 基线稀释**，真机定级仍待测」；并注明 21-37s 与 2024ms 的口径差异。

## 五、M4 · P1-2 的「宿主可达性实测」是弱证据，不足以支撑「第二台中转技术可行」

**v1.2 实测**：`netlify.com` / `vercel.com` / `render.com` = 200 ✅；`fresh.deno.dev` = 301 ✅；`deno.com` apex = TIMEOUT ❌ ⇒ 结论「跨宿主双出口技术可行」。

**问题**：
1. 测的是**平台的首页/apex 域名**，**不是未来部署产生的函数子域**（如 `xxx.netlify.app`）。而本文档自己论证的正是**「域名粒度」阻断**——**首页域名可达 ≠ 函数子域可达**。二者是不同域名，可能被不同策略命中。
2. 样本里 `deno.com`（apex）超时、`fresh.deno.dev`（子域）301，只能说明「apex 与子域策略可能不同」，**不足以**支撑「跨宿主即安全」。
3. 因此「做跨宿主双出口」是**合理方向**，但**该实测不能作为「可行」的结论证据**。

**建议**：将本实测降级为「**宿主层可达性初筛**（排除整片不可达）」；**真正的『可行』验证必须在部署后对实际函数域名复测**（与 §六-3 的 `/healthz` 自检同一路径）。
