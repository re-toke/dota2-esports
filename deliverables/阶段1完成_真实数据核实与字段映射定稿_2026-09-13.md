## 一、`admin-logs` 记录：**推断证实，且比想象更明确**

```
action: "cron_discover"    count: 248    operator: "cron"
summary: { total: 598, dota2: 598, existing: 500, new: 248, inserted: 100, skipped: 148 }
details: [{ _id: "dotaprocircuit2021222easterneuropeclosedqualifi..." }]   ← ★

```

### ✅ 铁证 1：`existing: 500`

代码 `.limit(500)` → 对比基数被**死死卡在 500**，而集合里有 **2,414** 条。

### ✅ 铁证 2：`details[0]._id` 是 **2021 年**的赛事

`dota pro circuit 2021-22 2 eastern europe closed qualifier` ——
这显然**早就在库里**（库中 2414 条含大量历史赛事），却被当成「新赛事」插入。

**→ 完全证实：「假新赛事」淹没了真新赛事。**

### 修正一个数字（我此前估错了）

| | 我此前估计 | 实际 |
|---|---|---|
| `new` | ~1900 | **248** |
| 原因 | 我假设 LP 侧有 2414 条 | **LP 侧只有 598 条**（`total: 598`）|

**更准确的机制**：LP 全量 598 条 − 命中前 500 的部分 ≈ 248 条被判「未收录」，
而这 248 条里**绝大多数是库里已有的**（只是不在前 500 名内）。
→ 每次 `inserted: 100` 插的都是这类老赛事，**真正的新赛事永远排在后面**。

## 三、字段映射定稿（可直接实施）

| 云开发 | Supabase | 处理 |
|---|---|---|
| `curation_events._id` | **新增列 `canonical_key text`** | ⚠️ **不是 league_id** |
| 其余业务字段（去掉 `_id`/`updatedAt`）| `data jsonb` | 原样透传 |
| `curation_teams._id` | `team_id bigint` | 数字，可直接映射 |
| 其余字段 | `data jsonb` | 原样透传 |
| `curation_meta._id` | `key text` | `'ti_contestant_ids'` |
| `ids` / `count` / `version` | 存 jsonb | |

### 🔴 必须先改 schema（`001-init.sql` 的设计与真实数据不匹配）

```sql
-- 现有设计（001-init.sql）
curation_events(league_id bigint NOT NULL UNIQUE, data jsonb)
                     ↑ 但真实 _id 是【字符串名字】，且 34% 的条目根本没有 leagueId
```

**需要的迁移**（`003-curation-schema-fix.sql`）：

```sql
ALTER TABLE public.curation_events ADD COLUMN IF NOT EXISTS canonical_key text;
UPDATE public.curation_events SET canonical_key = data->>'_id' WHERE canonical_key IS NULL;
ALTER TABLE public.curation_events ALTER COLUMN league_id DROP NOT NULL;   -- 34% 没有 leagueId
CREATE UNIQUE INDEX IF NOT EXISTS ux_curation_events_canonical ON public.curation_events(canonical_key);
```

> Supabase 的 `curation_events` 三张表**当前是空的**（已验证），所以改 schema 无数据风险。
