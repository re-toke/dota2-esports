## 1. 复核方法与论证

### 1.1 采样口径与局限

- 时间：2026-10-29；环境：Windows PC、上海家宽、`curl.exe`；每端点 1–3 次采样；EF 空请求另做 5 次背靠背对照（附录 B.3）；未做多次中位数。
- 指标定义：**TTFB** = `time_starttransfer`，**总耗时** = `time_total`（含下载），**体积** = 解压后 / gzip 后字节。
- **重要局限**：本机到中转的链路抖动极大（`/healthz` 1.10–10.46s；同一 EF 空请求 8.09–32.3s，连发后收敛到 1.5–1.7s；热 EF 真上游 6.1–242.3s；PostgREST 2.02–59.33s）。因此本文只把观测值当**区间**使用，不把单次绝对值当 SLA；结构性结论（请求数、串行关系、阻塞关系、体积）不受抖动影响。
- 未做真机 / 弱网模拟；附录 A 给出复现命令，建议在目标城市与 4G 网络各复测 3 次，再校准目标值。

### 1.2 七轮论证

#### 第 1 轮：体积是不是首屏主因？

- 主张（v1.0）：是，所以先裁响应。
- 实测：首页 bundle 仅 32KB / 4KB gzip，仍要 4.2–6.7s；EF 空请求（不触上游、立即 400）也要 8.1–32.3s；`getProMatches` 31KB 为 1.44–29.3s。
- 反证：KB 级响应耗时数秒，体积解释不了；EF / 中转链路的固定开销（冷启动 + 境外 RTT）才是主项。
- 结论：**修正**。体积只在三个端点显著：单场明细 286KB、items 336KB、`/od/api/live` 144KB；它们与传输时间叠加，仍值得修，但不能解释首页的首卡延迟。

#### 第 2 轮：`getHomeBundle` 一次 RTT 是否更快？

- 主张（v1.0 P1-5）：pro + live 合成 1 次调用，少 2 个 RTT。
- 实测：bundle **4.20 / 6.08 / 6.69s**；单路 pro **1.44 / 2.56s**（热），冷启动最差 29.3s。
- 代码：EF 侧 bundle 的 live 最多等 **2.5s**，超时返回 `live:null`；客户端 `proP = bundleP.then(...)`，即 `pro` 必须等 bundle 整体返回。
- 反证：少调用 ≠ 早首帧。bundle 把首卡推迟到 **live 等待结束 + EF 开销**之后；而 pro 本可以先到先渲染。
- 结论：**推翻**。首屏 `pro` / `live` 两路并行；bundle 只做后台合并刷新（或彻底退出首屏）。若保留，必须加 `HOT_ACTIONS` 且**不得 gate `pro`**。
- 诚实边界：若真机 A/B 显示 bundle 首卡更早（可能因为 EF 侧 pro 缓存更热），以首卡时间为准保留 bundle；但“3→1”不能作为验收指标。

#### 第 3 轮：启动预热越多越好？

- 主张（现状）：预热让切页秒开。
- 实测：`setTimeout(0)` 内并发 heroes（21KB，6.99s）、items（336KB，105.4s）、leagues（67KB，3.90s）、windows（4KB，25.5s）、auth、experiment；另有 t0 的 pro / live 与 index 的 bundle。
- 反证：弱网下 336KB 的 items 会长期占用连接与带宽，pro / live 与 bundle 同时抢同一条出口；而 items 对战报首帧是**阻塞项**，预热反而把阻塞项提前到启动期。
- 结论：**预热必须分级**。t0 只发首屏关键 pro / live；heroes / leagues 延后到首帧之后；items 只在战报页按需；windows 跟随赛事页。

#### 第 4 轮：战报首屏到底被什么卡住？

- 代码顺序：`load()` → `getMatch`（TTFB 4.04s / 总 11.87s）→ `applyMatch` → `Promise.all([heroesP, itemsP])` → 才 `loading:false`。
- `heroes.getHeroes()` = `api.getHeroes()`（EF 21KB）+ `api.getHeroStats()`（直连，未预热，12s 超时）；items = 336KB（12s 超时）。
- 反证：即使 `getMatch` 已经返回，页面仍会停在骨架，直到 items / heroStats 结束或超时。真机最坏 4–25s。
- 结论：**新增 P0-2**。首帧只依赖 `getMatch`；heroes / items 必须异步补齐。顺带把战报从 `heroes.getHeroes()` 改为 `api.getHeroes()`（战报不需要 `pro_pick` 等统计），可少一个 `heroStats` 请求。

#### 第 5 轮：中转缓存有效吗？

- 实测：`getLeagueDetailBundle` 首访 **6.87s**，60s 内二次 **1.35s**；说明 relay 内存缓存确实能跳过 EF。
- 代码：`EF_CACHE_MS` 只有 1 条（[worker.mjs#L67-L69](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/infra/proxy/worker.mjs#L67-L69)）；缓存 key 已含 `params`（[L345-L350](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/infra/proxy/worker.mjs#L345-L350)），扩面不会串数据。
- 结论：**有效但覆盖面太窄**。扩到 10 个只读 action，并加 stale-while-revalidate（过期也先回旧值 + 后台刷新），可把复访从 4–8s 压到 1–2s。首访仍受 EF 冷启动影响，不承诺改善。

#### 第 6 轮：图片是首屏瓶颈吗？

- 实测：Steam CDN `_sb.png` TTFB **2.64s** / 10.8KB；战报页 10 张英雄头像 + 最多 70 张物品图标（[match-detail.wxml](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/subpackages/detail/match-detail/match-detail.wxml) 的 `wx:for`），但 `lazy-load` 只在进入视口时加载。
- 反证：首帧（锚点卡 / MVP）不依赖图片，图片是滚动体验与视觉完整度问题。
- 结论：**P2**，不占 Batch A。用固定比例占位 + 骨架减少跳动即可；不建议为此引入图片代理或本地图标包。

#### 第 7 轮：8–32s 是冷启动，还是固定跨境开销？

- 主张（第 1 轮遗留）：EF 的秒级开销是“出境 RTT + 网关”的固定成本，改不了。
- 实测：同一 `opendota-proxy` 空 action（立即 400、不触上游）**连发 5 次** = **33.18 / 2.99 / 3.77 / 1.56 / 1.68s**；`bundle-aggregator` = 1.62 / 2.88 / 5.98s（附录 B.3）。
- 反证：若为固定成本，5 次应持平；实际首调 33s、随后收敛到 1.5–1.7s ⇒ **冷启动主导**，且可被预热消除。但同轮“热 EF + 真上游”仍是 6.1 / 9.5 / 66.9 / 242.3s ⇒ 上游与链路抖动独立存在，keep-warm 消不掉。
- 结论：**新增 P0-7 keep-warm**。它只消除冷启动段（8–33s → ≈1.7s 下界 + 上游抖动），**不承诺首访显著变快**；首屏改善仍必须靠客户端（P0-1 / P0-2 / P0-3 / P0-4）。这一轮同时解释了为什么 v1.0 的“减少请求数”既不够、也不该作为主杠杆：省掉 1 个请求，省不掉 33s 冷启动。

### 1.3 三条主因

1. **EF 冷启动 + 跨境链路**：中转 `/healthz` 1.10s 起；EF 空请求首调 8–33s、同 isolate 连发后收敛到 1.5–1.7s（§1.2 第 7 轮）；热 EF + 真上游仍 2–242s，PostgREST 2.02–59.33s。可消除的只有冷启动段（P0-7）；上游抖动只能靠缓存与 stale 兜（P1-3 / P1-4）。
2. **启动期争抢**：8 个左右请求（含 336KB items）在首屏同时发出，弱网下互相拖慢。
3. **关键路径串行 / 门控**：bundle gate pro；items + heroStats gate 战报首帧；getTeam ×2 拖后队徽；直播轮询被缓存吞掉。

## 2. 性能优化方案

### P0-1 启动期网络预算（新增）

**证据**：[app.js#L61-L62](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/app.js#L61-L62) 发出 pro / live；[L64-L120](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/app.js#L64-L120) 在同一 `setTimeout(0)` 内并发 probe、heroes、items、experiment、auth、leagues、windows。items 实测 336KB / 62KB gzip；windows 实测 25.5s。

**改法**

1. **删除** `app.js` 的 `api.getItems()` 预取（[L95-L100](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/app.js#L95-L100)）。战报页已有兜底加载；改为战报 `onLoad` 时与 `getMatch` 并行发起，不阻塞渲染。
2. heroes 预取移到首帧后 `t+3000ms`；leagues / windows 移到首次进入赛事页，或 `t+5000ms` 且与 heroes 串行。
3. `endpoints.probe()` 移到 `t+8000ms`；`auth.ensureLogin` / `experiment.refresh` 移到 `t+5000ms`（无首屏依赖）。
4. 保留 `api.getProMatches()` / `api.getLiveMatches()` 在 t0（与首页同一 action，前台去重生效）。

**验收**：启动 0–3s 内业务请求 ≤2；items 不再出现在启动网络面板；弱网下 pro / live 不再被 336KB 请求拖慢。

**风险**：首次进入赛事页可能仍需 3–6s 拉 leagues（页面已有骨架 + stale 缓存）；可接受。

### P0-2 战报渐进渲染（新增，原“详情页慢”的核心）

**证据**：[match-detail.js#L180-L186](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/subpackages/detail/match-detail/match-detail.js#L180-L186) 的 `Promise.all`；[L319-L348](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/subpackages/detail/match-detail/match-detail.js#L319-L348) 才把 `loading` 置 false；items 336KB / 12s 超时；`heroes.getHeroes()` 还额外拉 `heroStats`。

### P0-7 EF keep-warm（新增，唯一不依赖客户端发版的性能项）

**证据**：同一 `opendota-proxy` 空 action（立即 400、不触上游）连发 5 次 = **33.18 / 2.99 / 3.77 / 1.56 / 1.68s**；`bundle-aggregator` = 1.62 / 2.88 / 5.98s（附录 B.3）。首调即冷启动，之后收敛到热态空载下界 ≈1.5–1.7s。

**代价**：6 EF × 15 次/小时 ≈ 90 请求/小时，全部空转；Supabase Dashboard 会出现 400 计数上升，可接受（或在 EF 内加 `ping` 短路返回 204 以消噪音）。

**验收**：idle 10min 后连测 3 次，任一 EF 首调 ≤4s；上线前记录当下冷启动值（本次 33s）作对照。

**边界（必须写清）**：keep-warm 只削掉冷启动段。同轮“热 EF + 真上游”实测 6.1 / 9.5 / 66.9 / 242.3s，上游与跨境抖动仍在 ⇒ 首访仍可能数秒到数十秒，首屏必须靠客户端缓存 / stale / 裁剪（P0-1…P0-4、P1-3）。

### P1-4 中转 EF 缓存扩面 + stale-while-revalidate（新增）

**证据**：`EF_CACHE_MS` 只有 `bundle-aggregator|getLeagueDetailBundle` 60s；命中 1.35s vs 首访 6.87s。缓存 key 含 `params`（[worker.mjs#L345-L350](file:///d:/WorkBuddy项目文档/2026-07-19-15-21-29/dota2-esports/infra/proxy/worker.mjs#L345-L350)）。

**建议 TTL**

| EF / action | TTL | 理由 |
|---|---|---|
| `opendota-proxy` / `getLiveMatches` | 20s | 与 `/live` 对齐 |
| `opendota-proxy` / `getHomeBundle` | 30s | live 语义 |
| `opendota-proxy` / `getProMatches` | 60s | 职业赛列表变化慢 |
| `opendota-proxy` / `getLeagueMatches` | 60s | 比分刷新 |
| `opendota-proxy` / `getTeam` | 15min | 队徽 / 队名 |
| `opendota-proxy` / `getLeagues` | 30min | 列表 |
| `opendota-proxy` / `getLeagueWindows` | 30min | 赛期窗口 |
| `opendota-proxy` / `getHeroes` | 6h | 常量 |
| `bundle-aggregator` / `getLeagueDetailBundle` | 5–10min（由 60s 上调） | 对阵 / 队名变化慢 |

> `getTeamNames` / `getTeamLogos` / `getTeamTags` 走 `/explorer` 直连（不在 EF 白名单），客户端已有 6h 缓存，不在本表。

**stale-while-revalidate**：命中但已过期 → 立即返回旧 body（`X-Proxy-Cache: STALE`），后台单次刷新（`refreshing` 守卫）。这样 60s TTL 不再是硬等待，复访稳定在 1–2s。

**边界**：Deno / Netlify isolate 内存缓存，命中率取决于流量；首访仍受 EF 冷启动影响。不承诺“首访变快”，只承诺“复访不等 EF”。

## 6. 不建议做（含理由）

| 项 | 理由 |
|---|---|
| **把 `getHomeBundle` 作为首屏唯一数据源** | 实测 bundle 比单路 pro 慢 2–4s，且内部 live 等待 2.5s；它适合“后台合并刷新”，不适合 gate 首帧。 |
| **启动期继续全量预热** | items 336KB 是首屏的带宽竞争者、也是战报首帧的阻塞项；“预热”把慢请求提前，不是消除。 |
| **本期做暗色模式** | 前置是 186 处颜色 token 化 + TDesign 主题 + 队徽/插画适配；先清 P0，再单独立项。 |
| **把 `getMatch` 改成 explorer SQL 取字段** | 字段稳定性与解析状态需自维护，风险高于响应白名单裁剪。 |
| **删除 199KB 队徽快照** | 弱网 / 断网时的零网络来源，保留。 |
| **把 `t-icon` 全量替换为自绘 SVG** | 109KB 字体确实大，但覆盖 9 个组件的所有图标；仅在包体再次告急时做子集化。 |
| **继续拆分包 / 拆页面** | 首屏 bundle 与 `preloadRule` 已把详情链路压到 1 跳；继续拆只增加跳转空窗。 |
| **自建 WebSocket 实时后端** | 先把轮询修对（P0-5）；真有并发需求再评估。 |
| **大拆 `sources.js`** | 30+ 调用点、规则密集，高风险低感知；在新功能上渐进拆。 |
| **本期把 EF 热读迁移到 PostgREST** | PostgREST 实测也要 2.0–59.3s，且迁移面大；先做 relay 缓存与 stale，观察 2 周命中率再决策。 |
