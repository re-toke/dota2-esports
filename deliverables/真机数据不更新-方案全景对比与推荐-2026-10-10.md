## 第一部分：问题全面梳理（一页看懂）

### 1.1 现象（线上真机）
① 首页只显示当天对局、历史对局失败；② 赛事页停在「内置快照 **9月28日**」、**下拉重试无效**；③ 首页有重复对局卡片。

### 1.2 根因链（每条都有实测依据）

```
国内网络对境外域名做了「按域名粒度」的阻断/劫持
   │
   ├─ `*.supabase.co`（客户端唯一的后端：EF + PostgREST）
   │     → TLS 握手被 RST（SNI 阻断）★ 换 IP / DoH / hosts 全无效
   │
   └─ `api.opendota.com`（客户端"直连兜底"）
         → DNS 被劫持到 103.73.220.77 + 自签证书 ⇒ 兜底名存实亡
   │
   ▼
客户端两条取数路径**同时失效** ⇒ 只能显示打包时烘焙的 9-28 快照
   │
   └─ 且 `cloudEnabled()` 连续 3 次失败即熔断本会话的云通道
         ⇒ 之后全走直连（撞被劫持的域名）⇒ **下拉重试也永远恢复不了**
```

- 失败发生在**连接层**（`ERR_CONNECTION_RESET`，**92ms** 就失败）⇒ 与"超时/体量"无关；
- 与"账号/密钥"也无关（详见已排除项）。

### 1.3 已排除的怀疑（避免重复劳动）
| 怀疑 | 结论 | 依据 |
|---|---|---|
| 后端故障 | ❌ | CI 在境外机房：EF Health **26/26 成功**、Sync Upcoming **14/14 成功** |
| 真机 request 白名单缺域名 | ❌ | 用户实测已配全（`api.opendota.com`/`liquipedia.net`/`api.stratz.com`） |
| 客户端 `anonKey` 错值 | ⚠️ **是真缺陷，但不是本次成因** | 报错是连接层重置，401 不可能产生它；**但连通性恢复后会立刻暴露** |
| `/leagues` 1MB 未裁剪 ⇒ 12s 超时 | ❌ | **92ms** 就失败，与超时无关 |
| 代码回归 | ❌ | 09-28→10-10 **代码零改动** |

### 1.4 为什么开发者工具永远测不出来
`urlCheck: false`（模拟器不校验域名）+ 云通道失败后**静默回退直连** ⇒ 本地一切"正常"。

### 1.5 一个容易忽略的结构性事实
**CI 在境外 ⇒ 它能拿到全部数据**（读 Supabase ✓、抓 OpenDota/LP ✓）。
⇒ 这打开了"**不一定非要让客户端实时连后端**"的方案空间（见 §3 的 B 类）。

## 第四部分：★ 推荐方案（分层组合）

> 核心思路：**用 A′ 打通实时数据（最小改动）→ 用 B 做静态兜底（几乎零成本）→ 用 C 补强数据源**。
> 三层的收益是**叠加**的：任何一层可用，App 就不是"白屏/只有 9-28 快照"。

### P0（先做，1 天内可验证）—— **A′：国内云的香港地域 + 自有域名 做中转**
- 为什么推荐 A′ 而不是最初的 CF Worker：
  1. **免费子域实测不稳**（`pages.dev`/`workers.dev`/`vercel.app` 本轮均失败）⇒ CF 方案必须配**自有域名**才有意义；
  2. 既然都要自有域名，**放在国内云的香港地域**更顺：域名备案/合规路径清晰、可开票、控制台中文、且**出口在境外**（能连 Supabase ✓）；
  3. 实测同类域名可达 ✓（`cos.ap-guangzhou.myqcloud.com` TLS OK）。
- 落地：把我已写好的 `infra/proxy/`（CF Worker 版代码逻辑）**改造成香港轻量/云函数**跑（逻辑几乎不用改，只是载体不同）。
- **客户端改动**：仍只是 2 个常量（+ 加白名单，**不需要重新提审**）。
- **先做可达性实测**：浏览器打开 `https://<域名>/healthz` ⇒ 返回 JSON 即成立。

### P1（P0 之后，几乎零成本）—— **B：curation/赛程静态化到国内 CDN**
- **CI（境外）** 每日/每 5 分钟生成 `curation` + `schedule` JSON → 上传**腾讯云 COS**（实测可达 ✓）；
- 客户端优先读本地烘焙快照，其次读 CDN 静态 JSON ⇒ **中转挂了也不会退回 9-28**；
- 好处：**把"单点中转"的风险摊掉**；成本几乎为 0。

### P2（补强）—— **C：Valve 官方 API 作为比分/结果兜底源**
- `api.steampowered.com` 实测可达 ✓，key 免费申请；
- 用途：当 OpenDota（经中转）不可用时，仍能拿到**比赛结果/比分**；
- 局限：**没有 tier/赛事元数据** ⇒ 分级仍依赖 curation（由 P1 的静态数据供给）。

### 备选（若 A′ 域名也被阻断）
- **D：微信云开发（香港环境）** —— 免白名单，最稳，但架构回退，需评估维护成本。

### 无论选哪条都必做的两件小事
1. **修 `anonKey`**（或由中转在服务端覆盖 —— 已实现）；注意**不能改成空值**（`enabled()` 判据含它）；
2. **修重复卡片的合并键**（已复现：`1w Team` vs `1win`，见另一份诊断）。

## 第六部分：一句话总结

**问题本质**：国内对**域名粒度**的阻断让客户端的两条取数路径同时失效（Supabase 被 SNI 阻断、OpenDota 被劫持），
于是只剩 9-28 的烘焙快照；这与白名单、密钥、超时、代码都无关。
**方案不止"境外中转"一条** —— 还有 **静态投递到国内 CDN（成本几毛）**、**换用 Valve 官方 API（实测可达）**、
**微信云开发免白名单**。**推荐分层组合：A′ 打通实时 + B 做兜底 + C 补数据源**，
其中 **A′ 的客户端改动最小（2 个常量、不用重新提审）**，**B 的成本几乎为零且能吃掉单点风险**。

## 第七部分（用户追加提问）：「后端换到国内」有免费方案吗？

### 7.1 ★★ 决定性新发现（本轮实测）

```
① 本地 DNS：api.opendota.com → 103.73.220.77            ← 被劫持
② DoH（阿里 223.5.5.5，**国内可用**）→ 真实 IP：172.67.155.85 / 104.21.48.178
③ 连「真实 IP」但用 api.opendota.com 做 SNI + Host
      → **HTTP 200，32987 bytes ✅ 绕过成功**
```

**结论**：
- **`api.opendota.com` 只是「DNS 劫持」，TLS/SNI 完全没被阻断** ⇒ **用「真实 IP + Host/SNI 覆盖」就能取到数据** ✓✓
- **DoH（223.5.5.5）在国内可用** ⇒ 可**动态**解析真实 IP（不必写死 IP，容忍 CF 换 IP）✓
- ⚠️ **这套动作只能由服务端做**：小程序的 `wx.request` 只接受域名（不能给 IP）、也无法自定义 DNS ⇒
  **必须"国内服务 + IP 直连"** ✓
- ⚠️ 但 **`*.supabase.co` 是 SNI 阻断**（DNS 正常、握手被 RST）⇒ **IP 直连救不了它** ✗
  ⇒ **"后端放国内"的前提是：放弃 Supabase**（换成国内存储）。

### 7.2 免费方案（国内）对比

| 方案 | 免费？ | 免域名白名单？ | 能取到数据？ | 工作量 | 备注 |
|---|---|---|---|---|---|
| **F1 · 微信云开发（TCB）** | ✅ 有免费额度 | ✅ **免**（`wx.cloud.callFunction` 走微信私有链路） | ✅ 云函数用 **DoH+IP 直连** 访问 OpenDota（已验证） | **中大**（需恢复云开发调用链） | ★ **唯一"免费 + 免白名单 + 能取数"三者兼得** |
| F2 · 腾讯云函数 SCF / 阿里 FC | ✅ 有免费额度 | ❌ 需 API 网关域名 + 白名单 | ✅ 同上 | 中 | 需买域名（非纯免费） |
| F3 · 静态投递到国内 COS | 近免费（几毛/月） | ❌ 需域名白名单 | ✅（CI 境外生成） | 中（要适配层） | 见前文 B |
| F4 · 自建国内轻量 | ❌ 要钱 | ❌ | ✅ | 中 | — |

### 7.3 ★ 推荐：**F1 微信云开发（国内免费 + 免白名单）**

**为什么它正好解决问题**：
1. **免 request 白名单** —— 走 `wx.cloud.callFunction`（微信私有链路）⇒ 不碰域名阻断，**也不用买域名/备案**；
2. **云函数在国内** ⇒ 出网用 **DoH（223.5.5.5）+ IP 直连** 访问 OpenDota ✓（实测可绕过劫持）；
3. **数据库/存储在云开发内** ⇒ 国内天然可达 ⇒ **彻底摆脱 Supabase**；
4. **CI 仍可写库**（CI 在境外，访问国内云开发/数据库没问题）⇒ 抓取链路不用大改。

**代价（必须诚实说）**：
- 这是**架构回退** —— 项目 2026-09-22 刚从云开发迁到 Supabase，且当时**主动移除了 `_cloudFetchViaCloud`（云函数直调兜底）**；
- 需要：① 恢复/重建"客户端 → 云函数"调用链；② 数据访问层适配（EF/PostgREST 形状 → 云函数）；③ CI 写库目标可能要从 Supabase 表改为云开发数据库（或保留 Supabase 让云函数读——但云函数在国内读不到 Supabase ✗ ⇒ **必须搬**）；
- 工作量评估：**中大**（但代码框架与历史都在，`git log` 可回溯）。

**一个更轻的变体（若不想大改）**：
- **只把"直连兜底"换成"国内云函数"**：即客户端保持现有 Supabase 路径（等中转/域名方案），**另加一条国内云函数兜底**专门负责 OpenDota 取数（因为 IP 直连已验证可行）⇒ 工作量小得多，且能立刻让"赛事/比赛数据"恢复 ✓

### 7.4 因此更新后的推荐顺序

| 优先级 | 动作 | 免费 | 免白名单 | 工作量 |
|---|---|---|---|---|
| **①（最快恢复）** | **国内云函数只做 OpenDota 代理**（DoH+IP 直连），客户端把它当作新的"直连兜底" | ✅ | ✅（若用云开发） | **小** |
| ② | 若选云开发 ⇒ 顺手把 curation/赛程也迁进来（彻底摆脱 Supabase） | ✅ | ✅ | 中大 |
| ③ | 中转（A′）/ 静态投递（B）作为备选或补充 | 部分 | ❌/部分 | 小~中 |

> ★ **关键结论**：`api.opendota.com` 的"DNS 劫持"可被**服务端 IP 直连**绕过（已实测）⇒
> **"后端放国内"是成立的**，而且**微信云开发是唯一"免费 + 免白名单 + 能取数"的组合**。
> 唯一必须放弃的是 **Supabase 作为数据后端**（它被 SNI 阻断，国内服务同样取不到）。

## 第八部分：还有别的方案吗？——用「二维矩阵」把方案空间讲完

### 8.1 先回答一个前置问题（本轮实测，排除一条路）
**问：`www.opendota.com` 可达，那客户端能不能直连它的 API（零后端）？**
**答：不能。** 实测 `www.opendota.com/api/proMatches`、`/api/leagues`、`/api/heroStats` 全部返回
**`text/html` 的 SPA index 页**（不是 JSON）⇒ **该域名不提供 API** ✗
⇒ "不装后端、客户端直接拿 OpenDota 全量数据"这条路**已排除（有证据）**。

### 8.2 本质：能改的变量只有三个

```
① 客户端依赖谁   →  a) 只依赖「实测可达的境外源」  b) 依赖自建后端
② 服务端放哪     →  ⓞ 没有  ① 国内  ② 境外
③ 数据怎么送到客户端 →  实时接口 / 静态投递 / 随发版烘焙
```
**任何方案都是这三者的组合** ⇒ 把可行格子列出来，就能回答"还有没有别的方案"。

| **① 国内后端** | ★★ **方案 H（最平衡 · 我推荐）**<br>国内云函数**只做 OpenDota 代理**（**DoH+IP 直连**，已实测 ✓）<br>客户端其余仍直连可达源<br>⇒ 免费额度、若用云开发则**免白名单**<br>⇒ **立刻恢复赛事/比赛数据**，不动主体架构 | **F1 微信云开发全量后端**<br>免费 + 免白名单 + 数据完整<br>⚠️ 工作量中大（**架构回退**，需恢复 `_cloudFetchViaCloud`） |

### 8.4 ★ 两个"之前没提过"的方案

#### 方案 G · 零后端（最省钱、最省运维）
**客户端只直连这三家**（全部**实测可达**，无需任何自建服务）：
- `dota.haglund.dev` ✓（赛程/赛事，已在用）
- `liquipedia.net` ✓（赛事元数据/分级，已在用）
- **`api.steampowered.com` ✓（Valve 官方，新发现可达）** ⇒ 补"比赛结果/比分"
**curation / 赛事分级** 由 CI（境外）生成 → **随版本烘焙进包**（低频数据，够用）。
- ✅ **零服务器、零域名、零白名单新增（只需把 `dota.haglund.dev` 加进白名单）、零成本**
- ❌ 覆盖受限：拿不到 OpenDota 的 `tier`/全量赛事列表/`/explorer`；"赛事列表"要靠 curation 兜
- 客户端改造：**中大**（数据源适配层）
- ⇒ 适合：**能接受"赛事列表以策展为准、比分来自 Valve/haglund"** 的场合

#### 方案 H · 国内云函数只做 OpenDota 代理（**最平衡 · 推荐**）
- 一个**国内云函数**（云开发免白名单 / 或 SCF+网关），内部实现：**DoH 解析真实 IP → IP 直连 + SNI/Host 覆盖 → 返回 JSON**（这套逻辑我**已在沙箱跑通**）
- 客户端**只加一条兜底**：现有路径失败时调它 ⇒ **立刻恢复赛事/比赛数据**
- ✅ 免费额度、免白名单（若用云开发）、**不动 Supabase 主体架构**、工作量**小**
- ⚠️ 仍需替换 Supabase（其自身被 SNI 阻断）⇒ 但那是**第二阶段**，不急于一并做

### 8.5 决策矩阵（按你最在意什么选）

| 你最在意 | 选 | 代价 |
|---|---|---|
| **完全免费 + 不要任何运维** | **方案 G（零后端）** | 数据覆盖下降、客户端改造中大 |
| **尽快恢复数据 + 改动小** | **方案 H（国内云函数代理）** | 需要一个国内云账号（免费额度内） |
| **数据完整性最高** | **F1（云开发全量后端）** | 架构回退、工作量中大 |
| **客户端改动绝对最小** | A′（境外中转 + 自有域名） | 要域名、可能被阻断、非纯免费 |

### 8.6 诚实说明：方案空间到此为止
再往下**不是"新方案"，而是"参数选择"**（选哪家免费宿主、CI 跑多快、白名单加哪几个域名）。
根因只有一个（**域名粒度阻断**），能动的变量只有三个（见 §8.2），
所以正确的问法不是"还有没有别的方案"，而是
**"在『免费 / 改动小 / 数据全 / 上线快』四者里，你优先要哪两个"** —— 定了我就照着落。
