# P2-A 融合计算治理 · 实测定位与优化（2026-09-27）

> 交付物类型：**实测定位报告 + 已落地的优化**（方案 §9.3 定义：融合计算治理 → 预计算或移出热路径）
> 方法：临时分段插桩（模拟器真机数据）→ 定位热点 → 最小等价优化 → 同插桩复测 → 移除插桩
> 结论：**方案点名的三个热点实测合计仅 1~4ms（前提不成立）**；真正热点是 `curation.eventFor`
> 的查表实现，优化后 **D 段 74~102ms → 8~11ms（约 -90%）**，整条管线 **~70~106ms → ~11ms（约 -85%）**。

## 2. 根因：`_cardFromSeries` 内的两次 curation 查表

D 段内再细分（同一插桩，累计 43 次）：

| 子步骤 | 累计（优化前） | 每次 |
|---|---|---|
| `sources.leagueDisplayName(g0)` | **36~51ms** | ~0.9~1.2ms |
| `sources.getMatchTierForHome(...)` | **35~42ms** | ~0.9ms |
| `sources.isStaleLiveSeries(s, now)` | 0ms | ~0 |
| `this._dateKeyOf(...)` | 0~3ms | ~0 |

两者合计占 D 段 **~90%**，且**同一联赛的多张卡会重复算同一件事**。

链路：`leagueDisplayName` → `canonicalLeagueName` →（可能 2 次）`_canonLookupOnce` → `curation.curatedEventFor` → **`LOCAL.eventFor`**；
`getMatchTierForHome` → 又一次 `curatedEventFor`。⇒ **每张卡最多 3 次 `eventFor`**。

而 `eventFor` 的实现里有两处随调用次数线性放大：

```js
const ks = Object.keys(EVENT_INDEX);   // ① 每次调用都重建「全部 canonical + aliases」的键数组
for (let i = 0; i < ks.length; i++) {  // ② 宽松匹配：对全部事件键线性扫描
  const idx = k.indexOf(ek);           //    每个键最多 2 次 indexOf（正/反向）
```

① 是**纯分配浪费**（`EVENT_INDEX` 构建后永不变化）；② 是 O(事件键数) 扫描，命中越靠后越慢。

## 3. 已落地的优化（两步，均**不改变任何匹配语义**）

### 3-1 键数组缓存（`utils/curation.js`）
`EVENT_INDEX` 全仓仅两处写入（`buildLookups` 构建期）⇒ 键数组可安全缓存一次。
**缓存放在 `buildLookups` 闭包内**：curation 远端重载时 `remoteCuration` 会重跑 `buildLookups`
⇒ 新闭包 = 新缓存，**天然失效**，不会出现"curation 更新了但键数组还是旧的"。

### 3-2 名称匹配结果记忆化（`nameMatch(k, game)`）
- **为什么可缓存**：名称匹配只依赖 `(归一名, game)`，**与时间无关**。
- **为什么另一条路径不能缓存**：`pinLookup` 按 `leagueIdWindow` **判届**、依赖 `now`
  ⇒ **刻意不缓存**，否则跨窗后会取到旧届。
- **两条必须逐位等价的易错边界**（都已在代码注释与单测中锁住）：
  1. **精确命中时原实现是 `return validGame(EVENT_INDEX[k])`** —— 即使 `validGame` 返回 `null`
     也**直接返回**（不再走宽松扫描）。故实现为 `if (EVENT_INDEX[k]) { out = okGame(...) }`，
     而不是"不匹配就继续扫"。
  2. **宽松扫描里的 `game` 过滤发生在扫描内部**（跳过不匹配的条目、继续往后找）
     ⇒ 缓存键**必须含 `game`**；否则会把"因 game 不匹配而继续扫描才得到的结果"错配给另一个 game。
- 另加容量护栏（>800 条整体清空重建），防会话内无界增长。

## 5. 守卫（`test-canonical.js` 67 → 71）

新增 4 条，锁「记忆化不得改行为」的三个失效面：

| 守卫 | 锁什么 |
|---|---|
| 冷启动 vs 热命中逐位一致（canonical/leagueId/tier） | ① 缓存了错的值 |
| 同一输入重复 20 次幂等 | 缓存自身稳定性 |
| **不同 game 不串味**（合成 lookups，含"精确命中即 null"边界） | ② 键漏 game |
| **leagueId 判届路径未被缓存**（同 id 不同 now 必须取到不同届） | ③ 把时间相关路径也缓存了 |

### ★ 守卫的**证伪验证**（脚本 `_guard-falsify-p2a.js`，工作区根，未入库）
按纪律对"一次就过"的守卫做证伪，过程抓到 **1 条近永真断言**：

- 首版「跨 game 串味」用真实赛事 `PGL Wallachia Season 9` 做探针 —— 但该条**未声明 `game`**，
  `validGame` 不过滤 ⇒ dota2/cs2 结果**天然相同** ⇒ 漏掉 `game` 键**照样通过**。
  ⇒ 改为**合成 lookups**（`buildLookups([{canonical:'Epsilon Cup 2099', game:'cs2'}], {})`），
  证伪时 buggy 版本确实把 cs2 结果污染成 `null` ⇒ **守卫生效**。
- 「leagueId 判届未被缓存」证伪通过：一旦按 leagueId 缓存（忽略 now），不同 `now` 取到同一届
  ⇒ 该断言会 FAIL ⇒ 守卫生效。
- **教训**：拿真实数据当探针前，必须先确认该数据**能触发**待测分支；否则写出的就是永真断言。

## 7. 诚实边界

- 全部数据来自**微信开发者工具模拟器**（桌面 CPU）。真机（中端安卓）JS 通常慢 3~10×，
  **但相对占比应保持**：热点仍是同一处。**绝对耗时未在真机测得**。
- 未做帧率/首屏交互延迟（TTI）测量；DR 段耗时为纯 JS 同步耗时，不含渲染。
- 优化只针对**首页卡片工厂**的调用链；`eventFor` 另有若干调用点（详情页/战队页等），
  它们同样受益，但**本次未单独测量**。
