## 一、总体结论

代码整体优化意识非常好（多数页面已有：路径式 setData、防抖、请求 ID 防竞态、分页、SWR 缓存、inflight 去重、F3 分步渲染、onUnload 清理）。审查发现 **3 个 P1、4 个 P2、2 个 P3 观察项**，其中 P1 集中在「列表页异步增强链失控」「直播页轮询生命周期」「follow 同步存储读」。

**已确认健康、无需改动的关键点（排除误报）：**

- `api.js`：`cached()` 带 TTL + inflight 同 key 去重 + `cachedFresh` SWR + 增量游标 —— 缓存层设计规范，未发现绕开缓存重复拉取。
- `cache.js`：LRU prune 在未超限时提前返回，`set()` 内 prune 成本可接受。
- `liquipedia.js`：串行限流器（RATE_GAP_MS=2200ms）+ 重试退避 + 熔断 + slug 缓存 key —— `leagues.js enhanceListMetadata` 注释中的"2.2s 间隔"实际由该限流器保证，代码里 100ms 只是循环节奏，不是缺陷。
- `subscribe.js`：`ensureOpenId` / `requestSubscribe` 均永不 reject（fail 回调 resolve），页面裸 `.then()` 无 `.catch` 是安全的。
- `index.js`：`_loaded` 守卫防 onLoad+onShow 重复；`startTimer/stopTimer` 在 onHide+onUnload 双清理；tick 只做有变化的路径更新。
- `league-detail.js`：`_pendingTimer` 在 onUnload 清理；F3 两步渲染 + 路径更新 + 小场详情懒加载 + standings 懒加载。
- `app.js`：预热推迟到 `setTimeout(0)` 且全部 catch 隔离，不阻塞首屏。

### P1-1 列表页 `enhanceListMetadata` 并发链失控 + 无卸载清理 + 索引错位

**位置**：`pages/leagues/leagues.js:1159-1192`（定义），调用点 `:327`（loadLeagues）、`:1040`（applyAndSlice 末尾）、`:1048`（appendPage 末尾）

**问题**：

1. **无并发防重**：`applyAndSlice` 被 筛选切换 / 排序 / 视图 / 重置 / onShow 还原 / 翻页 等多入口触发，每次都启动一条独立的 `enhanceListMetadata` 链。多条链并行 → 同一赛事被重复请求 Liquipedia 元数据（虽然限流器串行 + `getLeagueMetadata` 有缓存兜底，但重复请求会排队占满 2.2s 限流队列，拖慢其它真实请求）。
2. **无卸载清理**：链内 `setTimeout` 在离开页面后仍会继续执行，对已销毁页面 `setData`（有 try/catch 包裹不报错，但网络请求与限流队列占用纯属浪费）。
3. **索引错位**：链启动时捕获 `var list = this.data.list` 快照，但 `setData` 的 `patch['list[' + idx + '].prizePool']` 按当前 `data.list` 的索引写入。若链执行期间列表被筛选/翻页重建，`idx` 会指向错误条目，把 A 赛事的奖金池写到 B 赛事上。

### P1-3 `follow.js` 无内存缓存，每次查询同步读 Storage

**位置**：`utils/follow.js:27-30`（isFollowed）、`:57-61`（list）、`:63-69`（counts）、`:11-21`（read）

**问题**：`read()` 每次调用都执行 `wx.getStorageSync`（同步 I/O，阻塞主线程）。调用面：`leagues.js` 的 `normalize()`（`:439`，每个联赛一次）、`buildUpcomingCard`（`:175`，每张赛程卡一次）、`mergeCurationUpcoming`（`:949`）、`sortSmart`（`:52`）。一次赛事列表加载可能触发 **200+ 次同步存储读**，叠加在 Promise 回调（主线程）里执行，直接推后列表 `setData` 的渲染时机。

**修复 diff**（模块级内存 memo，写入时失效；对外 API 不变）：

```diff
 const KEY = 'dota2_follow';
+// P1-3：模块级内存缓存，避免每次查询同步读 Storage。
+// 所有写入统一走 write()，写入后失效即可保证一致性（无外部绕过 follow.js 写该 key）。
+let _memo = null;

 function read() {
+  if (_memo) return _memo;
   try {
     const d = wx.getStorageSync(KEY);
     if (!d || typeof d !== 'object') return blank();
     if (!d.teams) d.teams = {};
     if (!d.leagues) d.leagues = {};
+    _memo = d;
     return d;
   } catch (e) {
     return blank();
   }
 }

 function write(d) {
+  _memo = d;   // 同步更新内存缓存（与落盘一致）
   try { wx.setStorageSync(KEY, d); } catch (e) {}
 }
```

> 注意：`_memo = d` 与 `write(d)` 的对象引用一致，`follow()`/`unfollow()` 里先 `read()` 再改字段再 `write(d)`，memo 始终持有最新对象，无需额外失效。若未来有其它模块直接 `wx.setStorageSync(KEY, ...)` 绕过本模块，需在此处加失效钩子（当前代码库无此情况）。

### 7.2 复审发现并修正的 2 处修复 diff 缺陷（原稿→修正后）

**缺陷 A（P1-1，死锁）**：原稿 `gen+1` 在 `if (this._metaEnriching) return;` **之前**。场景：链 A 运行中（`_metaEnriching=true`）→ 用户切换筛选触发新调用 → 先 `gen+1`（链 A 的代际失效）→ 命中 `_metaEnriching` 检查 return（新链未启动）→ 链 A 在下一个检查点因 `gen !== this._metaGen` 退出，但退出路径**不复位 `_metaEnriching`** → 残留 `true` → 此后所有 `enhanceListMetadata` 调用都在入口直接 return → **元数据增强永久死锁**。  
→ 修正：检查在前、`gen+1` 在后（运行中链被跳过时不递增代际，链 A 可正常跑完并复位）。

**缺陷 B（P1-2，无效位置）**：原稿把"赛后关闭 realtime"放在 `_applyLiveUpdate` 的 `if (m.radiant_win != null)` 分支内。但 `applyMatch` 的轻量路径判定 `stillLive = m.radiant_win == null && this.data.isLive`——**比赛结束（radiant_win 有值）时 `stillLive` 恒为 false，推送必然走完整渲染路径（`_applyMatchWithData`），永远不会进入 `_applyLiveUpdate`**；该函数内部的 `radiant_win != null` 分支本就是历史遗留死代码。原稿修复因此完全不生效。  
→ 修正：赛后关闭移到 `applyMatch` 开头（`if (m.radiant_win != null && this._realtime)`），覆盖所有推送路径，且与 `_applyMatchWithData` 内 `startRealtime(isLive=false)` 的 return 语义自洽。
