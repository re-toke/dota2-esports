## 二、P0 · 阻塞级问题

### P0-1 · `page::before`/`page::after` 伪元素在微信小程序中兼容性不确定

**位置**：§D.4 CSS 落地方案（第 244-275 行）

**问题**：
规范使用 `page::before` 和 `page::after`（`position: fixed; z-index: 0`）作为顶部/底部渐变遮罩。但微信小程序的渲染引擎（双线程架构：逻辑层 + 渲染层）对 `page` 伪元素的处理与标准浏览器不同：

1. `page` 并非真实 DOM 元素，而是渲染层的特殊根节点
2. `page` 伪元素在部分旧基础库（<2.7.0）中完全不支持
3. 即使支持，`page::before`/`::after` 的 `z-index` 堆叠上下文可能与预期不同——页面内容可能被遮罩覆盖导致不可交互

**影响**：遮罩层可能不生效（导航栏/tabBar 区域背景图过亮），或严重情况遮罩覆盖所有内容导致页面不可交互。

**建议修复**：
```css
/* 不要用 page::before / page::after，改为在 page 内部放置真实 view 元素 */
```
在每个页面的 WXML 根级添加：
```html
<view class="bg-mask-top"></view>
<view class="bg-mask-bottom"></view>
<!-- 原有内容 -->
```
```css
.bg-mask-top {
  position: fixed; top: 0; left: 0; right: 0; height: 30vh; z-index: 1;
  background: linear-gradient(180deg, rgba(13,13,13,0.9) 0%, transparent 100%);
  pointer-events: none;
}
.bg-mask-bottom {
  position: fixed; bottom: 0; left: 0; right: 0; height: 20vh; z-index: 1;
  background: linear-gradient(0deg, rgba(13,13,13,0.9) 0%, transparent 100%);
  pointer-events: none;
}
```
页面内容容器加 `position: relative; z-index: 2` 确保在遮罩之上。

### P0-2 · `background-attachment: fixed` 在微信小程序 `page` 上不生效

**位置**：§D.4（第 237 行）和 §D.4 要点第 3 条（第 283 行）

**问题**：
微信小程序 WXSS 不支持 `background-attachment: fixed`。设置后实际行为等同于 `scroll`。这是小程序文档明确指出的限制。

**影响**：页面滚动时背景图跟随滚动，底部可能出现背景图重复或截断。

**建议修复**：
在 §D.4 CSS 中删除 `background-attachment: fixed;` 并注释说明：
```css
/* 注：微信小程序不支持 background-attachment: fixed，此处省略 */
```
替代方案：使用 `background-size: 100% auto`（保持宽度填满）+ 确保图片高度足够覆盖最长页面，或接受背景跟随滚动的行为（在 28% opacity 下不太明显）。

### P0-3 · §D.5 图片处理脚本描述完全过时

**位置**：§D.5（第 310-323 行）

**问题**：
§D.5 描述的脚本逻辑（brightness × 0.25 + 近黑底混合 35% + Gaussian Blur 1.5px + WebP q=75 + 7KB/316KB）与实际脚本 `process-bg.py` **完全不符**。实际处理：
- 裁掉底部 7%（非 paste 覆盖）
- 拉伸回原始尺寸（新增步骤，非旧版逻辑）
- opacity 28% 叠加（非 brightness 操作）
- **零** Gaussian Blur
- WebP q=78，38KB / 850KB

**影响**：若有人按 §D.5 描述重新生成背景图，得到的产物与已定稿的 `bg-battlefield-dark.webp` 完全不匹配。

**建议修复**：
整节重写为：
```markdown
#### D.5 图片处理脚本

处理脚本位于 `scripts/process-bg.py`，执行三步处理：

1. **去水印**：裁掉底部 7%（水印区域），零 paste 痕迹
2. **拉伸全覆盖**：将裁后图像拉伸回原始 832×1216 比例（消除裁剪造成的空白）
3. **降暗**：opacity 28% 叠加在近黑底 #08080a 上（纯透明度混合，保留对比度和锐利轮廓）

**零模糊策略**：不使用 Gaussian Blur，建筑轮廓保持锐利清晰。

压缩输出：缩放至 750×1096 → WebP (q=78, 38KB) + PNG (850KB)

重新处理命令：
\`\`\`bash
python scripts/process-bg.py
\`\`\`

如需调整亮度，修改脚本中的 `opacity` 值（当前 0.28）即可。
```

### P0-4 · 方案 C 9 层 CSS 渐变积叠存在严重性能风险

**位置**：§1.1.1 方案 C（第 99-145 行）

**问题**：
规范建议将方案 D（战场图）+ 方案 C（9 层 CSS 渐变）叠加使用。在 `page` 上同时叠加 1 张 WebP 背景图 + 9 层 `radial-gradient`/`linear-gradient`，在低端 Android 设备（微信 benchmarkLevel < 10）上会导致：
- 首屏渲染延迟 200-500ms（每一层渐变都需要 GPU 合成）
- 滚动时帧率明显下降

当前项目已有 `benchmarkLevel` 检测逻辑（`custom-tab-bar/index.js` 中）。

**影响**：低端设备用户体验显著下降。

**建议修复**：
1. **不推荐叠加方案**：方案 D 本身已有足够的视觉趣味性（战场图 + 建筑轮廓 + 战争迷雾），叠加方案 C 的光晕效果增益有限但性能代价大
2. 如果真的需要叠加，用 `benchmarkLevel` 做分级渲染：
   ```css
   /* 默认：仅方案 D */
   page { background-image: url('bg-battlefield-dark.webp'); }
   /* 高性能设备：方案 D + C 简化版（仅 3 层核心光晕） */
   .perf-high page {
     background-image:
       radial-gradient(...),  /* 天辉 */
       radial-gradient(...),  /* 夜魇 */
       radial-gradient(...),  /* 中心 */
       url('bg-battlefield-dark.webp');
   }
   ```
3. 更新决策表标注：方案 D 独立使用即达标，方案 C 叠加为「可选增强（仅高性能设备）」

### P0-5 · 方案 D CSS `url()` 路径不符合微信小程序资源引用规范

**位置**：§D.4（第 233 行）

**问题**：
```css
background-image: url('assets/bg-battlefield-dark.webp');
```
微信小程序中 `background-image: url()` 引用本地图片需使用**绝对路径**（以 `/` 开头）或**相对路径**（相对于当前 wxss 文件）。

规范写 `url('assets/bg-battlefield-dark.webp')` 是相对路径，但未说明这个路径相对于什么。实际在 `app.wxss` 中使用时，相对路径的基准是 `app.wxss` 所在目录（即 `miniprogram/` 根目录）。

Phase 1.8 要求「拷贝到 `miniprogram/assets/`」，则正确路径应为 `url('/assets/bg-battlefield-dark.webp')` 或 `url('./assets/bg-battlefield-dark.webp')`。

**影响**：背景图 404 加载失败，页面只剩纯黑底。

**建议修复**：
```css
background-image: url('/assets/bg-battlefield-dark.webp');
```
同时在 Phase 1.8 中明确目标路径：`miniprogram/assets/bg-battlefield-dark.webp`。

### P1-3 · `@keyframes` 动画在小程序中作用域问题

**位置**：§1.4.2（第 462-502 行）

**问题**：
规范定义的 5 个 `@keyframes`（`pulse-glow`/`signal-dot`/`fade-up`/`star-fill`）写在规范中是「全局定义」，但微信小程序中：
- `app.wxss` 中定义的 `@keyframes` **可以被所有页面引用**（行为与 web 一致）
- 页面级 wxss 定义的 `@keyframes` **仅本页可用**

目前规范未明确这些 keyframes 应该放在哪里。

**建议修复**：
在规范中明确标注：「以上 5 个 `@keyframes` 全部定义在 `app.wxss` 中（全局可用）」。

### P1-4 · 方案 C 中的 `rpx` 在渐变中使用需验证

**位置**：§1.1.1 方案 C 第 9 层（第 141 行）

```css
repeating-linear-gradient(45deg, transparent, transparent 2rpx, rgba(255,255,255,0.015) 2rpx, rgba(255,255,255,0.015) 3rpx);
```

**问题**：
`rpx` 在 `repeating-linear-gradient` 的色标位置中使用。虽然 WXSS 理论上支持，但在部分渲染引擎中 `rpx` 单位在渐变色标中的计算精度可能不如 `px`。在高 DPI 屏幕上可能出现条纹宽度不一致。

**建议修复**：
改为 `px`（2px / 3px 在小程序中也是非常小的值，不影响在不同设备上的表现），或在规范中加一条注：「第 9 层纹理中的 rpx 单位在部分低端设备上可能渲染异常，如遇到改为 px」。

### P1-5 · 分区标签图标（sword/shield）未验证，存在空白图标风险

**位置**：§2.4（第 715/718 行）和 §2.5 图标表（第 746 行注释）

**问题**：
规范引用 TDesign 图标 `sword` 和 `shield`/`shield-error` 用于分区标签，但标注「需在实施前 grep 验证——若不存在可降级」。

这是 P0-1 类似风险——如果图标不存在则出现空白元素。应**在规范定稿前就完成验证**，而非留给实施阶段。

**建议修复**：
先运行验证，然后将验证结论写入规范。如不存在，直接在规范中标注备选方案（如使用 `chart`/`layers` 替代，或直接使用纯文字分区标签）。
