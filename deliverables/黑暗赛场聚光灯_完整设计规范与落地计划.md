#### 推荐方案

**方案 A（推荐）：极低透明度叠加层（最安全）**

```css
/* 在 page 背景上叠加 DOTA2 英雄图片，透明度极低仅作纹理暗示 */
page::after {
  content: '';
  position: fixed;
  inset: 0;
  z-index: -1;
  background-image: url('https://cdn.cloudflare.steamstatic.com/apps/dota2/images/dota_react/heroes/heroes_bg.jpg');
  background-size: cover;
  background-position: center;
  opacity: 0.08;          /* 极低透明度——仅纹理暗示，不喧宾夺主 */
  filter: blur(2px);      /* 轻微模糊，进一步弱化识别度 */
  pointer-events: none;
}
```

- 透明度 0.08 + 模糊 2px → 用户隐约感知到"有英雄在背景中"，但无法清晰辨认具体英雄
- 既是游戏元素又不构成"使用+分发游戏素材"的风险
- 纯 CSS 背景引用，不把图片文件打包进小程序
- ⚠️ 此方案使用 `page::after`，存在微信小程序兼容性风险（见方案 D §D.4 说明）。如选此方案需改用真实 view 遮罩层。

**方案 B：多英雄散落布局（更有趣味性，需 CDN 托管图片）**

.bg-hero {

.bg-hero--invoker { top: 5%; right: 5%; width: 40%; }

实现方式：图片托管在 Steam CDN（已在项目 `downloadFile` 合法域名中），不打包进小程序包。

#### D.4 CSS 落地方案（v12 实施版 · 页面级 image）

> ⚠️ **微信小程序硬性限制（2026-08-09 实施踩坑 ×2）**：
> 1. **WXSS 的 `background-image` 不支持本地资源路径**——只接受网络图片（https://）或 base64。在 `page` 上写 `url('/assets/bg-battlefield-dark.webp')` 会触发渲染层报错：`本地资源图片无法通过 WXSS 获取`。
> 2. **自定义组件内部的 `position: fixed` 不可靠**——背景图会随内容滚动，向下滑动后视口顶部露出 page 黑底（战队/我的页明显）。必须用**页面级元素**（直接放在页面 WXML 的 `<image>`/`<view>`，非自定义组件）。
> 3. `page::before`/`page::after` 伪元素兼容性不确定，`background-attachment: fixed` 不被支持。
>
> **正确方案（v12 落地）**：页面根容器直接放 `<image class="bg-page">`（页面级 fixed 相对视口，滚动不跟随），配合 `<view class="bg-page-dim">` 暗化层 + `<view class="bg-mask-top/bottom">` 渐变遮罩。

**`app.wxss`**（近黑底兜底 + 页面级背景样式）：
```css
page {
  /* 近黑底色（始终保底 + 图片加载失败时自动降级） */
  background: #0d0d0d;
}

/* 页面级战场图背景层：fixed 相对视口，滚动不跟随 */
.bg-page {
  position: fixed;
  top: 0; left: 0;
  width: 100%; height: 100%;
  z-index: -1;
  pointer-events: none;
}
/* 暗化层：整体压暗背景图至"似有似无、仅见模糊轮廓"程度
   rgba(13,13,13,0.84) ≈ 28% 图片亮度再压至 ~4%，近乎只剩隐约轮廓 */
.bg-page-dim {
  position: fixed;
  top: 0; left: 0;
  width: 100%; height: 100%;
  z-index: -1;
  background: rgba(13, 13, 13, 0.84);
  pointer-events: none;
}
```

**各页面 WXML**（根容器内插入，置于内容之前）：
```html
<view class="container with-tab-bar">
  <!-- 战场图背景层（页面级 image，mode=aspectFill 等效 CSS cover） -->
  <image class="bg-page" src="/assets/bg-battlefield-dark.webp" mode="aspectFill" />
  <view class="bg-page-dim"></view>
  <!-- 页面内容... -->
  <view class="bg-mask-top"></view>    <!-- 顶部渐变遮罩 -->
  <view class="bg-mask-bottom"></view> <!-- 底部渐变遮罩 -->
</view>
```

**遮罩样式（app.wxss）**：
```css
/* 顶部遮罩：确保导航栏区域背景比中间更暗 */
.bg-mask-top {
  position: fixed;
  top: 0; left: 0; right: 0;
  height: 30vh;
  background: linear-gradient(180deg,
    rgba(13, 13, 13, 0.9) 0%,
    rgba(13, 13, 13, 0.5) 50%,
    rgba(13, 13, 13, 0) 100%
  );
  z-index: -1;
  pointer-events: none;
}
/* 底部遮罩：确保 tabBar 区域背景比中间更暗 */
.bg-mask-bottom {
  position: fixed;
  bottom: 0; left: 0; right: 0;
  height: 20vh;
  background: linear-gradient(0deg,
    rgba(13, 13, 13, 0.9) 0%,
    rgba(13, 13, 13, 0.5) 50%,
    rgba(13, 13, 13, 0) 100%
  );
  z-index: -1;
  pointer-events: none;
}
```

**关键实现要点**：

1. **图片本身已降暗**：处理后的 WebP 图片为 opacity 28% 叠加在近黑底 #08080a 上的效果——在 CSS 中无需再做 `opacity` 或 `filter: brightness()` 处理，直接铺底即可
2. **战场图用页面级 `<image>`**：微信小程序 WXSS 的 `background-image` 不支持本地资源（仅网络图/base64），必须用 `<image>` 标签。`mode="aspectFill"` 与 CSS `cover` 等效。**关键：`<image>` 必须直接放在页面 WXML（页面级元素），不能包在自定义组件里**——组件内 `position: fixed` 不可靠，滚动会露出缺口
3. **上下渐变遮罩**：真实 `<view class="bg-mask-top">` / `<view class="bg-mask-bottom">`（非 `page::before`/`::after`），`z-index: -1` → 在 page 背景之上、内容之下，只暗化背景不遮挡内容。`pointer-events: none` 确保不拦截触控
4. **负 z-index 层级设计**：`.bg-page`/`.bg-page-dim` 与遮罩同为 `z-index: -1`，按 DOM 顺序——背景在页面开头、暗化层其后、遮罩在页面末尾，故遮罩盖在背景图之上，三者都在内容之下。**不要**给 `.container` 加 `position/z-index`（会创建 stacking context 干扰负 z-index，并改变页面内绝对定位元素的包含块）
5. **无 `background-attachment: fixed`**：微信小程序不支持此属性（行为等同于 `scroll`）。页面级 `<image>` fixed 已解决固定问题
6. **WebP 格式**：38KB，对小程序包体积影响可忽略（微信小程序原生支持 WebP）
7. **降级策略**：图片加载失败时背景自动退化为纯黑底 `#0d0d0d`（`background` 独立定义在 `page` 选择器），不影响任何信息阅读。无需额外 `onError` 处理
8. **背景过亮调节**：如整体仍偏亮，调 `.bg-page-dim` 的 alpha（当前 **0.84**，值越大越暗；调暗历程：0.45 → 0.78 → 0.81 → 0.84，对应亮度约 15% → 6% → 5% → **~4%**，已达"似有似无"目标）。如需进一步压暗，优先调大 alpha 而非改原图 opacity（避免发灰）。

#### D.5 图片处理脚本

处理脚本位于 `scripts/process-bg.py`，执行三步处理：

1. **去水印**：裁掉底部 7%（水印区域），零 paste 痕迹
2. **拉伸全覆盖**：将裁后图像拉伸回原始 832×1216 比例——消除裁剪造成的顶部空白，保证 `cover` 模式下 100% 全覆盖
3. **降暗**：opacity 28% 叠加在近黑底 `#08080a` 上（纯透明度混合，不操纵 `brightness`，完整保留对比度和锐利轮廓）

**零模糊策略**：不使用 Gaussian Blur——建筑轮廓和战争迷雾在暗化后仍保持清晰可辨，不会产生灰蒙雾感。

压缩输出：缩放至 750×1096 → 导出 WebP (q=78, 38KB) 和 PNG (850KB)。

重新处理命令：
```bash
python scripts/process-bg.py
```

如需调整亮度，修改脚本中的 `opacity` 变量（当前 0.28）即可——参数含义直观（值越大越亮）。

### 1.4.2 动效 & 微交互 Token（Motion Design）

> **新增（v7）**：当前设计语言中多处提到"脉冲呼吸""灯光渐暗"但无系统动效规范。"聚光灯"的舞台隐喻需要通过动效来体现。

```css
/* 缓动曲线 */
--ease-out:    cubic-bezier(0.16, 1, 0.3, 1);       /* 元素入场/展开 */
--ease-in-out:  cubic-bezier(0.65, 0, 0.35, 1);      /* 持续循环动画 */
--ease-spring: cubic-bezier(0.34, 1.56, 0.64, 1);    /* 弹性反馈（tabBar 选中） */
--ease-back:   cubic-bezier(0.68, -0.3, 0.27, 1.3);  /* 弹出（toast/徽章） */

/* 时长 Token */
--dur-fast:   150ms;   /* 微交互（hover/点击反馈） */
--dur-normal: 300ms;   /* 过渡（卡片淡入/页面切换/浸染展开） */
--dur-slow:   600ms;   /* 叙事动画（卡片浸染/页面切换） */
--dur-breath: 2400ms;  /* 呼吸循环（LIVE 脉冲/信号点）：参照平静呼吸 12-20 次/分，落在 ~25 次/分 区间，平缓不急促 */
--dur-sway:   1600ms;  /* 中等节奏装饰动画（加载更多待命光晕/箭头浮动/标签脉冲）：介于过渡与平静呼吸之间，约 37 次/分（v18 新增） */

/* ===== 关键动画定义 ===== */

/* ① LIVE 脉冲呼吸（赛事列表/详情页进行中卡片）
   节奏：吸气(0→35%) → 峰值保持(35→55%) → 呼气(55→90%) → 静息(90→100%)，模拟真实呼吸而非急促闪烁。
   v16 更新：原 dur-slow 600ms + 单峰无停留 → 急促闪烁感（~100 次/分）；
             改用 dur-breath 2400ms + 峰值停留段 → 平静呼吸节奏（~25 次/分）。 */
@keyframes pulse-glow {
  0%       { box-shadow: 0 0 4rpx  rgba(95,211,95,0.2); }
  35%, 55% { box-shadow: 0 0 14rpx rgba(95,211,95,0.5); }
  90%      { box-shadow: 0 0 4rpx  rgba(95,211,95,0.2); }
  100%     { box-shadow: 0 0 4rpx  rgba(95,211,95,0.2); }
}
.live-pulse {
  animation: pulse-glow var(--dur-breath) var(--ease-in-out) infinite;
}

/* ② 信号激活脉冲（我的页面·赛事提醒已开启徽章）—— 同呼吸节奏 */
@keyframes signal-dot {
  0%       { opacity: 0.4; transform: scale(0.8); }
  35%, 55% { opacity: 1.0; transform: scale(1.2); }
  90%      { opacity: 0.4; transform: scale(0.8); }
  100%     { opacity: 0.4; transform: scale(0.8); }
}
.signal-active {
  animation: signal-dot var(--dur-breath) var(--ease-in-out) infinite;
}

/* ③ 卡片入场（列表页首次渲染 + 分页加载） */
@keyframes fade-up {
  from { opacity: 0; transform: translateY(12rpx); }
  to   { opacity: 1; transform: translateY(0); }
}
.anim-fade-up {
  animation: fade-up var(--dur-normal) var(--ease-out) both;
}

/* ④ 触控按压反馈 */
.tap-scale:active {
  transform: scale(0.96);
  transition: transform var(--dur-fast) var(--ease-spring);
}

/* ⑤ 关注星标填充动画（从空心→实心） */
@keyframes star-fill {
  from { transform: scale(0.6); opacity: 0.3; }
  to   { transform: scale(1);   opacity: 1; }
}
```

**动效使用原则**：
- `dur-fast`：仅用于即时反馈（按钮点击、tab 切换）
- `dur-normal`：入场动画、展开/收起
- `dur-slow`：叙事动画（卡片浸染、页面切换），**不用于循环呼吸**
- `dur-breath`：呼吸循环动画专属（LIVE 脉冲、信号点），必须 `infinite` 循环
- `dur-sway`：中等节奏装饰动画（加载更多待命光晕、箭头浮动、live-pulse 标签脉冲），节奏快于平静呼吸但不过度急促（v18 新增）
- 呼吸类动画的关键帧必须有"峰值停留段"（如 35%-55%），模拟真实呼吸的吸气-保持-呼气节奏，避免急促闪烁感
- **功能性加载动画豁免 Token 化**：加载旋转（spin/lmSpin）、骨架屏（sk-shimmer）、图片淡入（imgfb-fade-in）等"加载反馈"动画不属于装饰氛围，保留各自节奏（v18 明确豁免）
- 所有动画需尊重 `prefers-reduced-motion` 用户偏好（微信小程序可通过 `wx.getSystemInfo` 获取并动态关闭动画类名）

## 2.6 品牌声音规范（Tone of Voice）

> **新增（v7）**：视觉设计语言有了，但文案设计语言缺失。DOTA2 的叙事风格宏大而有仪式感（"Battle of the Ancients"、"Who Will You Choose?"），小程序文案应呼应这种调性而非使用干巴巴的通用提示。

**文案风格三原则**：
1. **竞技场感**：用战场/竞技概念包装功能术语——"加载中"→"正在扫描战场…"
2. **克制不浮夸**：不要中二感（如"勇士，你的征途开始了！"），DOTA2 本身是冷峻硬核的
3. **短促有力**：中文文案控制在 8 字以内，英文参考 DOTA2 游戏内的提示风格

| 场景 | 避免（通用/干巴巴） | 推荐（竞技场风格） |
|---|---|---|
| 加载中 | "加载中…" | "正在扫描战场…" |
| 加载失败 | "加载失败，请重试" | "信号中断，正在重连…" |
| 下拉刷新 | "下拉刷新" | "释放刷新" 或 "↓ 刷新" |
| 空态-无关注 | "还没有关注任何战队" | "你的阵容还是空的——去赛场上招募几支战队吧" |
| 空态-无赛事 | "暂无相关赛事" | "暂无战局" |
| 已结束赛事标签 | "已结束" | "战局已定" |
| 进行中赛事标签 | "进行中" | "正在交锋" |
| 即将到来标签 | "即将到来" | — 保留，清晰度优先 |
| 已关注星标 tooltip | — | "已加入关注阵容" |
| 清除缓存确认 | "确定清除缓存？" | "确认清空本地数据？此操作不可撤销" |
| 隐私协议入口 | "隐私协议" | "隐私与协议" |
| 版本号 | "版本 1.0.0" | — 保持技术格式 |

> **注**：以上文案为风格指南，不要求在 v7 实施中全部替换——可在后续迭代中逐步迁移。关键场景（空态、加载失败、赛事状态标签）优先替换。

### Phase 7：组件三态设计（Loading / Empty / Error）

> **新增（v7）**：当前设计规范仅覆盖"正常态"。电竞数据类 App 依赖第三方 API，加载失败率高于工具类 App，必须有系统的三态设计。
