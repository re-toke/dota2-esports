## 1. P1：阻断是「域名粒度」——这是方案成立的根基

同一次探测里，同一个站的**不同子域命运完全不同**：

| 域名 | 解析 | TLS | 结果 |
|---|---|---|---|
| `api.opendota.com` | **103.73.220.77**（非真实 IP） | ❌ 自签证书 | ❌ 被劫持 |
| **`www.opendota.com`** | 172.67.155.85（**Cloudflare 真实 IP**） | ✅ Google Trust | ✅ **HTTP 200** |
| `opendota.com` | 103.73.220.215（非真实） | ❌ 自签 | ❌ 被劫持 |

⇒ **同一组织的域名，一个被劫持、一个完全正常** ⇒ **阻断/劫持按"域名"而非"IP/整站"做**
⇒ **推论：新域名（不在名单内）有很高概率可用** ✓ —— 这正是方案的前提。

**`*.supabase.co` 全族不可用**（三级验证）：
| 域名 | 现象 |
|---|---|
| `gkticzdaicpdtxheyxsd.supabase.co` | 真实 Cloudflare IP → **TLS 握手 `ECONNRESET`**（**SNI 阻断**） |
| `supabase.co`（根域） | IP 被污染成 76.76.21.21 → `ECONNRESET` |
| `api.supabase.com`（管理域） | IP 被污染 → **自签证书** |
⇒ **换 IP / DoH / hosts 一律无效**（DNS 与握手都不在自己手里）⇒ **只能换域名** ✓

## 2. P2 / P3：中转该挂哪里（实测宿主可达性）

| 宿主人选 | 本网络可达 | 可用性 |
|---|---|---|
| **Cloudflare 边缘**（`dota.haglund.dev` 302 ✓、**`pages.dev` 301 ✓**） | ✅ | **首选**（CF Worker / CF Pages + 自定义域名） |
| `vercel.com` / `app.netlify.com` / `deno.com` | ✅ 200 | 备选（同样边缘分发） |
| `workers.cloudflare.com` | ❌ **TIMEOUT** | ⚠️ 这只是 CF 的营销站；**`*.workers.dev` 本次未测** ⇒ 若要挂 worker，**必须实测那一域名** |
| 国内云（腾讯/阿里控制台） | ✅ 200 | ❌ **不可用作反代** —— 国内服务器连不上 `supabase.co`（P3） |

⇒ **实现选型建议**：**Cloudflare Worker 或 Cloudflare Pages Functions + 自有域名**（免费、边缘可达）；
若自定义域名一时没有，先拿 `*.pages.dev` / `*.workers.dev` 做**可达性实测**再定。

## 3. P4：中转的「形状」已用本地 mock 验证通过 ✅

**客户端拼 URL 的地方全仓只有 4 处**（这就是中转必须承接的全部形状）：
| 位置 | 形状 |
|---|---|
| `utils/supabaseClient.js:78` | `sb().url + '/functions/v1/' + name` |
| `utils/supabaseClient.js:154` | `sb().url + '/rest/v1/' + table + '?select=…'` |
| `utils/api.js:70` | `BASE + path` |
| `utils/liquipedia.js:217` | `BASE + '?' + qs` |

**mock 实测**（按上述拼法逐条发请求 → 中转按前缀路由）：
```
EF  edge()            HTTP=200  body={"data":{"ok":true,"ef":"opendota-proxy",…}}
EF  edge()            HTTP=200  body={"data":{"ok":true,"ef":"liquipedia-proxy",…}}
REST rest()           HTTP=200  body=[{"ok":true,"table":"curation_events"}]
OpenDota BASE+path    HTTP=200  body=[]
OpenDota (带查询)      HTTP=200  body=[]
Liquipedia BASE+?     HTTP=200  body={"parse":{}}
★ 全部路由命中、无 404 ⇒ 单域名 + 路径前缀方案【形状可行】
```
⇒ **客户端只需改 2 个常量**（`config.supabase.url`、`api.js` 的 `BASE`），LP 的 BASE 可选改 ⇒ **改动面极小** ✓

## 4. ★ 两个附带发现（对方案有实际影响）

**① `api.stratz.com` 也**不可靠 —— 同一天两次探测，一次解析到 Cloudflare（TLS OK），
一次解析到劫持 IP `141.193.154.210`（自签）⇒ **DNS 时好时坏**。
⇒ 现在客户端能真正依赖的直连兜底 **只剩 `dota.haglund.dev`**（✓ 实测 302）；`liquipedia.net` 需复测。
⇒ **含义**：中转的可靠性更重要（它将成为主路径，而"兜底"其实所剩无几）。

**② 中转可以「服务端注入正确的 Supabase key」** ⇒ **客户端那个错 `anonKey` 直接变得无害** ✓
⇒ **修 key 与换域名可以合并为同一次改动**（甚至不修 key 也能工作）——
这让 R3 的改动量与风险都下降。

## 5. ⚠️ 我无法在此验证的环节（**这是方案唯一的不确定点**）

| 环节 | 为什么测不了 | 怎么闭环 |
|---|---|---|
| **中转部署后是否国内可达** | 需要一个**真实域名 + 托管账号**（我没有） | 见下方"最小验证" |
| **中转能否连上 Supabase** | 本网络到 Supabase 已断 ⇒ 只能在中转服务器上测 | 部署后在中转上 `curl` 一次 EF |
| **域名是否"时而可用时而不可用"** | 需长期观测（`api.stratz.com` 已现此症状） | 预留**备用域名**；客户端支持双域名切换 |

### 最小验证（约 10 分钟，做完就能判定"成/不成"）
1. 你在 **Cloudflare**（或 Vercel/Deno Deploy）建一个最小反代（我可以把代码写好给你，复制即用）；
2. 拿到中转域名后，**先用沙箱测**（我这边能测国内可达性）⇒ 若通，再用**你的手机**开一次：
   - 浏览器打开 `https://<中转域名>/sb/functions/v1/opendota-proxy` ⇒ **期望返回 JSON（不是连接重置/证书错）**；
3. 若第 2 步通过 ⇒ **方案成立**，接着改客户端 2 个常量 + 发版；
4. 若第 2 步不通 ⇒ 换域名/换宿主（备选清单见 §2），或走**双域名 + 直连 haglund** 的降级组合。

## 6. 一句话回答"能不能实现想要的结果"

**能 —— 方案的三条根基（域名粒度阻断、境外边缘可达、形状可承接）全部实测通过，客户端改动只有 2 个常量。**
**唯一没验证的是"某个具体域名在你手机上是否可达"**，这需要一个真实域名（10 分钟可闭环）——
所以下一步不是改代码，而是**先落一个最小中转做可达性实测**。
