## R1 ❌ P4 不成立（我的过度声称）

原文称 `section`/`stageLabel = "{{Stage|Playoffs}}"` 是"会漏到 UI 的脏串"。

**核验**：`grep -rn "stageLabel|\.section" --include=*.wxml .` ⇒ **零命中**。
该 wxml 里出现的 `section` 全是**样式类名**（`source-section` / `lp-section-title`），非字段引用。

⇒ **该脏值当前不可见**。应**从问题清单移除**，或降级为"**内部脏值（隐患）**"。
（★ 仍有价值：它是 `classifyStage` 的输入，说明**上游把原始 wikitext 直接塞进了字段**。）

## R2 ❌ P2「同一卡互斥文案」表述错误（我的过度声称）

原文称 `isLive=true` 与 `countdownText='即将开始'` 并存是"同卡互斥文案"。

**核验**（`league-detail.wxml` L228-237）：
```xml
<text wx:if="{{s.phase === 'live'}}">● LIVE</text>
<text wx:if="{{s.phase === 'live' && s.liveProgress}}">· {{s.liveProgress}}</text>
<text wx:if="{{s.phase === 'live' && s.elapsedText}}">· 已进行 {{s.elapsedText}}</text>
<text wx:elif="{{s.phase === 'upcoming'}}">{{s.scheduledTimeText}}</text>
```
⇒ **渲染完全由 `s.phase` 决定**；upcoming 分支渲染的是 `scheduledTimeText`，**不是 `countdownText`**。

⇒ **"互斥文案"不是用户可见的矛盾**，只是**内部两个字段不一致**。
⇒ 应改写为「**内部两条判定路径不一致（隐患）**」；**可见后果并入 P1/P3**：
用户实际看到的是 **`● LIVE · 已进行 2h 19m`**（这才是真问题）。

## R3 ⚠️ P5 机理定位错误 —— 且**我上轮的 P0-a 修法对本案无效**

### 判别实验（Node 直接调 `utils/sources.js` 的 `applyBo`，用**实测卡片字段**）
```js
series = { seriesType: null, mapSlots: 5, declaredBo: null, phase: 'live',
           stageKey: 'playoff', section: '{{Stage|Playoffs}}', games: [], scoreA: 0, scoreB: 0 }
```
| ctx | 输出 |
|---|---|
| **空 ctx** | **BO5** ← ★ `mapSlots=5` 本身**会生效为 BO5** |
| `{stages:{}}` | BO5 |
| `{metaFormatBo:'BO3'}` | **BO3** ← S2 抢先 |
| `{boFormat:{playoff:'BO3'}}` | BO3 |
| **`{boFormat:{playoff:'BO3', grandFinal:'BO5'}}`** | **BO3** ← ★★ **补 grandFinal 也没用！** |
| `{boFormat:{...}, uniBo:'BO3'}` | BO3 |

### 修正后的机理
该卡 `stageKey = 'playoff'`（由 `classifyStage('{{Stage|Playoffs}}')` 推出，**是"淘汰赛"的粗粒度总称**）
⇒ 任何"**按 stageKey 取赛制**"的机制（S2/S4）**必然取到 playoff 的 BO3**
⇒ 而真正更精确的信号 —— **单场模板块位 `mapSlots=5`** —— 被排在 **S4.5（低优先级）** ⇒ 被 S2 抢先。

★★ **⇒ 我上一轮的 P0-a（"给赛事补 `boFormat.grandFinal:'BO5'`"）对这张卡无效**：
这张卡的 `stageKey` 是 `playoff` 而非 `grandFinal` ⇒ 取不到 `grandFinal` 的值。实验第 5 行已实证。

### ★ 但也不应简单"把 mapSlots 提到高优先级"
代码注释自述："**BO5 偶占 4 槽**"、"3/4 槽 → BO3（保守）" ⇒ **槽位数与 BO 不是严格映射**
⇒ 作者把 `mapSlots` 放低优先级**是有权衡的** ⇒ 直接提升会增加"**BO3 误判成 BO5**"的**反向风险** ⚠️

## R4 ⚠️ 修法需要重做：把「**BO 显示**」与「**终局判定**」拆开

| 维度 | 建议 | 理由 |
|---|---|---|
| **BO 显示** | **保持现状或标注"不确定"**，**不要盲目调优先级** | `mapSlots` 与 BO 非严格映射（4 槽可能 BO5 也可能 BO3）⇒ 改了会引入反向误判 |
| **终局判定** | ★ **用"可能的最大 BO（上限）"而非"判定出的 BO"** 判"是否已结束" | 天然保守：若存在 `mapSlots>=5` 等"更大 BO"信号 ⇒ **不得**用 BO3 阈值把 2:1 判成终局 |

⇒ ★★ **本议题与「BO5 被判成 BO3」议题在此合流**：
两处的正解是**同一个** —— **"不得提前判终局"的安全兜底**（宁可显"进行中"，由既有 `isStaleLiveSeries` 3h 兜底收尾）。

## R5 ⚠️ 我的 P0「零数据占位不得判 live」**有反向风险**，必须加限定

**原判据**：`games=[] && matchIds=[] && 0:0` ⇒ 至多 `upcoming`、绝不 `live`。

**风险**：**OpenDota 对"刚开始的比赛"可能收录滞后**（`games` 暂空、比分 0:0）
⇒ 会把**真-live** 降级成 `upcoming` ⇒ 用户看到"即将开始"而比赛正在打 ❌ **反向错误**

**修正建议（按风险从低到高）**：
1. ★ **推荐先做"显示层收口"**（风险最小）：
   `games=[] && matchIds=[]` 时**不渲染** `● LIVE` 与"· 已进行 X"（或改渲染 `scheduledTimeText`）
   ⇒ 直接消除用户看到的错误信息，**不动任何判定逻辑**
2. 再加**更精确的判据**（不是"零数据"这么宽）：**该系列来自 LP 排期占位**（`key` 前缀 `liq-`）
   **且**对手为 `TBD`/未定（`team2Name==='TBD'`）⇒ 才不得判 live
3. ⚠️ **不要**用"零数据"作为唯一判据

## R7 🆕 复核中新发现：`resolveBoType` 对"非空但不完整"的 ctx 会抛异常

```js
const ev = c.stages[stageKey];   // ← c = ctx || {...default}; 若 ctx = {} ⇒ c.stages === undefined
```
**实证**：传 `ctx = {}` 且 `mapSlots=0`（走到 S4 之后的行）⇒
`ERR: Cannot read properties of undefined (reading 'playoff')`

⇒ 建议 `(c.stages || {})[stageKey]`。**与本案无关，但属健壮性缺陷**（调用方传 `{}` 很常见）。
