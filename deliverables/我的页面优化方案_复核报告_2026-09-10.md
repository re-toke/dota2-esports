## 一、实质错误（按严重度）

### ❌ 错误 1（严重）：B9「提醒静默失效」是**假警报**

**我的原判断**：
> 关闭云同步后，赛前提醒仍显示「已开启」但推送已死 → v8.41 引入的耦合缺口

**核查结果 —— 不成立**：

| 核查项 | 事实 |
|---|---|
| 生效的推送链路 | **客户端触发**：首页 `index.js:1567` `checkPreMatchReminders` → `reminderStrategy.evaluate` → `subscribe.sendSubscribeMessage` |
| 该链路依赖什么 | `getOpenIdSync()` / `ensureOpenId()` —— 即 **openid（登录）**，**不是云同步** |
| 服务端批量推送 `smart-reminders` | **未接线**（全仓仅 2 处注释提及，客户端零调用） |
| 云端 profile 的作用 | 只服务 `smart-reminders`（未接线）+ `restoreSubFromCloud`（恢复） → **与「发送」无关** |

**真实影响**（比原判断轻得多）：
关闭同步 → `syncSubStatus` / `restoreSubFromCloud` 被守卫拦 →
**换机或清缓存后，订阅授权状态无法恢复**（症状：「以前授权过，重装又提示授权」）。
**不是**「推送失效」。

**修正**：B9 从 **P0 降为 P1**，改为「关闭同步影响的是**恢复**能力，而非推送」，
修法从「联动关闭提醒」改为 **提示文案**：
> 关闭后：换设备/清缓存将无法自动恢复提醒授权状态（推送本身不受影响）

> ★ 教训：我把「云端有 profile」误当成「推送的必要条件」，忽略了实际生效的是客户端触发链路。
> **判「静默失效」前必须确认哪条链路是活的**，不能只看数据流。

### ❌ 错误 2：B2「chips 置灰不可点」方向错了

**我的原方案**：未订阅时把提前量/级别 chips **置灰不可点**，让用户「看到能怎么配」。

**核查结果 —— 会造成能力倒退**：
- 提前量/级别是**纯本地策略**（`reminderStrategy`，存本地 `dota2_*`）
- **首页本地检查用同一套策略**（`index.js:1567/1589`）
- 置灰 = 用户在未订阅时**无法预先配置**，且会误以为「不开提醒就不能配」

**修正**：改为 **常显且可编辑**。未开启时靠**状态徽章**（已有「未开启」）区分，
而不是禁用控件。开启提醒后策略立即生效，无需重新配置。

## 三、方案漏洞（原方案未覆盖）

### 漏洞 1（严重）：**云端孤儿没有清理入口**

A2 会造成云端孤儿。但我方案里的「删除云端数据（关闭云同步）」**依赖开关处于开启态** ——
孤儿场景下开关显示「未开启」，**这个入口就点不动了** → 用户永远删不掉。

**修正**：该入口必须设计为 **恒定可用**（与开关状态无关）：
点击 → 先 `ensureLogin()` 拿 JWT → 调 EF delete → 按结果如实提示。

---

### 漏洞 2（严重）：★ **`cloudSync.disable()` 在无 JWT 时会「假装删除成功」**

这是我 **v8.41 自己埋的坑**：

```js
function disable() {
  var jwt = auth.getJwtSync();
  if (!jwt) {
    finishLocal();               // ← 本地直接置为「未开启」
    _setStatus('off');
    return Promise.resolve({ ok: true, reason: 'no_jwt' });   // ← 返回成功
  }
  ...
}
```

**问题**：若本地 JWT 被清掉（如用户执行过清缓存、或 JWT 30 天过期）而**云端仍有数据**，
此时点关闭 → **返回 `ok:true`、UI 提示「已关闭并删除云端数据」，但云端根本没删** → **虚假承诺**。

**修正**：无 JWT 时**不应直接成功**，应：
1. 先 `ensureLogin()` 尝试拿回 JWT（同一用户 openid 不变，能拿回）
2. 拿到 → 正常删除
3. 拿不到（网络/登录失败）→ 本地可关，但状态置 `failed` + 文案如实说「**云端数据未能删除，可重试**」

> 这条与隐私协议的删除权承诺直接相关 —— **不能报假成功**。

---

### 漏洞 3：`clearCache` 改「保留开关状态」缺少**清理清单**

方案说「保留 `dota2_cloud_sync`」，但 `wx.clearStorageSync()` 是一刀切，要改成按 key 清，
就必须明确**哪些 key 属于缓存、哪些属于账号态**（否则容易漏掉新 key 或误删账号态）。

**修正**：明确三类清单并写成常量，便于后续维护：

| 类别 | 处理 | 示例 key |
|---|---|---|
| 缓存类（可清） | 清除 | `dota2_leagues_*` / 搜索历史 / logoCache / logo 负命中 |
| 账号态（**保留**） | 保留 | `dota2_cloud_sync`（开关状态） |
| 凭证类（需按需处理） | **视场景** | `dota2_openid` / `dota2_jwt` —— 清缓存时保留（否则要重新登录）；「重置全部」时清除 |

---

### 漏洞 4（补充）：「重置全部」的**执行顺序与失败处理**未定义

若先清本地再删云端 → JWT 没了 → **删不掉云端** → 又造一个孤儿。

**修正**：顺序必须是 **① 登录取 JWT → ② 删云端 → ③ 成功后才清本地**；
若 ② 失败 → **中止**并提示「云端删除失败，本地数据未清除」（避免制造新的不一致）。

## 五、复核方法论沉淀

本次复核之所以能抓出假警报，靠的是**同一动作**：对每条「X 会失效/矛盾」的论断，
回去确认**哪条代码路径是实际生效的**（而非哪条在仓库里存在）。

具体到本次：
- 我说「推送依赖云端 profile」→ 实际生效路径是**客户端触发**，`smart-reminders` 未接线
- 我说「降级态是 P0」→ 实际 `TMPL_ID` 已配置，该分支**不可达**
- 我说「chips 置灰无害」→ 实际策略**同时驱动本地检查**，置灰是能力倒退

**三条通用自查清单**（建议后续方案都过一遍）：
1. **可达性**：这个分支/状态在当前配置下真的会发生吗？
2. **活链路**：我引用的机制是生效的那条，还是仅存在于代码里的死代码？
3. **副作用面**：这个设置项除了被我提到的功能使用，还有别处消费吗？
