## 二、本次新查清的事实（此前从未核实）

### ① 三个定时触发器的真实职责（终于读到实现）

```
schedulePreheat（30min 轻量）→ handleSchedulePreheat
  · preheatUpcoming()        → 写 upcoming_schedule（6h TTL：列表页「即将」tab + 首页秒开）
  · preheatScheduledMatches  → 预热 SCHEDULED_MATCHES_SLUG_OVERRIDE 页缓存（详情页秒开）
  指数退避：失败退避至 4h，防故障时打爆

cacheRefresh（6h 重任务）→ handleTimer
  · 上述两项 + refreshTeams（热门战队）
```

**关键洞察**：这些预热的产物是**云端缓存 key**（`upcoming_schedule` 等），
**预热的作用是让客户端调用「秒回」**。

→ **关停云开发 = 这两条预热链路消失** —— 而这恰好是「首页秒开 / 详情页秒开」的实现手段。

### ② 云开发 DB 有 **5 个集合**（此前只讨论了 curation_events）

```
aggregation_cache    云端缓存 L2（定时预热的写入目标）
curation_events      2,414 条（+ 每日发现写入）
curation_teams
curation_meta
admin-logs           告警 / 审计（管理后台数据源）
```

「完全脱离」需要处理**全部 5 个**，不是 1 个。

## 三、🔧 修正一个此前的错误判断（这是好消息）

**我此前对方案④ `getUpcomingSchedule` 的判断是错的。**

| | 我此前的判断 | 实际情况 |
|---|---|---|
| ④ 的本质 | 「服务端**实时聚合**多个赛事 → 一次性返回」 | **定时预热写缓存（`upcoming_schedule`）+ 客户端读缓存** |
| 难度 | 「最复杂、要重写聚合逻辑、建议先量化收益」 | **与 LP / KV 同构** —— 把预热产出物写进 Supabase，客户端直读即可 |

→ ④ 的难度**被严重高估**。它和通用 KV 是同一类问题：**「定时任务产出 → 写表 → 客户端直读」**。
→ 而且它与 ①（cacheRefresh / schedulePreheat 迁移）**是同一件事** —— 预热产出物直接写 Supabase 即可，双赢。

## 四、⚠️ 我明确未核实的 4 项（诚实清单）

| # | 未核实项 | 为什么重要 |
|---|---|---|
| 1 | `refresh-wx-token` / `smart-reminders` / `subscribe-send` 三个 EF 的**触发机制** | Supabase EF **没有内建定时器**（微信云开发有 timer）。若没人配 pg_cron / 外部调度 → **它们根本没在跑**，「智能提醒」可能是死的 |
| 2 | 客户端是否有路径**读 `upcoming_schedule`** | 若有 → 那就是④的迁移对象；若没有 → 预热只服务云函数自身 L1 缓存，关停后自然消失、无需迁移 |
| 3 | `admin/` 管理后台**怎么读数据** | 直连云开发 DB？还是经云函数？决定它是否必须改造 |
| 4 | 云开发侧 `aggregation_cache` 是否还有**消费者** | 若客户端仍经某条路径读它，关停会坏 |

**这 4 项没有核实之前，任何「完全脱离」的时间表都是不可信的。**
