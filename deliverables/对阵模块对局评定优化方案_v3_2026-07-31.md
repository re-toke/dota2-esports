## 二、v2.1 方案问题修复（优化项 19-26）

### 优化项 19：isRecent 字段语义修复 — 统一时间单位与计算逻辑（修复 P1/P2）

#### 问题描述

v2.1 优化项18的修复代码存在两个问题：

1. **时间单位混用**：`groupSeries` 中 `isRecent` 用毫秒计算（`(now - lastEnd) < 2 * 3600 * 1000`），而 v2.1 修复代码用秒计算（`(fmtNowSec - lastEnd) < 2 * 3600`）。虽然 Liquipedia 补充赛程确实用秒级 `startTime`，但与 `groupSeries` 语义不统一。

2. **lastEnd 计算错误**：v2.1 写 `const lastEnd = m.startTime || 0`，把开赛时间当作结束时间。但 `groupSeries` 的 `lastEnd` 是 `last.start_time + last.duration`（实际结束时间）。Liquipedia 补充赛程没有 `duration` 字段。

#### 修复方案

Liquipedia 补充赛程的 `isRecent` 应基于 Liquipedia 的 `finished` 标记 + 时间估算：

```js
// league-detail.js Liquipedia 赛程转换中
// 原方案（v2.1）：const lastEnd = m.startTime || 0;
//                const isRecent = lastEnd && m.phase === 'recent' && (fmtNowSec - lastEnd) < 2 * 3600;

// 修复后（v3）：
// 对于已结束的 Liquipedia 比赛，用 finished 标记判定，不依赖精确结束时间
// isRecent 语义统一为「2h内结束」，但 Liquipedia 无 duration，改为：
//   - phase==='recent' 且 startTime 距现在 < 4h（假设比赛最长 2h，2h内开始且已结束 = 2h内结束）
//   - 如果 startTime 距现在 > 4h 但 phase==='recent'，不算 isRecent（太早结束的已不"新鲜"）
var liqIsRecent = false;
if (m.phase === 'recent' && m.startTime > 0) {
  var elapsedSec = fmtNowSec - m.startTime;
  // 估算：已结束且从开赛到现在 < 4h（2h比赛 + 2h缓冲）
  // 超过 4h 的已结束比赛不算"新鲜"
  liqIsRecent = elapsedSec > 0 && elapsedSec < 4 * 3600;
}
// 赋值
isRecent: liqIsRecent,
```

**设计说明**：Liquipedia 补充赛程无 `duration`，无法精确计算结束时间。用 `startTime + 4h` 窗口估算（2h 比赛时长 + 2h 缓冲），确保「刚结束」的语义与 `groupSeries` 一致（2h 内结束的才算 isRecent）。

#### 变更

| 文件 | 修改内容 |
|------|---------|
| `league-detail.js` L464-465 | `isRecent` 改为基于 `startTime + 4h` 窗口估算 |

### 优化项 20：僵死检测 — 精确定义基准时间 + BO1 特殊处理（修复 P3/P4）

#### 问题描述

v2.1 优化项13/17 的僵死检测存在两个问题：

1. **6h 基准时间未定义**：方案说"6h 无更新自动降级"，但未明确基准是 `last.start_time`（最后一场开赛时间）还是 `lastEnd`（最后一场结束时间）。对于未结算比赛，`last.duration` 可能为 0 或已有值（OpenDota 对 live 比赛返回实际持续时间），导致 `lastEnd` 不稳定。

2. **BO1 僵死检测失效**：优化项17 的 `BO_WIN_THRESHOLD['BO1'] = 1`，但 BO1 中唯一一场未结算时 `scoreA=0, scoreB=0`，不满足 `scoreA >= 1`，BO 胜场检测不触发。

#### 修复方案

**统一基准时间**：使用 `last.start_time`（最后一场开赛时间，秒级）作为僵死检测基准，不依赖 `duration`：

```js
// sources.js groupSeries 中，isLive 判定后增加僵死检测
// 基准：最后一场的开赛时间（不依赖 duration，因为 live 比赛的 duration 不稳定）
const lastStartSec = last.start_time || 0;

// 僵死检测：分两层
// 第一层：时间阈值（适用所有 BO 类型，特别是 BO1）
//   最后一场开赛超 6h 且仍未结算 → 数据异常，降级为 recent
if (isLive && lastStartSec > 0 && (nowSec - lastStartSec) > 6 * 3600) {
  // 检查是否有其他正在进行的场（如 BO5 中第4场已结束、第5场刚开赛）
  // 如果最后一场开赛在 6h 内，不降级
  // 如果最后一场开赛超 6h，检查倒数第二场是否在 6h 内
  var prevStartSec = games.length > 1 ? games[games.length - 2].start_time || 0 : 0;
  if (!(prevStartSec > 0 && (nowSec - prevStartSec) <= 6 * 3600)) {
    isLive = false;
  }
}

// 第二层：BO 胜场条件（适用 BO3/BO5，BO1 已被第一层覆盖）
//   已结算场数已达 BO 胜场条件 → 系列赛实际已结束，降级为 recent
//   注意：BO1 的阈值=1，但未结算时 scoreA=0，不触发，依赖第一层时间检测
const BO_WIN_THRESHOLD = { 'BO3': 2, 'BO5': 3, 'BO2': 2, 'BO1': 1 };
const winThreshold = BO_WIN_THRESHOLD[boType] || 0;
if (isLive && winThreshold > 1 && (scoreA >= winThreshold || scoreB >= winThreshold)) {
  isLive = false;
}
// winThreshold > 1 排除 BO1（BO1 靠时间检测）
```

**设计说明**：
- 第一层时间检测覆盖所有 BO 类型（特别是 BO1）
- 第二层 BO 胜场检测仅对 BO2+ 生效（`winThreshold > 1`），避免 BO1 的无效检测
- 检查倒数第二场开赛时间，避免 BO5 中"第4场6h前开赛但第5场刚开赛"的误降级

#### 变更

| 文件 | 行号 | 修改内容 |
|------|------|---------|
| `sources.js` groupSeries | L847-855 | 僵死检测改为双层：6h 时间基准（last.start_time）+ BO 胜场条件（winThreshold > 1） |

### 优化项 21：UPCOMING 窗口分页 — 3天窗口 + 按日期折叠（修复 P5/P6）

#### 问题描述

v2.1 优化项5/14 将 UPCOMING 窗口从 2 天扩展到 3 天，但存在两个问题：

1. **列表膨胀**：TI 小组赛 3 天内可能有 15+ 场比赛，全部显示为 UPCOMING 列表过长。
2. **far_future 静默丢弃**：超过 3 天的 UPCOMING 标记为 `far_future` 后，在三段式排序中被丢弃，用户无法查看 3 天后赛程。

#### 修复方案

**取消 far_future 标记，改为按日期分组 + 折叠展示**：

```js
// sources.js groupSeries 中
// 原方案（v2.1）：超 3 天标记为 far_future
// if (s.phase === 'upcoming' && s.lastTime > nowSec + 3 * 86400) {
//   s.phase = 'far_future';
// }

// 修复后（v3）：不改变 phase，增加 dateGroup 字段供 UI 分组
if (s.phase === 'upcoming' && s.lastTime > 0) {
  // 计算日期分组（北京时间）
  var bjTime = s.lastTime + 8 * 3600;
  var bjDay = Math.floor(bjTime / 86400);
  var nowBjDay = Math.floor((nowSec + 8 * 3600) / 86400);
  var dayOffset = bjDay - nowBjDay; // 0=今天, 1=明天, 2=后天, ...
  s.dateGroup = dayOffset; // 供 WXML 按日期分组
}
```

```js
// league-detail.js 三段式排序中
// 不再丢弃 far_future，而是将所有 upcoming 都保留
// 按日期分组排序：同一天内按 lastTime asc，天之间按日期 asc
upcomingList.sort(function (a, b) {
  // 先按日期分组
  var dayDiff = (a.dateGroup || 0) - (b.dateGroup || 0);
  if (dayDiff !== 0) return dayDiff;
  // 同一天内按时间升序
  return a.lastTime - b.lastTime;
});
```

**WXML 展示**：UPCOMING 段按日期插入轻量分隔线，3 天以上折叠：

```xml

  <view class="date-sep">{{item.label}}</view>
  <block wx:for="{{item.series}}" wx:key="key">
    <!-- 对阵卡片 -->
  </block>
</block>
<!-- 3天后赛程折叠入口 -->
<view wx:if="{{hasFarFuture}}" class="far-future-toggle" bindtap="toggleFarFuture">
  {{showFarFuture ? '收起远期赛程' : '查看更远赛程 (' + farFutureCount + '场)'}}
</view>
```

**league-detail.js 增加日期分组逻辑**：

```js
// 在三段式排序后，对 upcomingList 按日期分组
var upcomingGroups = [];
var currentGroup = null;
upcomingList.forEach(function (s) {
  var day = s.dateGroup || 0;
  var label;
  if (day === 0) label = '今天';
  else if (day === 1) label = '明天';
  else if (day === 2) label = '后天';
  else label = (day + 1) + '天后';

  // 3天以内的默认展示，3天以上折叠
  if (day <= 2) {
    if (!currentGroup || currentGroup.day !== day) {
      currentGroup = { day: day, label: label, series: [] };
      upcomingGroups.push(currentGroup);
    }
    currentGroup.series.push(s);
  }
});
// 3天以上的单独统计
var farFutureCount = upcomingList.filter(function(s) {
  return (s.dateGroup || 0) > 2;
}).length;
```

function extractTeamOpponent(raw) {
  if (!raw) return { name: '', score: 0 };
  var m = raw.match(/\{\{TeamOpponent\s*\|([^}]*)\}\}/i);

  var name = extractTeamOpponentName(raw); // 复用现有提取逻辑
  return { name: name, score: score };
}

// 在 parseMatchFields 中使用
var opp1 = extractTeamOpponent(fields.opponent1 || '');
var opp2 = extractTeamOpponent(fields.opponent2 || '');
// ...
return {
  team1Name: opp1.name,
  team2Name: opp2.name,
  score1: opp1.score,   // 新增
  score2: opp2.score,   // 新增

  finished: finished,
  phase: phase

### 优化项 23：section 字段提取 — 在 getScheduledMatches 层解析标题层级（修复 P8）

#### 问题描述

v2.1 优化项7/8/14 都依赖从 Liquipedia 提取 `section` 字段（如 "Group Stage"、"Playoffs"），但 `section` 不在 `{{Match}}` 模板内，而在 wikitext 的标题层级中：

```wikitext
== Group Stage ==
=== Group A ===
{{Match|...}}
{{Match|...}}

=== Group B ===
{{Match|...}}

== Playoffs ==
=== Upper Bracket ===
{{Match|...}}
```

`parseMatchFields` 只解析 `{{Match}}` 模板参数，无法获取 section。

#### 修复方案

**在 `getScheduledMatches`（或 `liquipedia-parse.js` 的 `parseScheduleFromWikitext`）中维护当前 section 上下文**：

```js
// liquipedia-parse.js 中新增 section 解析逻辑
// 在遍历 wikitext 行时，维护当前 section 上下文

function parseScheduleFromWikitext(wikitext) {
  var lines = wikitext.split('\n');
  var currentSection = '';
  var currentSubsection = '';
  var matches = [];

  lines.forEach(function (line) {
    line = line.trim();
    // 检测二级标题（== Section ==）
    var h2 = line.match(/^==\s*([^=]+?)\s*==$/);
    if (h2) {
      currentSection = h2[1].trim();
      currentSubsection = '';
      return;
    }
    // 检测三级标题（=== Subsection ===）
    var h3 = line.match(/^===\s*([^=]+?)\s*===$/);
    if (h3) {
      currentSubsection = h3[1].trim();
      return;
    }
    // 检测 {{Match|...}} 模板
    if (line.indexOf('{{Match') === 0 || line.indexOf('{{ Match') === 0) {
      // 提取 Match 模板内容
      var body = line.replace(/^\{\{\s*Match\s*\|?/, '').replace(/\}\}\s*$/, '');
      var parsed = parseMatchFields(body);
      if (parsed) {
        // 注入 section 上下文
        parsed.section = currentSection;
        parsed.subsection = currentSubsection;
        matches.push(parsed);
      }
    }
  });

  return matches;
}
```

### 优化项 24：Liquipedia 时区解析修正（修复 P9）

#### 问题描述

`parseLiquipediaDate` 去掉时区缩写（如 CEST、PST）后按 UTC 解析：

```js
// 当前代码
var cleaned = dateStr.replace(/\{\{[^}]*\}\}/g, '').trim();
cleaned = cleaned.replace(/\s+[A-Z]{3,5}\s*$/, '').trim(); // 去掉时区缩写
// 然后按 Date.UTC 解析
```

但 Liquipedia 标注的日期通常按赛事举办地时区。例如 `April 22, 2024 - 13:00 {{Abbr/CEST}}` 中的 13:00 是 CEST（UTC+2）时间，去掉 `{{Abbr/CEST}}` 后按 UTC 解析会差 2 小时。

#### 修复方案

**保留时区信息并正确转换**：

```js
// liquipedia-parse.js parseLiquipediaDate 中
function parseLiquipediaDate(dateStr) {
  if (!dateStr) return 0;
  // 去掉 {{Abbr/XXX}} 模板但保留时区名
  var cleaned = dateStr.replace(/\{\{[^}]*\}\}/g, '').trim();

  // 提取时区缩写（在时间末尾）
  var tzMatch = cleaned.match(/\s+([A-Z]{3,5})\s*$/);
  var tzAbbr = tzMatch ? tzMatch[1] : '';
  cleaned = cleaned.replace(/\s+[A-Z]{3,5}\s*$/, '').trim();

  // 时区偏移表（常见电竞赛事时区）
  var TZ_OFFSET = {
    'UTC': 0, 'GMT': 0,
    'CEST': 2, 'CET': 1,    // 欧洲
    'EST': -5, 'EDT': -4,   // 美东
    'PST': -8, 'PDT': -7,   // 美西
    'CST': 8,               // 中国（也可能是美中 -6，但 Dota2 赛事多用北京时间）
    'KST': 9,               // 韩国
    'MSK': 3,               // 莫斯科
    'TRT': 3,               // 土耳其
    'AST': 3,               // 阿拉伯标准时间
    'GST': 4,               // 海湾标准时间
    'BRT': -3,              // 巴西
    'ICT': 7,               // 印度支那
    'WIB': 7                // 印尼西部
  };
  var tzOffset = TZ_OFFSET[tzAbbr] != null ? TZ_OFFSET[tzAbbr] : 0;

  // 解析日期时间
  var m1 = cleaned.match(/(\w+)\s+(\d+),\s*(\d{4})\s*[-–]?\s*(\d{1,2}):(\d{2})/);
  if (m1) {
    var monthMap = {
      'january': 0, 'february': 1, 'march': 2, 'april': 3, 'may': 4, 'june': 5,
      'july': 6, 'august': 7, 'september': 8, 'october': 9, 'november': 10, 'december': 11
    };
    var monthIdx = monthMap[m1[1].toLowerCase()];
    if (monthIdx == null) return 0;
    // 按时区偏移计算 UTC 时间
    var d = new Date(Date.UTC(parseInt(m1[3]), monthIdx, parseInt(m1[2]),
      parseInt(m1[4]) - tzOffset, parseInt(m1[5])));
    return Math.floor(d.getTime() / 1000);
  }
  // ... 其余解析逻辑同步修改
}
```

**风险控制**：如果时区缩写未在 `TZ_OFFSET` 表中，偏移为 0（退化为当前行为），不会导致更差的结果。

### 优化项 25：多源去重增强 — 队名模糊匹配（修复 P11）

#### 问题描述

当前去重用 `toLowerCase().replace(/\s+/g, '')` 归一化，但不处理 Liquipedia 全名 vs OpenDota 缩写的情况。例如：
- Liquipedia: "Team Falcons" → `teamfalcons`
- OpenDota: "Falcons" → `falcons`

两者不一致，导致同一对阵未被去重，在列表中重复显示。

#### 修复方案

**增加队名后缀清理，提升匹配率**：

```js
// league-detail.js 中，扩展 dedupeKey 函数
function normalizeTeamNameForDedup(name) {
  if (!name) return '';
  var n = String(name).toLowerCase().trim();
  // 去掉常见后缀：esports / gaming / team / e-sports
  n = n.replace(/\s*(esports|e-sports|gaming|team|club)\s*$/g, '');
  // 去空格和标点
  n = n.replace(/[^a-z0-9一-鿿а-яё]/g, '');
  return n;
}

function dedupeKey(n1, n2) {
  if (isTBD(n1) || isTBD(n2)) return null;
  var k1 = normalizeTeamNameForDedup(n1);
  var k2 = normalizeTeamNameForDedup(n2);
  if (!k1 || !k2) return null;
  return k1 + '__' + k2;
}
```

**双向匹配**：队名 A 包含队名 B 或反之（长度 >= 3）：

```js
function fuzzyMatchName(a, b) {
  var na = normalizeTeamNameForDedup(a);
  var nb = normalizeTeamNameForDedup(b);
  if (!na || !nb || na.length < 3 || nb.length < 3) return false;
  if (na === nb) return true;
  // 包含关系（短名是长名的子串）
  return na.indexOf(nb) >= 0 || nb.indexOf(na) >= 0;
}
```

在去重时，除了精确匹配归一化键，还增加模糊匹配：

```js
// 构建 openDotaKeys 时同时存储归一化名
var openDotaNames = []; // [{ normalized, key }]
this.allSeries.forEach(function (s) {
  if (s.radiantName && s.direName) {
    var k1 = dedupeKey(s.radiantName, s.direName);
    if (k1) {
      openDotaKeys.add(k1);
      openDotaKeys.add(k1.split('__').reverse().join('__'));
    }
    openDotaNames.push({
      n1: normalizeTeamNameForDedup(s.radiantName),
      n2: normalizeTeamNameForDedup(s.direName)
    });
  }
});

// 过滤 Liquipedia 赛程时
liqSeries = liqScheduled.filter(function (m) {
  if (!m.team1Name || !m.team2Name) return false;
  var k = dedupeKey(m.team1Name, m.team2Name);
  if (!k) return true; // TBD 阵容直接保留
  var kRev = k.split('__').reverse().join('__');
  if (openDotaKeys.has(k) || openDotaKeys.has(kRev)) return false; // 精确匹配去重

  // 模糊匹配去重（新增）
  var ln1 = normalizeTeamNameForDedup(m.team1Name);
  var ln2 = normalizeTeamNameForDedup(m.team2Name);
  for (var i = 0; i < openDotaNames.length; i++) {
    if ((fuzzyMatchName(ln1, openDotaNames[i].n1) && fuzzyMatchName(ln2, openDotaNames[i].n2)) ||
        (fuzzyMatchName(ln1, openDotaNames[i].n2) && fuzzyMatchName(ln2, openDotaNames[i].n1))) {
      return false; // 模糊匹配成功，去重
    }
  }
  return true; // 保留
});
```

## 九、FAQ

### Q1：v3 相比 v2.1 的核心变化是什么？

v3 修复了 v2.1 中 12 处方案漏洞（时间单位混用、BO1 僵死检测失效、far_future 静默丢弃、比分提取实现缺失、section 解析层级错误等），新增 8 项优化（community 重复计权修复、cancelled 过滤、setData 性能优化、时区解析修正等），细化了 5 个优化项的实现方案。

### Q2：为什么僵死检测要分两层？

- 第一层（时间检测）：覆盖所有 BO 类型，特别是 BO1（BO1 无 BO 胜场条件可检测）
- 第二层（BO 胜场检测）：仅对 BO2+ 生效，更精确地检测"实际已结束但数据未更新"的场景
- 两层独立工作，互不干扰

### Q3：为什么取消 far_future 而改为折叠展示？

far_future 标记导致超 3 天的赛程被静默丢弃，用户无法查看。改为折叠展示既控制了列表长度，又保留了查看能力。对于 TI 等长赛程赛事，用户可以展开查看完整赛程。

### Q4：Liquipedia 比分从哪里提取？

从 `{{Match}}` 模板中 `{{TeamOpponent|队名|score=N}}` 的 `score` 参数提取。当前 `parseMatchFields` 只提取队名（`extractTeamOpponentName`），v3 新增 `extractTeamOpponent` 同时提取队名和比分。

### Q5：section 为什么不在 Match 模板中？

Liquipedia 的赛程结构是：
```
== Group Stage ==
=== Group A ===
{{Match|...}}
{{Match|...}}
== Playoffs ==
{{Match|...}}
```
section 信息在 wikitext 标题层级中（`==` / `===`），不在 `{{Match}}` 模板参数内。需要在遍历 wikitext 行时维护当前 section 上下文。

### Q6：Liquipedia 时区修正会影响已有数据吗？

不会。修正只影响 `parseLiquipediaDate` 的解析结果。如果 Liquipedia 没有时区标注（某些旧赛事），`tzOffset=0`，退化为当前行为。修正后的时间更准确，不会更差。
