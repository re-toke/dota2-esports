## 二、🔴 必须修正：方案②的前提不成立

方案原文写「目标表已存在」，据此判定该项「难度低」。

**实测结果**：

```
curation_events   🔴 0 行 —— 表存在但为空
curation_teams    🔴 0 行 —— 表存在但为空
curation_meta     🔴 0 行 —— 表存在但为空
```

### 这意味着什么

- 「表存在」= 001-init.sql 建过 schema；但**从未真正灌过数据**
- 云函数的 curation 数据实际来自**代码内打包的 `curation-shared.js`**（随部署分发），不走 DB
- 所以 ② 若照原方案「把读迁到表」→ **客户端会读到空数据，直接丢失 curation**

### 修正后的 ② 方案

必须先回答「**写入方在哪**」（这正是我在方案里列的贯穿原则，但自己没先去验证）：

```
真实数据源 = 代码内 curation-shared.js（两端镜像，已由 sync-canon-map 保证一致）
                                         ↓ 需要新增
写入路径    = ① GH Actions 把 curation 灌进 curation_events/teams（与 LP 同一套路）
              或 ② 云函数 adminWriteCuration 双写 Supabase
读取路径    = 客户端 PostgREST 直读（此时才有意义）
```

**并且要先确认**：`utils/remoteCuration.js` 是否已有「远程失败 → 回落到代码内 curation」的兜底？
若有 → 迁移风险低（最差退化为打包数据）；若无 → 必须先加兜底再迁。

## 三、方案遗漏项（本次审计新发现）

### 🔴 遗漏 1：`aggregation_cache` 没有 GC，过期行永久堆积

```
合计 198 行 | 已过期 9 行   ⚠️ 无 GC 机制
```

每行都有 `expire_at`，但**没有任何进程删除过期行**。现在 9 行无所谓，但：
- `od:*` 类缓存每次新 SQL 都新增一行且 TTL 短 → 长期是主要增长源
- 表的体积会无限增长（Supabase 免费/低配套餐的存储与查询性能都会受影响）

**建议**：在 GH Actions 同步脚本末尾加一步 `DELETE FROM aggregation_cache WHERE expire_at < now()`（用 service key 走 REST DELETE）。一次写入、每日回收，成本极低。

### 🟡 遗漏 2：`od:` 缓存的 key 是**完整 SQL 字符串**

实测样例 key 长度 400+ 字符：

```
od:/explorer?sql=SELECT%20leagueid%2C%20min(start_time)...（约 400 字符）
```

- `key` 是主键 → 超长主键影响索引效率
- 每个不同的 SQL 参数组合 = 新行（SQL 里带 `start_time > 1781237283` 这类**随时间变化的常量**）→ **行数会持续增长**

> ⚠️ 注意：这正是项目记忆里记过的坑 —— explorer SQL 的**时间下界必须对齐当日 00:00 UTC**，否则缓存 key 每秒漂移、永远 miss。现在看是**对齐了**（key 里的整数是固定值），但每过一天就是一个新 key → 每天新增行数 = 当天用到的不同 SQL 数。

**建议**：要么加 GC（遗漏 1 已覆盖），要么把 `od:` key 改为「SQL 模板 + 参数哈希」。

### 🟡 遗漏 3：`lp:logo:*` 尚未灌表

方案把队标迁移标为「已完成」，但**数据还没进表**。真机此时走的仍是云函数回落。

## 六、贯穿教训（本次复核再次印证）

方案里我自己写了「**每项先验证前置假设**」和「**先问写入方在哪**」，
结果 ② 这一项**两条都违反了** —— 凭「表存在」就判定「难度低」，没去查表里有没有数据。

> **写方案时也得遵守自己定的原则** —— 「表存在」≠「表有数据」，
> 就像此前「客户端有本地解析路径」≠「本地解析能拿到数据」、「LP 服务可迁」≠「灌表范围覆盖对阵页」。
> **同一个思维漏洞，今天已经是第三次踩了。**
